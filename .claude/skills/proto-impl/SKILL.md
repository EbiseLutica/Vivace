# proto-impl

Vivace の実装を、1つの PR ずつ進めるための手順。実装の順番と、どこまでできたら次へ進むかの正は `docs/IMPLEMENTATION.html`。各 PR に共通の決まりは、その文書の「各 PR に共通の決まり」にある。

## 方針

- 節目ごとに、動かして眺められる状態にする。どの PR も、マージした時点で `vivace run` と `vivace dry-run` が動く
- 設計書（`docs/design/`）は完成形として残す。各節目では、その中から要る部分だけを作る
- 形を整えるだけのリファクタの PR は作らない。邪魔になったら、そこを触る PR の中で直す

## やること

### 1. 次の PR を決める

1. `main` を最新にする
2. `docs/IMPLEMENTATION.html` を読み、チェックの入っていない最初の節目と、その中の未完の項目を見る
3. 1つの PR の範囲を決める。差分は 1,500 行以内を目安にし、マージした時点で動く所で切る。ユーザーが範囲を指定したら、それに従う
4. 範囲を1行でユーザーに伝えて、そのまま進める（返事は待たない）
5. ブランチ `impl/mN-内容` を作る（例：`impl/m1-system-clock`）

### 2. 実装を頼む

Haiku のサブエージェントに実装を頼む。サブエージェントはこの会話を知らないので、依頼文に次を入れる。

- IMPLEMENTATION の該当の節（この PR で作る項目）と、参照の章
- 範囲外のもの（節の「範囲外」と、この PR で作らない残りの項目）
- 完了条件（節の完了条件のうち、この PR で満たすもの）
- `CLAUDE.md` に従うこと
- 関心ごとにコミットし、各コミットでビルドとテストが通る順に並べること
- 終えた項目は、IMPLEMENTATION のチェックを入れること（`checked` を足す）
- プッシュしないこと
- 自分で `dotnet build`（警告0）と `dotnet test` を回すこと

### 3. メインが確かめる

サブエージェントの報告を鵜呑みにしない。報告の事実は間違っていることがある。

- メインも `dotnet build` と `dotnet test` を回し、差分を読む
- `vivace run` か `vivace dry-run` を回し、振る舞いの変化を自分の目で見る

### 4. レビューを1回だけ頼む

Opus の別のサブエージェントに、ブランチの差分のレビューを1回だけ頼む。

- IMPLEMENTATION の節と設計書と照らす
- 再現と変異（わざと壊す）で確かめる
- 指摘に重大度（blocker / should-fix / nit）を付けて返す

指摘の扱い：

- **blocker**：実装したサブエージェントに続きを送って直させる（コンテキストが残る）。直した差分は、メインが確かめる。レビューのサブエージェントには戻さない
- **should-fix**：この PR で直すか、次の PR に回すかをメインが決める。回したものは、IMPLEMENTATION の該当の節に項目として足す
- **nit**：直さなくてよい

### 5. PR を作る

PR の本文は通常の日本語で書き、次を入れる。

- 何をしたか（IMPLEMENTATION の節と項目）
- `vivace run` か `vivace dry-run` の出力の変化（前後の抜粋）
- ユーザーに見てほしい判断：多くても3件、1行ずつ。なければ書かない
- 次の PR に回したもの
- 確かめたこと：そのコミットで実際に確かめたことだけを書く。前のコミットで確かめたことは、そう書く

PR を作ったら、ユーザーのマージかレビューの返信を待つ。レビューの返信には、メインのエージェントが自分で対応する。マージされたら、次の PR へ（1. に戻る）。

## 設計の判断

- 設計の一部だけを作るのは、設計書を直さず、IMPLEMENTATION の「範囲外」に書く
- 設計の判断が要るとき、VISION の考え方を変えないものはメインが決め、PR に書く。変えるものはユーザーに聞く
- J-xx に載せるのは、設計書の本文と食い違う判断だけ。正の章の本文を直し、`docs/design/index.html` の「枠の外の判断」に、出どころ「エージェント（PR #N）」を付けて載せる。「合意」の印は付けない
- エージェントが決めた J は、運転して困ったら、ユーザーに断らずに決め直してよい。決め直したら行を書き換え、出どころをその PR にする。出どころが「ユーザーが確認」のものを変えるときは、ユーザーに聞く

## 気をつけること

- エージェントどうしのやり取り（サブエージェントへの依頼文、サブエージェントの報告、続きの指示）は、原始人モード（genshijin の通常）で書く。敬語、前置き、クッション言葉を削り、体言止めと箇条書きで短くする。技術用語、コード、ファイルパス、数値、エラーメッセージはそのまま正確に残す。依頼文では、その書き方で報告するよう指定する
- 原始人モードはエージェントどうしの出力だけ。ファイルの中身（コード、コメント、設計書）、コミットメッセージ、PR の本文とコメントは、通常の日本語で書く
- レビューのあとに履歴を組み直すときは、最終のツリーがメインの確かめたものと一致することと、各コミットでビルドとテストが通ることを確かめる
- GitHub への書き込み（PR のスレッドへの返信、resolve）は、権限で止まることがある。止まったら、文案をユーザーに渡す
