オーサリング支援：長文からの生成

長文の自由記述から、LLM で構造化データ（ワールドの場所、ペルソナの性格や生活習慣など）を生成する機能は、コアには入れない。TOML を書き出す入力手段として、コアの外の作者向けツール（CLI やフロントエンド）に、後から足す。最初の到達点（ebise 相当の再現）には要らない。方式は未決で、いまの案は次のとおり。

  • 全体を再生成せず、lore の変更をパッチとして提案させる。LLM には、旧 lore、新 lore、現在の構造化データ（手直し込み）を渡し、追加・変更・削除を出させて、ユーザーが差分を見て承認する
  • 構造化データから lore への同期はしない。lore は元の設定メモで、実行時の正ではない
  • 構造化データの各項目に「生成 / 手直し」の印を付け、手直し済みの項目に触れるパッチは個別に確認する
  • 生成時の lore のハッシュを持ち、変わっていなければ LLM を呼ばない
  • ワールドとペルソナで、同じ部品（原文 + 構造化 + パッチ）を使う

モバイルアプリ

「メールチェックも調べ物もしない。勝手に仮想世界の中で動き回るだけで、あなたの秘書にはならないが、あなたと友達になり、メッセージを送ると返してくれることがある AI スマホアプリ。Claude などの API キーを登録して使う」も、コアの大きな設計変更なしに作れる見込み。

秘書にならない

ペルソナの行動とツールを、ユーザーの外部資源（メール、Web など）に触れないものだけに限る（許可リスト方式。7章）。

返してくれることがある

受信箱と availability の機能そのもの。アプリ内チャット用の AppChannel（チャンネルのプラグイン）を足す。

実装

.NET MAUI（または Avalonia）で Vivace.Core を参照する。

  • バックグラウンドで動き続けられない（特に iOS）。アプリを開いたときに、前回から現在までを早送りでシミュレートする追いつき（4章）で対応する。ペルソナから話しかけるのは難しい（端末ローカルの通知を事前に仕込む手はあるが確実ではない。Android は定期ジョブで近いことができる）
  • API キーの持ち込み（BYO）: 端末の安全な領域（Keychain / Keystore）に保存し、端末から直接 API を呼ぶ。使用量の見える化と、予算の上限が要る
  • ILlmClient は複数プロバイダに対応できるようにする
  • ストア審査で、AI コンパニオンとしての年齢区分や安全面の説明が求められやすい
コアに足す項目 AppChannel、使用量の計測と上限。追いつきは、コアの標準機能（4章）。

旅行

ペルソナが別のワールドへ旅行する機能。旅行がなくても、ワールドが複数あれば要る決めごと（時計とループはホストに1つ、時刻は UTC、ペルソナごとの乱数、記憶の worldId）は、本文に入れてある。作るときの要点は次のとおり。

  • 接続: ワールド定義に、出口の場所（駅など）と、相手ワールドの到着の場所（転移門など）を結ぶ接続を宣言する。両側が宣言して初めて成立する。到着の場所を省略したら、相手ワールドの既定の入口にする。手段と所要時間は、接続に持たせる
  • 前もって計画する: 旅行は、前もって決めた日に行く。最初は、作者が固定予定に書き、家と出口の間の移動は Planner が挿入する。行けなくなったら、ブロックの開始時の確認で中止する（欠席と同じ）。旅行の好み（travelAffinity）で計画を抽選するのは、事前に予定を組む仕組み（下表）と一緒に考える
  • 時間の持ち主: 出発の時点で、ペルソナの所属を旅行先のワールドに書き換える。キューとループはホストに1つ（4章）なので、受け渡しは所属の書き換えで済む。居住ワールドには「不在」と記録する。受信箱とチャンネルはインスタンスに付いてくる
  • 旅行先で: 携行品に、持っていけるか（portable）を付け、持っていけない物が要る行動は候補から外す。話題の判定は、いまいるワールドの lore と場所で行う。訪問者は、旅行先で場所を生成しない
  • 記憶: 旅の思い出は、元のワールドでも話題にできる。ただし、旅行先の場所は、元のワールドの行き先の候補にしない。複数のワールドにまたがる記憶の worldId の扱いは、このとき決める
  • 同行: 旅行先での同行は、ペルソナ同士の関わり（14章）と一緒に設計する。同行中に現地のペルソナが生成した場所は、旅行先のワールドに属する
  • 他のユーザーのワールドへの訪問（マルチプレイ）は、セキュリティを含めて、さらに別の機能として考える
