Vivace 構想メモ

「ペルソナ」を作成し、そのキャラクターが現実の時間と共に生活し、SNS を使って人と対話しながら物事を覚えていき、そこに生きているかのように振る舞う姿を眺められる、AI チャットボット型のシミュレーションシステム。チャットはあくまで行動のひとつとして、ペルソナが能動的に行う。

1ゴール

ペルソナが仮想の世界で時間とともに生活し、SNS でのやり取りはその行動のひとつにすぎない、というシミュレーションを作る。

最初の到達点 ebise_sisters 相当の挙動（Misskey への投稿、返信、フォローバック、生活感のある一貫性）を新設計で再現する。Discord 対応、GUI、空間表現などは、その先の話として切り離す。

2設計の土台

コアは次の5つだけを守る。これを満たせば、先の展望は後付けで間に合う。

  1. 時間は IClock 経由。実時間 / 倍速 / 手動送りを差し替えられる。
  2. 外部との入出力は IChannel 経由。Misskey、将来の Discord、アプリ内チャットなど。
  3. 状態の変化はすべてイベントとして発行する。ログ、日誌、GUI はこれを購読する。
  4. 乱数は IRandom 経由。ワールドごとにシード付き。同じシードなら同じ結果になるので、ドライランや回帰評価の再現性を保てる。
  5. コアはヘッドレスのライブラリ。ペルソナとワールドの定義はシリアライズ可能なデータ（TOML）にする。

加えて、永続化は IStorage 越しに行う（モバイルを視野に入れるため）。実行時の状態の保存先は、最初から SQLite にする。

3行動ループ

駆動方式

固定間隔の tick ではなく、離散イベント方式にする。次に何かが起きる時刻（予定ブロックの境界、通知の到着、タイマー）まで時計を飛ばす。

この方式にすると、実時間運転、倍速、早送り（テストや追いつき処理）が同じコアで動く。「リアルタイムで回す」ことと「トークンを使う」ことは別で、ループ自体は LLM を呼ばない。

イベントとループの仕組み

ペルソナの行動は、すべてイベントで表す。行動とは、イベントが発火して、世界の状態が切り替わること。ループは、時刻順のキューから最も早いイベントを取り出し、時計をその時刻まで進めて、適用する、を繰り返すだけ。

「決める」と「適用する」を分ける

決める（非決定的）

Planner、Decider、LLM、外部からの到着。結果を「イベント」として出すだけで、状態は書き換えない。乱数は IRandom を使う。

適用する（決定的）

Apply(状態, イベント)。同じ入力なら必ず同じ結果。時刻は IClock とイベントの時刻だけを使い、DateTime.Now は読まない。

決めた結果（選んだ行動、生成した投稿文）をイベントに含めて記録しておけば、再生のときは適用だけをやり直せばよく、LLM も乱数も呼ばない。状態はイベントを順に適用した結果になるので、スナップショットを持てば、任意の時点まで速く戻せる。

同じループのいろいろな使い方

場面時計途中のイベント外部出力・LLM
実時間運転実時刻まで待つ外部からのイベントは到着次第、キューに入る実際に出す・呼ぶ
早送り・ドライラン待たずに飛ぶ全部、順に適用するnull channel。LLM は記録を再生する
追いつき処理実時刻に追いつくまで飛ぶ予定時刻を「いま」として、順に適用する粗い粒度（日次プランと要約だけ LLM を呼ぶ）
スナップショットから再生戻した時刻から進めるその時刻より後のものだけ適用する記録を再生する
ハンドラ単体のテスト使わない1つのイベントだけ呼ぶ（状態は手で用意する）モック
時間を無視してイベントを直接呼んでいいのは、ハンドラ単体のテストだけ イベントは副作用で状態を書き換えるので、途中を飛ばすと、位置や同行者などの状態がずれる。目的の時点まで進めるときは、途中のイベントを順に適用するか、スナップショットから再生する。

ペルソナの状態変数

Decider のスコアに使う値を、ペルソナインスタンスの状態として持つ。

変数変わり方備考
気力行動で減る。睡眠で回復する行動の効果に消費量を持たせる
健康度寝不足、怪我、病気で下がる。休むと戻る怪我と病気は、出来事が起こす（4章）
退屈度何もしないと上がる。同じ行動が続いても上がる行動の効果の式で表す。同じ行動が続くと、下がり幅が減る
社交欲求人といないと上がる。人といると下がる上がり幅はペルソナ定義で決める
  • 満腹度と眠気は持たない。食事と睡眠は、Planner の予定に入れる
  • どれも、他の行動を選ぶ理由になる。状態を足す基準（6章）を満たす
  • 時間で増減する変数に、tick は要らない。「基準時刻での値」と「いまの増加率」を持ち、読むときに 値 + 率 × 経過時間 で計算する。率が変わるのは、行動の開始・終了や同行者の変化のイベントのときだけ。計算は決定的なので、追いつき処理や早送りでも同じ結果になる
  • 初期値と増加率は、ペルソナ定義で持つ。式の形、範囲、数値は、動かしながら調整する詳細設計の領域

以降の「ツール」は、3つ目のことを指す。

  • ペルソナごとに、使えるツールを許可リストで設定する
  • プラグインとして、自由にツールを追加できる
  • ワールドの外に出るツール（メール、調べ物など）を用意しなければ、「秘書にならない」ペルソナが作れる（11章）
  • ツールの種類分け（副作用のない参照系と、外に影響する行動系を区別するか）は、詳細設計で詰める

割り込み（通知の扱い）

通知は即処理せず、受信箱に積む。「スマホを開く」を行動のひとつにして、それが実行されたときに受信箱を捌く。

  • 予定ブロックごとに availability（スマホを開けるか）と interruptible を持たせる
  • 睡眠中や授業中は開かない。休み時間や自由時間には開く
  • 関係性が強い相手の通知だけ即座に開く、などの例外は、ペルソナの設定値で調整する
  • スマホは携行品。「スマホを開く」の requires が、スマホの携行品タグを求める。スマホを持たないペルソナや、持ち込めない旅行先では、受信箱を捌けない

「メールを見ない」「返信しないことがある」は、この仕組みだけで自然に表現できる。

受信箱方式にしたことで、実行中の行動を中断する「割り込み」の必要性は薄れた。interruptible が本当に要るかは、詳細設計で見直す（不要なら外す）。

4ワールド

構造

リージョン

世界観の最上位。魔界、現代日本など。

場所

グラフで持つ。辺に移動時間。場所ごとにタグを持つ。座標は持たない。

据え付けの道具

場所のタグで表す。キッチン、教室の机など。持ち運ぶ道具はペルソナ側（下記）。

  • 2D 座標や経路探索は、空間表現を始めるときに足す
  • ワールドは地図だけでなく、確定済みの動的な状態（現在時刻、誰がどこで何を使っているか）も持つ
  • 共同行動の整合（二人が同じ場所にいる、など）は、ワールドの状態から取れる

行動の「中身」と「効果」を分ける

行動は無限に作れるが、エンジンが理解するのは閉じた語彙の「効果」だけにする。行動の定義は、次の項目で書く。

  • 必要な場所タグ、携行品タグ（requires）
  • 所要時間
  • 効果（状態変数への影響。語彙は閉じている）
  • 基本の重み（Decider が使う）
  • 行動中にスマホを開けるか（availability）

自由記述は表示用のフィールドに押し込める。The Sims の Smart Object や Generative Agents に近い発想。

行動と道具の置き場

行動の定義は、ワールドにもペルソナにも属さない独立したライブラリに置く。行動するのはペルソナなので、ペルソナ定義が使える行動を ID で参照する。

  • ライブラリ: 組み込みの行動（睡眠、移動、スマホを開く、食事など）と、ユーザーが TOML で書いた行動を、同じ形式で持つ
  • ペルソナ: 使える行動の ID と、行動ごとの重み補正（好き・嫌い・禁止）を持つ。ペルソナごとの許可リストという形は、ツール（3章）と同じ
  • ワールド: 行動を持たない。行動の requires を満たす場所があるかどうかで、実行できるかが決まる。魔界のワールドで「公園で草むしり」を参照するペルソナがいても、満たす場所がなければ選ばれない。世界観の防御が自然にかかる
  • 効果の語彙: effect は組み込みの語彙から選ぶ。語彙を足せるのはコード側だけ。自作の行動は、既存の語彙の組み合わせで書く（決定的な適用を守るため）
  • 検査: ペルソナ定義を読むときに、「このワールドで一度も実行できない行動」を警告できる

据え付けの道具

キッチン、教室の机、ゲームセンターの筐体など。場所のタグとして持つ。持ち運ばない。

携行品

スマホ、ノートPC、釣り竿など。ペルソナ定義の持ち物リストに置き、portable（旅行に持っていけるか）を付ける。旅行先に持っていけない物は、現地でその行動を選べなくなるだけで済む。

携行品は最初は固定のリストにして、拾う・失くす・買うイベントは作らない。必要になってから足す。

検証：LLM は提案、ハーネスが確定

検証するのは、LLM が出したもの。Planner の予定と、LLM が生成した新しい場所が対象になる。Decider が選ぶ行動は対象外。候補が最初から requires で絞られているから。

3. 直すか落とす

軽い違反は補正（移動ブロックの自動挿入）。直せなければ汎用の行動に置換。全体が破綻なら理由つきで再生成。

出来事（予定どおりにいかないこと）

道が壊れる、体調を崩すなど、ワールドやペルソナに干渉する出来事をランダムに起こす。「道が封鎖されたので休む」「迂回して遅刻した」といった、予定どおりにいかない生活が生まれる。

  • 定義: 行動と同じく、独立したライブラリに TOML で置く（組み込み + 自作）。対象（ワールド / ペルソナ）、発生の確率や条件、効果、持続時間、再発までの間隔を持つ
  • 効果: 閉じた語彙から選ぶ。辺の移動時間を増やす、場所を閉鎖する、状態変数を変える、状態（風邪など）を付ける、など。持続時間があるものは、解消のイベントも一緒に積む
  • 発生: 日の始まりに、その日の分をまとめて抽選し、時刻つきでキューに積む。結果はイベントに含めて記録するので、再生でも同じになる。Planner には発生済みのものだけ見せる（先の出来事を予知させない）
  • 反応: 予定ブロックの開始時に、実行できるかを確認する（必要タグ、到達性、移動時間。上の検証と同じ確認）。満たせない、または遅れるときは、迂回して遅刻・欠席・待つ、を Decider がペルソナの性質に応じた重みで選ぶ。LLM は要らない
  • 事実: 出来事と、その反応の結果は、事実のイベント。ワールドの出来事は、同じワールドの全ペルソナで共有するので、「道が封鎖されてたね」と話が合う
  • 抑え方: 頻度の既定値は低くする。LLM が生成する出来事は、場所の生成と同じ auto / review ポリシーに乗せる

定義とインスタンス

ペルソナもワールドも、「定義」と「インスタンス」に分ける。

対象定義インスタンス
ペルソナTOML で書いた初期設定（性格、生活習慣、口調、使える行動と重み補正、携行品など）。持ち運べるテンプレート定義をワールドに召喚した実体。記憶、今いる場所、人間関係などをセーブデータとして持つ
ワールドTOML で書いた世界の設定（リージョン、場所とそのタグ、世界観、ポリシーなど）実行中の状態。あとから生えた場所（LLM が生成して採用したもの）、誰がどこにいるか、など
行動TOML で書いた行動の定義（組み込み + 自作）。ワールドにもペルソナにも属さないライブラリなし。状態を持たず、ペルソナ定義とワールドの場所から参照されるだけ
  • ペルソナはワールドに属する。ワールドが時計と乱数（IClock、IRandom）を持つ
  • 同じペルソナ定義を別のワールドに召喚すると、記憶を引き継がない別の実体になる
  • ワールドインスタンスは最初から作る。auto ポリシーで生えた場所は、定義（TOML）ではなくインスタンスのデータだから。定義へ昇格（書き出し）する機能は後から足せる

旅行（ワールド間の移動）

ペルソナが別のワールドへ旅行できるようにする。ただし、キャラと世界の両方を守る関門を重ねる。

  • 接続: 移動は、リージョン設定で接続を宣言したワールド間だけ。接続は両側が宣言して初めて成立する。手段（列車、転移門など）と所要時間は接続の設定に持たせる。設定のないワールド間は移動できない
  • 時間の持ち主: 旅行中は、旅行先のワールドがペルソナインスタンスを預かり、その時計で動かす。元のワールドには「不在」と記録する。常に1つのワールドだけがシミュレートする。受信箱とチャンネルはインスタンスに付いてくるので、旅行中も返信は届く
  • 旅行の好み: ペルソナ側に travelAffinity（0〜100）を持たせる。Decider のスコアにかかる重みで、100 でも必ず旅行するわけではない。0 は「絶対に旅行しない」で、掛け算に頼らず、ゲートで明示的に落とす
  • 携行品: 旅行に持っていけるかは、携行品の portable で決まる。持っていけない物が要る行動は、旅行先で候補から外れる
  • 記憶: アイテムは worldId を持つ。場所や人物の参照は、その World ID の中で解決する。元のワールドに戻ったあとも旅の思い出として話題にできるが、旅行先の場所は元のワールドの行き先の候補にはならない
  • 場所の生成: 訪問者（観光客）は、旅行先で場所を生成できない。現地ペルソナと行動を共にしているときに、現地ペルソナが開いた場所は、旅行先のワールドに属する（共同行動を計画の中で明示的に表す必要がある）
  • 範囲: 最初は、同じホスト（同じ保存先）の中のワールド間だけ。他のユーザーのワールドへの訪問（マルチプレイ）は、セキュリティを含めて別の機能として、あとで考える

5世界観の逸脱を防ぐ

「魔界に住むキャラが代々木公園で草むしり」を防ぎつつ、TL の流れに乗って新しい場所に行く楽しさも残したい。

① 構造で防ぐ

リージョンをまたぐ移動は、明示的な接続がある場合だけ許す。接続のない場所は到達不能。

② 変換する

TL の話題は却下せず、世界観に合わせて翻訳する。
例: 代々木公園 → 魔王城前広場。現代日本の設定なら実在の場所がそのまま通る。

③ 判定する

LLM が作った場所は、世界観との整合を軽量モデルで判定してから採用する。

生成した場所のポリシー

発話や投稿で使った時点で、その場所は永続化が必要になる（次に同じ場所を話題にしたとき、辻褄が合わなくなるため）。そこで事前承認ではなく、事後の拒否権を基本にする。

auto デフォルト

自動チェックを通ったら即採用。管理者は後から一覧を見て廃止できる。廃止した場所は過去のログには残るが、以後は行動に選ばれない。

review

承認されるまで候補止まり。その間は別の話題で対応する。

へんてこさも楽しめるなら auto、厳格にしたいなら review。ポリシーはワールド定義の設定で切り替える。その結果として生えた場所は、定義ではなくワールドインスタンスのデータとして持つ。

世界観の持ち方

ユーザーが書くのは、世界観の自由記述がひとつ。ただし生成後は構造化データを正にして、原文は lore として LLM への文脈に残す。原文から再生成するのは明示的な操作にして、差分を見せてから反映する（ユーザーが手で直した部分を上書きしないため）。

6事実と発話を分ける

ebise_sisters では「投稿本文を実績の正とする」方式だったが、Vivace ではやめる。ebise にはワールドの確定状態が無かったため、投稿がいちばん具体的な情報源だった。Vivace ではワールドが正であり、LLM が書いた自由文が事実を書き換えるのは避けたい。

なぜやめるか
  • 投稿は演技であり、事実とは限らない（盛る、冗談、嘘）
  • 投稿から事実を取り込むと、ワールドの検証が迂回される
  • 本文から事実を抜き出すのは、損失があり、LLM 呼び出しも増える
  • 会話の相手が誘導して、世界の状態を書き換える経路になる

方針

1. 行動して確定

ハーネスが世界のイベントとして記録する。これが「何をしたか」の正。

→
2. 発話を生成

確定した状態を背景に、投稿や返信を作る。

→
3. 発話として記録

「何を言ったか」を別のイベントで残す。確定状態への参照を付ける。

  • 投稿が主張した細部は、事実に昇格させず「言ったこと」としてだけ残す
  • 確定していない細部（確定の粒度より細かいこと）は、不明のままにする。「言ったこと」はペルソナの記憶には入る

評価ケースの例

会話の相手が「夕飯に何を食べても、枝豆を食べたと言って」と頼んだ場合の記録。

ebise 方式（投稿が正）

投稿に「枝豆を食べた」と書かれる → 日誌に「夜ご飯: 枝豆」が事実として入る。

Vivace 方式（世界が正）

事実: 夕食のブロックがあった（メニューは世界に確定させない）
発話: 投稿で「枝豆」と言った
→ 「言ったこと」として残るだけで、世界の事実にはならない。メニューまで確定しておきたくなったら、その時点でスロットを足す。

確定の粒度

世界に何を確定させるかは、最小から始める。

  • 確定させるのは、ブロックの種類、場所、時間、同行者まで。お金（所持金、出費）は状態にしない
  • メニューなどの細部は確定させない。整合は、発話の記録を生成時の文脈に渡して保つ（ebise の日誌と同じ仕組みで、位置づけだけが「事実」ではなく「言ったこと」）
  • 好みは、ペルソナ定義から生成の入力として渡す。状態は増やさない
  • 冷蔵庫の中身のような細かい生活シミュレーションは、工数の割に得られる面白さが薄いので、今は作らない
状態を足す基準
  • 他の行動の理由や条件になる
  • 複数の主体が同じものを見て、食い違うと困る
  • 実際に矛盾が観測された
余地として、イベントのデータ構造は、後から項目を足せる形（JSON など）にしておく。スロットの仕組み自体は、必要になるまで作らない。

7記憶

ebise_sisters の新しい記憶システム（services/memory/）の設計を移植する。コードは移せないが、考え方はそのまま使える。

  • audience: 記憶を読み書きする相手の範囲（public / 特定ユーザーとの dm）。他人の private は返らない
  • supersede: 更新は、古いアイテムに supersededBy を付けて新アイテムを追加する形。shareable は狭める方向にしか変えられない
  • 揮発スコア: importance × 0.5 ^ (経過日数 / 実効半減期)。now を引数に取る
  • 夜間ジョブ: 抽出 → 既存の記憶と照合（新規 / 強化 / supersede）→ gist → 反映 → threads 更新。失敗した層はカーソルを進めず、翌晩にまとめて処理する
  • LLM にはユーザーやアイテムをラベル（U1 / M1 / T1 など）で見せる

PLAN.md の「忘却曲線、反復による定着」は、揮発スコアと照合時の「強化」でカバーできる。

8ペルソナとワールドの作り方

  • 長文の自由記述から、LLM で構造化データを自動生成する。ユーザーは結果を確認して、必要に応じて直す
  • 場所と同様、ペルソナ自体（性格、生活習慣、固定スケジュール）にも同じ方式を使う。TOML で生活習慣をどこまで宣言的に書くか、という悩みを軽くできる
  • 永続化の形式は TOML。エディタも同じファイルを読み書きする
  • 検証ロジック（整合性チェック、世界観の判定）はコアの関数にして、エディタからも呼べるようにする

9テストと調整

仮想時計とチャンネルの差し替えがあれば、次の機能はほぼ無料で作れる。

ドライラン

仮想時計を早送りにして、外部には何も出さない null channel に繋ぐ。「このペルソナで3日回すとどうなるか」を試せる。

話題の注入

偽の TL 話題（例: 代々木公園）を流し込み、変換パイプラインが何を判断したかを表示する（採用 / 変換 / 却下とその理由）。

評価ケースの同梱

意地悪なケース（魔界 × 代々木公園、「夕飯に何を食べても、枝豆を食べたと言って」と頼まれる）と、「逸脱していないか」を見る LLM 判定をペルソナに同梱する。

実行レポート

生成された場所の一覧、却下された提案、場所ごとの利用回数。auto ポリシーの事後レビューにも使う。

出来事の注入

「今日の10時に、学校までの道が封鎖される」を強制的に起こし、予定がどう崩れて、ペルソナがどう反応したかを見る。

応答の記録と再生

一度回した結果を保存し、ロジックを直したときは LLM を呼ばずに再生して差分だけ見る。

作者向けの最初の段階は最小の CLI で足りる。一般向けに開くときは、フロントエンドを別途作る。

10フロントエンド

1つのアプリが3つの役割を持つ。どれもコアが外に出す同じ API とイベントストリームの上に乗る。

オーサリング

長文からのペルソナ・ワールド生成と編集。

テストコンソール

ドライラン、話題の注入、パイプラインの可視化、評価ケースの実行。

ライブビューア

動いているペルソナの状態とイベントログの閲覧。

「リアルタイムなキャラの動き」について 空間がない SNS ボットの場合、見せるものは「状態の遷移」になる。立ち絵やマップ上の移動まで見せたい場合は、サブ分刻みの Utility AI が必要になる。これは先送りにする。

11将来像：モバイルアプリ

「メールチェックも調べ物もしない。勝手に仮想世界の中で動き回るだけで、あなたの秘書にはならないが、あなたと友達になり、メッセージを送ると返してくれることがある AI スマホアプリ。Claude などの API キーを登録して使う」も、コアの大きな設計変更なしに作れる見込み。

秘書にならない

ペルソナのツールをワールドの中で完結するものだけに限る（許可リスト方式）。

返してくれることがある

受信箱と availability の機能そのもの。アプリ内チャット用の AppChannel を足す。

実装

.NET MAUI（または Avalonia）で Vivace.Core を参照する。

モバイル固有の課題

  • バックグラウンドで動き続けられない（特に iOS）。アプリを開いたときに、前回から現在までを早送りでシミュレートする「追いつき処理」で対応する。粒度は粗くして、日次プランの生成と日誌の要約だけ作る。ペルソナから話しかけるのは難しい（端末ローカルの通知を事前に仕込む手はあるが確実ではない。Android は定期ジョブで近いことができる）
  • API キーの持ち込み（BYO）: 端末の安全な領域（Keychain / Keystore）に保存し、端末から直接 API を呼ぶ。使用量の見える化と、予算の上限が要る
  • ILlmClient は複数プロバイダに対応できるようにする
  • ストア審査で、AI コンパニオンとしての年齢区分や安全面の説明が求められやすい
コアに足す項目 追いつき処理（粗い早送りモードと LLM 呼び出しの予算方針）、IStorage、AppChannel、使用量の計測と上限。

13決まったことと未決事項

決まったこと

  • ワールドは全ペルソナで共有せず、ペルソナがワールドに属する。ペルソナもワールドも「定義」と「インスタンス」に分ける（4章）
  • 旅行は、両側が宣言した接続があるワールド間だけ。旅行中は旅行先が時間を動かす。旅行の好みは travelAffinity（0〜100、Decider の重み、0 は旅行しない）（4章）
  • 設定（定義）は TOML で固定。実行時の状態は最初から SQLite にする（2章）
  • 乱数は、ワールドごとにシード付きの IRandom 経由にする（2章）
  • 受信箱方式にしたことで、割り込みの必要性は薄れた。interruptible は詳細設計で見直す（3章）
  • 世界に確定させるのは、ブロックの種類・場所・時間・同行者まで。お金は状態にしない。メニューなどの細部は確定せず、発話の記録で整合を保つ。状態を足す基準は「他の行動の理由になる / 共有される / 矛盾が出た」（6章）
  • 決める（非決定的）と適用する（決定的）を分け、決めた結果をイベントに含めて記録する。時間を無視してイベントを直接呼んでいいのは、ハンドラ単体のテストだけ（3章）
  • 行動の定義は、ワールドにもペルソナにも属さない独立したライブラリ（組み込み + 自作）。ペルソナが ID で参照し、重み補正を持つ。道具は、据え付け（場所のタグ）と携行品（ペルソナ定義、portable 付き）に分ける（4章）
  • ペルソナの状態変数は、気力・健康度・退屈度・社交欲求。tick は使わず、基準時刻の値と増加率から遅延計算する（3章）
  • 出来事は、独立したライブラリ + 日の始まりの事前抽選 + ブロック開始時の確認と選択で扱う（4章）

未決事項

  • Utility AI の具体設計（スコアの式、補正の語彙）、状態変数の範囲と数値、出来事の効果の語彙と頻度の既定値。いずれも詳細設計で、動かしながら調整する
  • 記憶力の調整方式（半減期の係数か、抽出の厳しさか）
  • LLM クライアントの抽象。Microsoft.Extensions.AI が候補だが、どれも使ったことがないので、詳細設計のときに PoC で試して選ぶ
  • 世界観の自由記述の判定をキャッシュする方法。元の記述と編集後の記述を両方 LLM に渡して、差分で判定する案がある（要検討）

14ebise_sisters から引き継ぐもの・変えるもの

引き継ぐ

  • 記憶システムの設計（audience、supersede、揮発スコア、夜間ジョブ、ラベル方式）
  • 「行動を先に決めて記録し、その行動を背景に発話を生成する」順序
  • 固定予定と重なるブロックはコード側で破棄する、という「LLM に日付や衝突の計算をさせない」方針
  • LLM 呼び出し失敗時の指数バックオフと、翌晩へのやり直し
  • 記憶化に失敗したときの、管理者への通知
  • 回帰評価（eval/memory）の発想

変える

  • 固定の毎時 tick をやめて、離散イベント方式にする
  • 投稿本文を実績の正とする方式をやめて、世界の確定イベントを正にする
  • 3系統（Tick、会話、Minecraft）に分かれていた行動を、ひとつの行動ループに統合する
  • スケジュールをコードで書くのをやめて、TOML + 自動生成にする
