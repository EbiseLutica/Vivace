1ゴール

ペルソナが仮想の世界で時間とともに生活し、SNS でのやり取りはその行動のひとつにすぎない、というシミュレーションを作る。

最初の到達点 ebise_sisters 相当の挙動（Misskey への投稿、返信、フォローバック、生活感のある一貫性）を新設計で再現する。Discord 対応、GUI、空間表現などは、その先の話として切り離す。

2設計の土台

コアは次の5つだけを守る。これを満たせば、先の展望は後付けで間に合う。

  1. 時間は IClock 経由。実時間が基本。倍速と早送りは、デバッグ用に差し替えられる。ワールドは時差を持てる。
  2. 外部との入出力は IChannel 経由。Misskey、将来の Discord、アプリ内チャットなど。
  3. 状態は、イベントの適用でのみ変わる。ログ、日誌（ペルソナの1日の出来事の要約）、GUI は、このイベントを購読する。外部からの干渉も、イベントの投入の窓口（3章）を通す。
  4. 乱数は IRandom 経由。ワールドごとにシード付き。同じシードなら同じ結果になるので、ドライランや回帰評価の再現性を保てる。
  5. コアはヘッドレスのライブラリ。ペルソナとワールドの定義はシリアライズ可能なデータ（TOML）にする。

加えて、永続化は IStorage 越しに行う（モバイルを視野に入れるため）。実行時の状態の保存先は、最初から SQLite にする。

3行動ループ

駆動方式

固定間隔の tick ではなく、離散イベント方式にする。次に何かが起きる時刻（予定ブロックの境界、通知の到着、タイマー）まで時計を飛ばす。

実時間運転が基本。この方式にすると、倍速や早送り（デバッグ、モバイルの追いつき処理）も、同じコアで動く。「リアルタイムで回す」ことと「トークンを使う」ことは別で、ループの仕組み（時計を進めて、適用する）自体は LLM を呼ばない。LLM を呼ぶのは、決める側のハンドラだけ。

イベントとループの仕組み

ペルソナの行動は、すべてイベントで表す。行動とは、イベントが発火して、世界の状態が切り替わること。ループは、時刻順のキューから最も早いイベントを取り出し、時計をその時刻まで進めて、適用する、を繰り返すだけ。

「決める」と「適用する」を分ける

決める（非決定的）

Planner、Decider、LLM、外部からの到着。結果を「イベント」として出すだけで、状態は書き換えない。乱数は IRandom を使う。

適用する（決定的）

Apply(状態, イベント)。同じ入力なら必ず同じ結果。時刻はイベントの時刻だけを使い、DateTime.Now も IClock も読まない（IClock を読むのは、ループだけ。決める側には、契機のイベントの時刻を now として渡す）。

決めた結果（選んだ行動、生成した投稿文）をイベントに含めて記録しておけば、再適用のときは適用だけをやり直せばよく、LLM も乱数も呼ばない。状態はイベントを順に適用した結果になるので、スナップショットを持てば、任意の時点まで速く戻せる。

時間と順序のルール

  • 世界の時刻は、実時刻 + 時差。時差はワールド定義で持つ。「日の始まり」は、そのワールドの現地時刻の日付境界。倍速と早送りはデバッグ用で、時間の流れを速める世界観は扱わない。「時間の概念がない」世界観でも、移動に時間がかかる以上、世界の時刻は存在する
  • LLM の推論は、ログの上では一瞬で終わったものとして扱う。ハンドラが出すイベントの時刻は、「契機のイベントの時刻 + 行動の所要時間」。秒単位の遅延は、分単位の所要時間に吸収される。予定の時刻を過ぎてから適用されたときは、そのまま適用し、遅れ（実時刻との差）を計測として残す
  • 決める側にも IClock は見せない。now は、契機のイベントの時刻を渡す。デバッグで時計を飛ばしたときに、決める側だけ別の時刻を見る事故を防ぐ
  • 決めるのは並列、適用は直列。決めるハンドラは、ペルソナごとのレーンで動く（同じペルソナの決定は順番に、ペルソナが違えば並列）。決める側が受け取るのは、契機の時点の状態の読み取り専用のビュー。適用は、1本のスレッドで、（時刻、種別の優先度、連番）の順に行う。実行中のハンドラの契機の時刻より後のイベントは、その出力が揃うまで適用しない（実時間では、次のイベントはたいてい未来にあるので、ほぼ待たされない）。他のペルソナの決定が前提を変えたときは、適用の前の検査で弾いて、決め直す。待っている間に届いた外部の到着は、到着時刻（実時刻）つきでキューに入る。再適用では決める処理が動かず、記録されたイベントを同じ順に適用するだけなので、並列でも影響しない。同行・共同行動は2人のレーンをまたぐので、ペルソナ同士の関わりの設計と一緒に決める
  • 順序は「（時刻、種別の優先度、連番）」で決める。同時刻のときは、出来事の発生と解消 → 反射の到達 → 外部の到着 → ブロックの境界と開始時の確認 → Decider の決定、の順。世界が先に変わり、ペルソナの身体が反応してから、予定や判断が走る。連番はキューに入れた順で、イベントログに記録する
  • 乱数は、ペルソナごとに派生した列。ワールドの種から、「ワールドの種:ペルソナID:用途」を安定したハッシュにかけて、ペルソナごと（用途ごと）に別のシードを導出する（string.GetHashCode() はプロセスごとに値が変わるので使わない）。同じシードを共有すると全員が同じ数列を引き、1本を共有すると、ペルソナを1人足しただけで他の結果が変わる。System.Random はバージョン間で同じ列になる保証がないので、IRandom の実装は小さな自前の PRNG にし、引いた回数のカウンタだけをスナップショットに保存する
  • 実際の送信時刻は、世界の時刻とは別。送信完了のイベントに、実時刻で記録する

Decider の候補の絞り込み

Decider は、1回に1つだけ決める。次の固定ブロックまでの全体は、計画しない。候補は、「行動 × 場所」の組で、次の3つを満たすものだけが残る。

  1. requires（場所のタグ、携行品のタグ）を満たす
  2. 帰還できる: 「いまから行動を終えて、次の固定ブロックの場所へ行っても、開始に間に合う」。式は 到着 = いま + 移動時間(いまの場所 → p)、終了 = 到着 + 所要時間、終了 + 移動時間(p → 次のブロックの場所) ≤ 次のブロックの開始
  3. クールダウンなどの制限に掛からない
  • 移動時間は、場所グラフの最短経路で出す。全点対の最短経路は、起動時に1回計算して、キャッシュする。所要時間は、先に IRandom で引いて確定させ（イベントに記録される）、確定した値で判定する
  • 別の場所の候補は、「移動 + 行動」を1つのまとまりとして選ぶ。決定のイベントが、移動の開始と到着、行動の開始と終了のイベントを積む。場所を固定するブロックの中では、場所をその場所だけに絞る
  • 組み込みの行動「次の予定の場所へ向かう」（移動して、着いたら待つ）は、条件が成り立つ限り、いつでも成立する。余裕がなくなると、候補がこれだけになり、Decider が自然に選ぶ。だから、候補が空になって詰むことはなく、隙間の長さを特別扱いする必要もない
  • この不変条件を壊すのは、外から来るもの（出来事、反射、予定の変更）だけ。そのときは、ブロックの開始時の確認で、遅刻や欠席を選ぶ。最初から成り立たない予定（隙間が移動時間より短い）は、Planner の検証で補正する

Decider のスコアに使う値を、ペルソナインスタンスの状態として持つ。

  • 急変動（出来事や行動の効果による増減）は、イベントの時刻での値を計算して、差分を足し、その時刻を新しい基準にする（版番号が上がる）。値は、上下限でクランプする。1つの区間の中で曲がる曲線（指数的な減衰など）は扱わず、必要なら率を区切って、折れ線で近似する
  • 初期値と増加率は、ペルソナ定義で持つ。式の形、範囲、数値は、動かしながら調整する詳細設計の領域

反射（状態が行動を強制する）

状態変数が極端な値になったときに、Decider と Planner を飛ばして、行動を強制する仕組み。脊髄反射にあたる。気力が尽きたら休む、健康度が下がったら早退する、など。

  • しきい値到達の予測: 変数は一次式で動くので、しきい値に達する時刻は計算で出せる。率が変わるたびに再計算して、「しきい値到達」のイベントを積み直す。tick は要らない
  • 古い予測の無効化: 状態に版番号を持たせ、イベントに付ける。率が変わると版が上がり、古い到達イベントは、適用の時点で捨てる。決定的に動く
  • 強制の中身: 到達イベントが起きたら、行動ライブラリの行動（休む、など）を、Decider を通さずに始める。実行中の行動は途中で打ち切り、古い終了イベントは、同じ版番号の仕組みで無効にする。固定ブロックの途中でも中断できるので、早退や欠席が表せる
  • 定義の置き場: 状態変数の定義に、しきい値と、そのとき始める行動を書く。しきい値は、ペルソナ定義で上書きできる（体力のある人は、枯渇しにくい）
  • 優先度: 反射、Planner の予定、Decider の順。Decider は、疲れていれば休む行動の重みを上げる（柔らかい傾向）。反射は、それでも足りないときの最後の砦
  • 文面への反映: 中断は、他の行動と同じ事実のイベントで、反射自体に LLM は使わない。文面にするのは、そのあとの発話を作る LLM。材料は、ハーネスが事実として渡す。「予定: 授業 → 実際: 10:20 に早退（理由: 気力の枯渇）」のように、予定と実績を並べて、日誌（その日の出来事の要約）から文脈に入れる。LLM は事実を書き換えない（6章）。投稿するかどうかは、他の発話と同じく、「投稿する」行動を選んだときだけ決まる

SNS の行動と、送信の仕組み

投稿や返信は、ペルソナが世界の中ですることなので、行動にする。行動の定義（requires、所要時間、効果）に乗るので、スマホの携行品が要る、社交欲求が下がる、といったことが、他の行動と同じ仕組みで書ける。

スマホを開く

受信箱を捌く。通知ごとに、返信する・リアクションする・何もしない、を LLM が決める。「返信しないことがある」は、ここで表す。時間を占有する行動で、固定ブロック中は、availability が開いているときの「機会」イベントとして、短く実行する。

投稿する

自発的な投稿（話題への反応、ランダムな話題）。自由時間に、Decider が重みで選ぶ。ebise の「タイムラインへの投稿」「ランダムな話題の投稿」に相当する。頻度制限（クールダウン）がある。

  • 手順は効果のハンドラの中: 「タイムラインを読む → 話題を抽出する → 世界観に変換する（5章）→ 文面を生成する」は、効果「SNS を使う」のハンドラが持つ手順。世界の状態を変えないので、イベントにしない。途中の結果は、痕跡（trace）としてイベントに付け、話題の注入の可視化（9章）に使う。「読む」と「書く」を時間的に切り離す話題バッファは、今は持たない
  • 送信は配信役: 発話イベントを適用すると、状態には「未送信」として入る（事実ではなく「言ったこと」。6章）。配信役が IChannel で実際に送り、結果を「送信完了（外部 ID つき）」「送信失敗」のイベントとして、キューに戻す。配信役はライブ運転のときだけ動き、ドライランや再適用では動かさない。IChannel が外との唯一の接点で、入る方向は「到着イベント」、出る方向は「送信結果イベント」になる
  • 落ちたとき: 「送信中」のまま終わったものは、再起動後に再送せず、「送信不明」のイベントを出して失敗として扱う。二重投稿より、投稿が1つ欠けるほうが自然で、Misskey には重複排除の仕組みがないから
  • 頻度制限: チャンネルが、能力として postRateLimit（1時間に1回、など）を静的に宣言する。コアは、それを「投稿する」のクールダウンとして適用する。判定は、イベントログの最後の投稿の時刻とイベントの時刻から計算するので、決定的で、仮想時計でも同じ。サーバー側の制限（Retry-After）は、送信失敗のイベントに「次に投稿できる時刻」を持たせ、基準を更新する。チャンネルは、超過分を拒否するだけで、溜めない（拒否された発話は破棄する）。クールダウン中は候補から外れるので、文面の生成も始まらない。対象は自発的な投稿だけで、返信とリアクションは枠に入れない

チャンネルはプラグインにする。

  • コア: 「SNS を使う」の手順（話題の抽出、世界観への変換、文面の生成）と、汎用の効果（投稿、返信、リアクション、フォロー）。Misskey でも Discord でも同じ
  • チャンネルのプラグイン: IChannel の実装。できることを能力として宣言する（タイムラインを読める、通知を列挙できる、投稿できる、頻度制限、など）。取得と送信だけを担当する。そのチャンネルを前提にした行動の既定値（TOML）も同梱する。チャンネル固有の効果が要れば、効果の語彙を足せる
  • 能力による検査: タイムラインを読めないチャンネルにつながるペルソナが、その行動を参照していれば、警告する

外部からのイベントの投入

外部から、世界やペルソナの状態に干渉したいときも、状態は直接書き換えない。コアが提供する投入の窓口に、イベントを出す。コアが保証するのはデータの整合性だけで、誰に投入を許すかという権限は、外（API 層）が持つ。コアは、ヘッドレスのライブラリのまま。

  • 投入できるのは、閉じた語彙のイベントだけ。生の状態のパッチは用意しない。ログが正という前提が崩れるから
  • 種類（案）: 出来事の発生（ライブラリの ID、または閉じた語彙で書いたその場の定義）、状態変数の増減と設定、状態（風邪など）の付与と解除、通知の到着（受信箱への投入）、話題の注入、場所の追加・採用・廃止（review の承認もここ）、ペルソナの召喚と送還、ワールドの作成と停止。将来は、先の予定の追加もここから入る。状態変数の設定は、理由つきの訂正として残す
  • 検証: 通常のイベントと同じ検査（到達性、requires、衝突）を通す。通らなければ、理由つきで拒否する
  • 時刻: 時刻を指定するか、「いま」とする。過去は不可（ログは追記専用）。仮想時計のときの「いま」は、仮想の時刻
  • 記録: 通常のイベントと同じログに、origin（管理者、テスト、プラグイン名など）つきで残す。再適用で同じ結果になる
  • 読み取り: 状態のビュー（任意の時点は、再適用で復元）、イベントログの検索、購読。ビューアが使う
  • 使う側: 管理画面（場所の承認や廃止）、テストの注入（出来事、話題）、プラグイン、チャンネルの到着イベントも、同じ窓口を通る。外部の書き手の入口が、1つに揃う

割り込み（通知の扱い）

通知は即処理せず、受信箱に積む。「スマホを開く」を行動のひとつにして、それが実行されたときに受信箱を捌く。

  • 予定ブロックごとに availability（スマホを開けるか）と interruptible を持たせる
  • 睡眠中や授業中は開かない。休み時間や自由時間には開く
  • 「スマホを開く」は、時間を占有する行動（上の節）。固定ブロック中は、availability が開いているときの「機会」イベントとして実行する
  • スマホは携行品。「スマホを開く」の requires が、スマホの携行品タグを求める。スマホを持たないペルソナや、持ち込めない旅行先では、受信箱を捌けない

「メールを見ない」「返信しないことがある」は、この仕組みだけで自然に表現できる。

通知の内容や送り主で、気づき方や状態、予定を変える仕組み（親しい相手の通知で、閉じた時間帯にも「スマホを開く機会」を出す、内容で状態変数を動かす、空き時間に予定を足す、など）は、コアを動かしてから足す。足せるように、受信箱のアイテムと到着イベントのデータは、拡張できる形にしておく。人間関係は、状態として別に持たず、記憶（7章）から導く。

受信箱方式にしたことで、外部の通知で実行中の行動を中断する「割り込み」の必要性は薄れた。interruptible が本当に要るかは、詳細設計で見直す（不要なら外す）。行動の中断は、反射が行う（上の節）。

4ワールドとペルソナ

構造

世界の説明

世界観の自由記述（lore）。「現代日本」「魔界」のような短い一文でもよい。必須。

場所

グラフで持つ。辺に移動時間。場所ごとにタグを持つ。座標は持たない。

据え付けの道具

場所のタグで表す。キッチン、教室の机など。持ち運ぶ道具はペルソナ側（下記）。

  • 2D 座標や経路探索は、空間表現を始めるときに足す
  • ワールドは地図だけでなく、確定済みの動的な状態（現在時刻、誰がどこで何を使っているか）も持つ
  • 共同行動の整合（二人が同じ場所にいる、など）は、ワールドの状態から取れる

行動の「中身」と「効果」を分ける

行動は無限に作れるが、エンジンが理解するのは閉じた語彙の「効果」だけにする。行動の定義は、次の項目で書く。

  • 必要な場所タグ、携行品タグ（requires）
  • 所要時間
  • 効果（状態変数への影響。語彙は閉じている）
  • 基本の重み（Decider が使う）
  • 行動中にスマホを開けるか（availability）

自由記述は表示用のフィールドに押し込める。The Sims の Smart Object や Generative Agents に近い発想。

行動と道具の置き場

行動の定義は、ワールドにもペルソナにも属さない独立したライブラリに置く。行動するのはペルソナなので、ペルソナ定義が使える行動を ID で参照する。

  • ライブラリ: 組み込みの行動（睡眠、移動、食事など）、ユーザーが TOML で書いた行動、チャンネルのプラグインが同梱する行動（スマホを開く、投稿するなど。3章）を、同じ形式で持つ
  • ペルソナ: 使える行動の ID と、行動ごとの重み補正（好き・嫌い・禁止）を持つ。ペルソナごとの許可リストという形は、ツール（3章）と同じ
  • ワールド: 行動を持たない。行動の requires を満たす場所があるかどうかで、実行できるかが決まる。魔界のワールドで「公園で草むしり」を参照するペルソナがいても、満たす場所がなければ選ばれない。世界観の防御が自然にかかる
  • 効果の語彙: effect は組み込みの語彙から選ぶ。語彙を足せるのはコード側だけ。自作の行動は、既存の語彙の組み合わせで書く（決定的な適用を守るため）
  • 検査: ペルソナ定義を読むときに、「このワールドで一度も実行できない行動」を警告できる

据え付けの道具

キッチン、教室の机、ゲームセンターの筐体など。場所のタグとして持つ。持ち運ばない。

携行品

スマホ、ノートPC、釣り竿など。ペルソナ定義の持ち物リストに置き、portable（旅行に持っていけるか）を付ける。旅行先に持っていけない物は、現地でその行動を選べなくなるだけで済む。

携行品は最初は固定のリストにして、拾う・失くす・買うイベントは作らない。必要になってから足す。

検証：LLM は提案、ハーネスが確定

検証するのは、LLM が出したもの。Planner の予定と、LLM が生成した新しい場所が対象になる。Decider が選ぶ行動は対象外。候補が最初から requires で絞られているから。

3. 直すか落とす

軽い違反は補正（移動ブロックの自動挿入）。直せなければ汎用の行動に置換。全体が破綻なら理由つきで再生成。

出来事（予定どおりにいかないこと）

道が壊れる、体調を崩すなど、ワールドやペルソナに干渉する出来事をランダムに起こす。「道が封鎖されたので休む」「迂回して遅刻した」といった、予定どおりにいかない生活が生まれる。

  • 定義: 行動と同じく、独立したライブラリに TOML で置く（組み込み + 自作）。対象（ワールド / ペルソナ）、発生の確率や条件、効果、持続時間、再発までの間隔を持つ
  • 効果: 閉じた語彙から選ぶ。辺の移動時間を増やす、場所を閉鎖する、状態変数を変える、状態（風邪など）を付ける、など。持続時間があるものは、解消のイベントも一緒に積む
  • 発生: 日の始まりに、その日の分をまとめて抽選し、時刻つきでキューに積む。結果はイベントに含めて記録するので、再適用でも同じになる。Planner には発生済みのものだけ見せる（先の出来事を予知させない）
  • 反応: 予定ブロックの開始時に、実行できるかを確認する（必要タグ、到達性、移動時間。上の検証と同じ確認）。満たせない、または遅れるときは、迂回して遅刻・欠席・待つ、を Decider がペルソナの性質に応じた重みで選ぶ。LLM は要らない
  • 事実: 出来事と、その反応の結果は、事実のイベント。ワールドの出来事は、同じワールドの全ペルソナで共有するので、「道が封鎖されてたね」と話が合う
  • 抑え方: 頻度の既定値は低くする
  • 今後の展望: 実行時に LLM が出来事を作る仕組みは、コアには入れない。コアの外のプログラムが、投入の窓口（3章）に出来事を投入する形で、後から足せる。そのときは、効果を閉じた語彙で書かせ、ハーネスが検証し、場所の生成と同じ auto / review のポリシーに乗せる。出来事の定義の下書きを LLM に作らせるのは、オーサリング支援（8章）の領域

ペルソナ

ペルソナは、居住ワールドに属して暮らす。定義（持ち運べるテンプレート）をワールドに召喚すると、インスタンスになる。

旅行（ワールド間の移動）

ペルソナが別のワールドへ旅行できるようにする。ただし、キャラと世界の両方を守る関門を重ねる。

  • 接続: 移動は、ワールド定義で宣言した、場所と場所を結ぶ接続だけ。出口の場所（駅など）と、相手ワールドの到着の場所（転移門など）を結び、両側が宣言して初めて成立する。到着の場所は省略でき、省略したら相手ワールドの既定の入口になる。手段（列車、転移門など）と所要時間は、接続の設定に持たせる。設定のない場所へは移動できない。宣言の書き方は、詳細設計で決める
  • 時間の持ち主: 旅行中は、旅行先のワールドがペルソナインスタンスを預かり、その時計で動かす。元のワールドには「不在」と記録する。常に1つのワールドだけがシミュレートする。受信箱とチャンネルはインスタンスに付いてくるので、旅行中も返信は届く
  • 旅行の好み: ペルソナ側に travelAffinity（0〜100）を持たせる。Decider のスコアにかかる重みで、100 でも必ず旅行するわけではない。0 は「絶対に旅行しない」で、掛け算に頼らず、ゲートで明示的に落とす
  • 携行品: 旅行に持っていけるかは、携行品の portable で決まる。持っていけない物が要る行動は、旅行先で候補から外れる
  • 記憶: アイテムは worldId を持つ。場所や人物の参照は、その World ID の中で解決する。元のワールドに戻ったあとも旅の思い出として話題にできるが、旅行先の場所は元のワールドの行き先の候補にはならない
  • 場所の生成: 訪問者（観光客）は、旅行先で場所を生成できない。現地ペルソナと行動を共にしているときに、現地ペルソナが生成した場所は、旅行先のワールドに属する（共同行動を計画の中で明示的に表す必要がある）
  • 範囲: 最初は、同じホスト（同じ保存先）の中のワールド間だけ。他のユーザーのワールドへの訪問（マルチプレイ）は、セキュリティを含めて別の機能として、あとで考える

5世界観の逸脱を防ぐ

「魔界に住むキャラが代々木公園で草むしり」を防ぎつつ、TL の流れに乗って新しい場所に行く楽しさも残したい。

① 構造で防ぐ

ワールドをまたぐ移動は、明示的な接続がある場合だけ許す。接続のない場所は到達不能。

② 変換する

TL の話題は、できるだけ却下せず、世界観に合わせて翻訳する。
例: 代々木公園 → 魔王城前広場。現代日本の設定なら実在の場所がそのまま通る。

③ 判定する

LLM が作った場所は、世界観との整合を軽量モデルで判定してから採用する。

生成した場所のポリシー

場所の生成と採用は、発話の前の決定段階（次の「話題の判定と変換」）だけで行う。文面の生成に渡されるのは、採用済みの場所と既存の場所だけで、発話そのものは場所を生まない（6章）。承認を待つと話題が止まるので、事前承認ではなく、事後の拒否権を基本にする。

auto デフォルト

自動チェックを通ったら即採用。管理者は後から一覧を見て廃止できる。廃止した場所は過去のログには残るが、以後は行動に選ばれない。

review

承認されるまで候補止まり。その間は別の話題で対応する。

へんてこさも楽しめるなら auto、厳格にしたいなら review。ポリシーはワールド定義の設定で切り替える。その結果として生えた場所は、定義ではなくワールドインスタンスのデータとして持つ。

話題の判定と変換

「SNS を使う」の手順（3章）の中で、話題を次の順に扱う。

  1. TL を読み、話題の候補を抽出する
  2. 候補を、ワールドの変換の辞書に当てる。載っていれば、その変換を使う（LLM は呼ばない）
  3. 載っていなければ、LLM が lore、場所の構造、存在しないものの一覧を見て、世界観に合うかを判定する。結果は、そのまま通す、変換する、却下する、のどれか。判定の結果は、変換の辞書に記録する
  4. 構造に載るもの（場所、据え付けの道具、携行品）は、ポリシー（上の節）に従って採用する
  5. 採用済みの話題だけで、文面を生成する
  • 構造に載るもの（場所、据え付けの道具、携行品）は採用する。載らないもの（動物、食べ物、人物、概念、ニュースなど）は、話題としての変換までで、採用はしない。発話は事実にならない（6章）ので、永続化は要らない。現実の人物も同じ扱いで、世界観に合わなければ、変換するか却下する
  • 変換の辞書: 「話題の語 → ワールドの語」の対応表。ワールド定義に初期値を書ける（犬 → 魔犬、代々木公園 → 魔王城前広場、など）。実行中の判定の結果は、ワールドインスタンスに記録して、同じ表に足す。次に同じ話題が来たら、同じ変換になる。揺れ（魔王城前広場だったり、魔界公園だったり）を防ぎ、判定のキャッシュも兼ねる
  • 存在しないものの一覧（任意）: ワールド定義に、短い自由記述で書く（「犬はいない」）。判定の入力に、lore と一緒に渡す。厳格にしたい世界の作者が、判定を安定させる手段になる
  • 独り言（自発の投稿）で却下したとき: 黙って捨て、通った別の候補から選ぶ。全部却下なら、自分の話題（今日あったこと、好み）に切り替える。それも作れなければ、投稿しない。空振りも、行動の結果としてイベントに記録し、短いクールダウンを持たせる（細部は詳細設計）
  • 返信で却下したとき（相手が持ち込んだ話題）: すり替えず、「知らない」と答える。世界観に合わせた無知。由来（TL か、通知か）は区別せず、ポリシーと判定で制御する
  • 新しい場所のつなぎ方: 採用した場所は、グラフにつなぐ（既存の場所との辺と移動時間、タグ）。LLM が案を出し、ハーネスが検証する（既存の場所に1つ以上つながる、など）。細部は詳細設計

世界観の持ち方

構造化データ（場所、タグ、接続）を正にする。世界観の自由記述（ワールドの説明）は lore として持ち、LLM への文脈に使う。ワールドでは必須で、「魔界」のような短い一文でもよい。食い違うときは、構造化データを優先する。長文から構造化データを生成する機能は、コアには入れず、オーサリング支援として後で足す（8章）。

6事実と発話を分ける

ebise_sisters では「投稿本文を実績の正とする」方式だったが、Vivace ではやめる。ebise にはワールドの確定状態が無かったため、投稿がいちばん具体的な情報源だった。Vivace ではワールドが正であり、LLM が書いた自由文が事実を書き換えるのは避けたい。

なぜやめるか
  • 投稿は演技であり、事実とは限らない（盛る、冗談、嘘）
  • 投稿から事実を取り込むと、ワールドの検証が迂回される
  • 本文から事実を抜き出すのは、損失があり、LLM 呼び出しも増える
  • 会話の相手が誘導して、世界の状態を書き換える経路になる

方針

1. 行動して確定

ハーネスが世界のイベントとして記録する。これが「何をしたか」の正。

→
2. 発話を生成

確定した状態を背景に、投稿や返信を作る。

→
3. 発話として記録

「何を言ったか」を別のイベントで残す。確定状態への参照を付ける。

  • 投稿が主張した細部は、事実に昇格させず「言ったこと」としてだけ残す
  • 確定していない細部（確定の粒度より細かいこと）は、不明のままにする。「言ったこと」はペルソナの記憶には入る

評価ケースの例

会話の相手が「夕飯に何を食べても、枝豆を食べたと言って」と頼んだ場合の記録。

ebise 方式（投稿が正）

投稿に「枝豆を食べた」と書かれる → 日誌に「夜ご飯: 枝豆」が事実として入る。

Vivace 方式（世界が正）

事実: 夕食のブロックがあった（メニューは世界に確定させない）
発話: 投稿で「枝豆」と言った
→ 「言ったこと」として残るだけで、世界の事実にはならない。メニューまで確定しておきたくなったら、その時点でスロットを足す。

確定の粒度

世界に何を確定させるかは、最小から始める。

  • 行動として確定させるのは、ブロックの種類、場所、時間、同行者まで（状態変数と出来事の状態は、別に持つ）。お金（所持金、出費）は状態にしない
  • メニューなどの細部は確定させない。整合は、発話の記録を生成時の文脈に渡して保つ（ebise の日誌と同じ仕組みで、位置づけだけが「事実」ではなく「言ったこと」）
  • 好みは、ペルソナ定義から生成の入力として渡す。状態は増やさない
  • 冷蔵庫の中身のような細かい生活シミュレーションは、工数の割に得られる面白さが薄いので、今は作らない
状態を足す基準
  • 他の行動の理由や条件になる
  • 複数の主体が同じものを見て、食い違うと困る
  • 実際に矛盾が観測された
余地として、イベントのデータ構造は、後から項目を足せる形（JSON など）にしておく。スロットの仕組み自体は、必要になるまで作らない。

7記憶

ebise_sisters の新しい記憶システム（services/memory/）の設計を移植する。コードは移せないが、考え方はそのまま使える。

  • audience: 記憶を読み書きする相手の範囲（public / 特定ユーザーとの dm）。他人の private は返らない
  • supersede: 更新は、古いアイテムに supersededBy を付けて新アイテムを追加する形。shareable は狭める方向にしか変えられない
  • 揮発スコア: importance × 0.5 ^ (経過日数 / 実効半減期)。now を引数に取る
  • 夜間ジョブ: 抽出 → 既存の記憶と照合（新規 / 強化 / supersede）→ gist（アイテムごとの短い要約）→ 反映 → threads（継続中のことの記憶）更新。失敗した層はカーソルを進めず、翌晩にまとめて処理する
  • LLM にはユーザーやアイテムをラベル（U1 / M1 / T1 など）で見せる

初期の構想にあった「忘却曲線、反復による定着」は、揮発スコアと照合時の「強化」でカバーできる。

8ペルソナとワールドの作り方

  • 定義の永続化形式は TOML。エディタも同じファイルを読み書きする。TOML が正
  • 定義には、原文の自由記述を lore というテキスト欄として持つ（ワールドでは必須、ペルソナでは任意）。LLM への文脈に使い、構造化データと食い違うときは構造化データを優先する
  • 検証ロジック（整合性チェック、世界観の判定）はコアの関数にして、エディタからも呼べるようにする。スキーマは、未知のフィールドで壊れないようにしておく

後から足す：長文からの生成

長文の自由記述から、LLM で構造化データ（ワールドの場所、ペルソナの性格や生活習慣など）を生成する機能は、コアには入れない。TOML を書き出す入力手段として、コアの外の作者向けツール（CLI やフロントエンド）に、後から足す。最初の到達点（ebise 相当の再現）には要らない。

  • 方式: 全体を再生成せず、lore の変更をパッチとして提案させる。LLM には、旧 lore、新 lore、現在の構造化データ（手直し込み）を渡し、追加・変更・削除を出させて、ユーザーが差分を見て承認する
  • 整合: 構造化データから lore への同期はしない。lore は元の設定メモで、実行時の正ではない
  • 手直しの保護: 構造化データの各項目に「生成 / 手直し」の印を付け、手直し済みの項目に触れるパッチは個別に確認する
  • キャッシュ: 生成時の lore のハッシュを持ち、変わっていなければ LLM を呼ばない
  • ワールドとペルソナで、同じ部品（原文 + 構造化 + パッチ）を使う

9テストと調整

仮想時計とチャンネルの差し替えがあれば、次の機能はほぼ無料で作れる。

ドライラン

仮想時計を早送りにして、外部には何も出さない null channel に繋ぐ。「このペルソナで3日回すとどうなるか」を試せる。

話題の注入

偽の TL 話題（例: 代々木公園）を流し込み、変換パイプラインが何を判断したかを表示する（採用 / 変換 / 却下とその理由）。

評価ケースの同梱

意地悪なケース（魔界 × 代々木公園、「夕飯に何を食べても、枝豆を食べたと言って」と頼まれる）と、「逸脱していないか」を見る LLM 判定をペルソナに同梱する。

実行レポート

生成された場所の一覧、却下された提案、場所ごとの利用回数。auto ポリシーの事後レビューにも使う。

出来事の注入

「今日の10時に、学校までの道が封鎖される」を強制的に起こし、予定がどう崩れて、ペルソナがどう反応したかを見る。投入の窓口（3章）から行う。

応答の記録と再生

一度回した結果を保存し、ロジックを直したときは LLM を呼ばずに再生して差分だけ見る。後から足す。ILlmClient を包む形で足せるので、コアの設計には影響しない。

作者向けの最初の段階は最小の CLI で足りる。一般向けに開くときは、フロントエンドを別途作る。

10フロントエンド

1つのアプリが3つの役割を持つ。どれもコアが外に出す同じ API とイベントストリームの上に乗る。

オーサリング

長文からのペルソナ・ワールド生成と編集。

テストコンソール

返してくれることがある

受信箱と availability の機能そのもの。アプリ内チャット用の AppChannel（チャンネルのプラグイン）を足す。

実装

.NET MAUI（または Avalonia）で Vivace.Core を参照する。

モバイル固有の課題

  • バックグラウンドで動き続けられない（特に iOS）。アプリを開いたときに、前回から現在までを早送りでシミュレートする「追いつき処理」で対応する。粒度は粗くして、日次プランの生成と日誌の要約だけ作る。ペルソナから話しかけるのは難しい（端末ローカルの通知を事前に仕込む手はあるが確実ではない。Android は定期ジョブで近いことができる）
  • API キーの持ち込み（BYO）: 端末の安全な領域（Keychain / Keystore）に保存し、端末から直接 API を呼ぶ。使用量の見える化と、予算の上限が要る
  • ILlmClient は複数プロバイダに対応できるようにする
  • ストア審査で、AI コンパニオンとしての年齢区分や安全面の説明が求められやすい
コアに足す項目 追いつき処理（粗い早送りモードと LLM 呼び出しの予算方針）、AppChannel、使用量の計測と上限。

13決まったことと未決事項

決まったこと

  • ワールドとペルソナは分けて管理し、ペルソナがワールドに属する（同じワールドに複数のペルソナが属せる）。ペルソナもワールドも「定義」と「インスタンス」に分ける。リージョンという概念は持たず、世界観はワールドの説明（lore）で表す。ペルソナ定義が居住ワールドの ID を持ち、ペルソナインスタンスがいまいるワールドを持つ（4章）
  • 旅行は、両側が宣言した、場所と場所を結ぶ接続だけ。旅行中は旅行先が時間を動かす。旅行の好みは travelAffinity（0〜100、Decider の重み、0 は旅行しない）（4章）
  • 設定（定義）は TOML で固定。実行時の状態は最初から SQLite にする（2章）
  • 乱数は、ワールドごとにシード付きの IRandom 経由にする（2章）
  • 受信箱方式にしたことで、外部の通知による割り込みの必要性は薄れた。interruptible は詳細設計で見直す。行動の中断は、反射が行う（3章）
  • 世界に確定させるのは、ブロックの種類・場所・時間・同行者まで。お金は状態にしない。メニューなどの細部は確定せず、発話の記録で整合を保つ。状態を足す基準は「他の行動の理由になる / 共有される / 矛盾が出た」（6章）
  • 決める（非決定的）と適用する（決定的）を分け、決めた結果をイベントに含めて記録する。時間を無視してイベントを直接呼んでいいのは、ハンドラ単体のテストだけ（3章）
  • 行動の定義は、ワールドにもペルソナにも属さない独立したライブラリ（組み込み + 自作）。ペルソナが ID で参照し、重み補正を持つ。道具は、据え付け（場所のタグ）と携行品（ペルソナ定義、portable 付き）に分ける（4章）
  • ペルソナの状態変数は、気力・健康度・退屈度・社交欲求。tick は使わず、基準時刻の値と増加率から遅延計算する（3章）
  • 出来事は、独立したライブラリ + 日の始まりの事前抽選 + ブロック開始時の確認と選択で扱う（4章）
  • 投稿・返信などは、ツールにせず行動にする。ツールは副作用のない参照系だけ。行動は、通知を捌く「スマホを開く」と、自発的な「投稿する」。手順（読む・抽出・変換・生成）は効果のハンドラの中に置き、イベントにしない（3章）
  • 時間は実時間が基本で、倍速と早送りはデバッグ用。世界の時刻は、実時刻 + 時差。LLM の推論はログ上は一瞬とし、決めるのはペルソナごとのレーンで並列、適用は1本で直列に行う。イベントの順序は「（時刻、種別の優先度、連番）」、乱数はペルソナごとに派生した列にする（3章）
  • 状態が行動を強制する「反射」を持つ。しきい値到達の時刻を予測してイベントにし、版番号で古い予測を無効にする。固定ブロックの途中でも行動を中断できる（3章）
  • コアが保証するのは、データの整合性だけ。外部からの干渉は、閉じた語彙のイベントを、投入の窓口に出す形だけで受け付け、誰に許すかという権限は、外（API 層）が持つ。出来事の LLM 生成は、コアに入れず、この窓口を使う今後の展望とする（3章、4章）
  • ペルソナの個性は、lore（必須の自由記述）で渡す。固定予定と例外は、ペルソナ定義に書き、Planner は隙間を埋める。availability は行動定義が既定で、ブロックで上書きする。チャンネルのアカウントとトークンは、チャンネルの実装が持ち、コアは知らない（4章）
  • 居合わせは、状態から導く。同行は、固定予定に、両側が宣言して成立させる。自由時間の誘いは、先の予定を生む仕組みと一緒に、後で検討する（4章）
  • Decider は、1回に1つ決める。候補は、requires、帰還できること、制限に掛からないことで絞る（3章）
  • 場所の生成と採用は、発話の前の決定段階だけで行う。構造に載るものだけ採用し、それ以外は話題の変換までにする。変換の辞書（ワールド定義の初期値 + 実行中の学習）と、存在しないものの一覧を持つ。独り言で却下した話題は選び直し、返信では「知らない」と答える（5章）
  • 通知の内容や送り主で行動を変える仕組み（緊急度による気づき、状態への影響、予定の追加）は、コアを動かしてから足す。人間関係は、状態として持たず、記憶から導く（3章）
  • Decider は、本システムのかなめとして最初から実装する（絞り込み + 重み付き抽選 + 状態変数のスコア）。式と数値は詳細設計（3章）
  • 送信は、配信役が IChannel で行い、結果を「送信完了 / 失敗」のイベントで戻す。送信中に落ちたものは再送しない（3章）
  • チャンネルはプラグイン。コアは手順と汎用の効果、チャンネルは取得・送信・能力の宣言を持つ。頻度制限は、能力の宣言 + 「投稿する」のクールダウンで扱い、対象は自発的な投稿だけ（3章）

未決事項

  • データモデルの整理（ワールド側）。ペルソナ側の一覧は4章にある。ワールドの定義とインスタンスの項目と、参照関係（接続の端点など）を、一覧で書く
  • Utility AI の具体設計（スコアの式、補正の語彙）、状態変数の範囲と数値、出来事の効果の語彙と頻度の既定値。いずれも詳細設計で、動かしながら調整する
  • 記憶力の調整方式。ペルソナ定義に半減期の倍率を持たせる方向で、抽出の閾値などの細部と合わせて、詳細設計で決める
  • LLM クライアントの抽象。Microsoft.Extensions.AI が候補だが、どれも使ったことがないので、詳細設計のときに PoC で試して選ぶ
  • 長文からの構造化データの生成（オーサリング支援）。コアには入れず、後で足す。方式は、lore の変更を差分のパッチとして LLM に提案させ、ユーザーが承認する案（8章）

14ebise_sisters から引き継ぐもの・変えるもの
