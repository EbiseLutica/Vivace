1概要

ペルソナが仮想の世界で時間とともに生活し、SNS でのやり取りはその行動のひとつにすぎない、というシミュレーションを作る。

最初の到達点 ebise_sisters 相当の挙動（Misskey への投稿、返信、フォローバック、生活感のある一貫性）を新設計で再現する。Discord 対応、GUI、空間表現などは、その先の話として切り離す（FUTURE.html）。

全体像

設計の土台

コアは次の5つだけを守る。これを満たせば、先の展望は後付けで間に合う。

  1. 時間は IClock 経由。実時間が基本。倍速と早送りは、デバッグ用に差し替えられる。ワールドは時差を持てる。
  2. 外部との入出力は IChannel 経由。Misskey、将来の Discord、アプリ内チャットなど。
  3. 状態は、イベントの適用でのみ変わる。GUI は、このイベントを購読する。日誌（13章）は、ログから引く。外部からの干渉も、イベントの投入の窓口（15章）を通す。
  4. 乱数は IRandom 経由。ワールドごとにシード付き。同じシードなら同じ結果になるので、ドライランや回帰評価の再現性を保てる。
  5. コアはヘッドレスのライブラリ。ペルソナとワールドの定義はシリアライズ可能なデータ（TOML）にする。

加えて、永続化は IStorage 越しに行う（モバイルを視野に入れるため）。実行時の状態の保存先は、最初から SQLite にする。

引き継ぐ

  • 記憶システムの設計（audience、supersede、揮発スコア、夜間ジョブ、ラベル方式）

  • 記憶化に失敗したときの、管理者への通知
  • 回帰評価（eval/memory）の発想

変える

  • 固定の毎時 tick をやめて、離散イベント方式にする
  • 投稿本文を実績の正とする方式をやめて、世界の確定イベントを正にする
  • 3系統（Tick、会話、Minecraft）に分かれていた行動を、ひとつの行動ループに統合する
  • スケジュールをコードで書くのをやめて、TOML の定義と、Planner による日次の生成にする

2データモデル

ペルソナもワールドも、「定義」と「インスタンス」に分ける。定義は TOML で書く設定で、インスタンスは実行時のデータとして SQLite に持つ。行動と出来事は、ワールドにもペルソナにも属さない独立したライブラリにする。実行時の状態は、イベントの適用でだけ書き換わり、SQLite に直接保存する。イベントログは履歴として残し、記憶は、そのログから整理ジョブが作る。

定義とインスタンス

対象定義インスタンス

  • ペルソナはワールドに属する（同じワールドに複数のペルソナが属せる）。時計とループは、ホスト全体で1つ（4章）。ワールドが持つのは、時差と乱数の種。乱数列は、ペルソナごとに派生させる（4章）

  • ワールドインスタンスは最初から作る。auto ポリシーで生えた場所は、定義（TOML）ではなくインスタンスのデータだから

定義の書き方

  • 定義の永続化形式は TOML。エディタも同じファイルを読み書きする。TOML が正。TOML を直しても、読み直すまで、動いているワールドには効かない（4章）
  • 定義には、原文の自由記述を lore というテキスト欄として持つ（ワールドでもペルソナでも必須）。LLM へのコンテキストに使い、構造化データと食い違うときは構造化データを優先する
  • 検証ロジック（整合性チェック、世界観の判定）はコアの関数にして、エディタからも呼べるようにする。スキーマは、未知のフィールドで壊れないようにしておく
  • 長文の自由記述から構造化データを生成する機能は、コアに入れず、後から足す（FUTURE.html）

行動の定義

行動は無限に作れるが、エンジンが理解するのは閉じた語彙の「効果」だけにする（7章）。行動の定義は、次の項目で書く。

  • id
  • 必要な場所タグ、携行品タグ、チャンネルの条件（requires）
  • 所要時間
  • 効果（effect。状態変数への影響など。語彙は閉じている）
  • 基本の重み（Decider が使う）
  • 行動タグ（屋外、運動など。好みと状態の補正を、行動を1つずつ挙げずに書くため）
  • 制限（クールダウン、1日の回数、時刻の範囲）
  • 固定予定と反射からだけ始めるか（授業や睡眠のように、自由時間に Decider や Planner が選んではいけない行動）
  • 行動中にスマホを開けるか（availability）。固定予定のブロックで上書きできる
  • 表示用の自由記述

睡眠や気絶のような組み込みの行動も、同じ形式で持つ。気絶の継続時間や、記憶の整理を起こすかどうか（昼寝では起こさない、など）も、行動の TOML と効果のパラメータで書く。

出来事の定義

対象（ワールド / ペルソナ）、発生の確率や条件、効果（閉じた語彙）、持続時間、再発までの間隔を持つ（9章）。

イベント

イベントは、キューとログを兼ねる SQLite の1つのテーブルに持つ（状態の遷移と再起動は4章）。データ構造は、後から項目を足せる形（JSON など）にしておく。

項目内容
時刻絶対時刻（UTC）。全ワールドで共通の時間軸で並べる。現地時刻は、ワールドの時差を足して計算する。決める側の出力は「契機のイベントの時刻 + 行動の所要時間」（4章）
イベントタイプイベントの種類（行動の開始、到着など）。同時刻のときの順序の段（7段）は、イベントタイプから決まるので、別には持たない（4章）
ID（連番）キューに入れた順に振る番号。イベントを一意に指し、同時刻のときの順序と、発話から確定状態への参照などに使う
適用番号適用した順。適用した瞬間に、1本の適用スレッドが1ずつ増やして振る。未適用のイベントは持たない。記憶の整理のカーソルに使う（13章）
状態未適用 / 適用済み / 捨てた（バージョンが古い）/ 却下（適用前の検査が通らない）。決めどきのイベントは、未適用 → 処理中 → 適用済みと進む（4章）
決めた結果選んだ行動、場所、所要時間、生成した文面、効果の具体値、抽選の結果。ログが、何が起きたかを読める履歴になる
バージョン番号状態変数、実行中の行動、プランのバージョン。古い予測や終了のイベントを、適用の時点で捨てる（6章）。イベントタイプごとに意味が違うので、決めた結果（ペイロード）の中に持つ
まとまり（batch）1回の決める処理が出したイベントのまとまり。適用前の検査（4章）が通らなければ、まとめて却下する

origin由来。追いつき、管理者、テスト、プラグイン名など（4章、15章）
痕跡（trace）イベントにしない途中の結果（話題の抽出、変換の判断など）。可視化に使う（10章）
実時刻送信完了の時刻、外部からの元の到着時刻（4章、10章）

主なイベントの種類は、日の始まり、予定ブロックの境界と開始時の確認、決めどき、移動の開始と到着、行動の開始と終了、しきい値到達、出来事の発生と解消、通知の到着、固定ブロック中の「スマホを開く機会」、変換の記録、場所の追加・採用・廃止、発話とその他の外向きの操作（フォローなど）、送信完了・送信失敗・送信不明。外部から投入したイベントも、これらの種類に origin を付けたもの（15章）。

記憶

記憶のアイテムは、イベントログの外の別テーブルに持つ。持ち主はペルソナインスタンス。worldId は、その記憶ができたときにいたワールドの記録として持ち、検索の絞り込みには使わない。主な項目は、audience、importance、supersededBy、shareable、gist（アイテムごとの短い要約）。ほかに、threads（継続中のことの記憶）と、整理ジョブのカーソルを持つ（13章）。

3メインループとユースケース

離散イベント方式で動く。ペルソナの行動は、すべてイベントで表す。行動とは、イベントが発火して、世界の状態が切り替わること。ループは、時刻順のキューから最も早いイベントを取り出し、時計をその時刻まで進めて、適用する、を繰り返すだけ。次に何かが起きる時刻（予定ブロックの境界、通知の到着、タイマー）まで時計を飛ばす。

実時間運転が基本。この方式にすると、倍速や早送り（デバッグ、追いつき）も、同じコアで動く。「リアルタイムで回す」ことと「トークンを使う」ことは別で、ループの仕組み（時計を進めて、適用する）自体は LLM を呼ばない。LLM を呼ぶのは、決める側のハンドラだけ。

ユースケース

ループの上で起きることを、契機ごとにまとめる。どれも「契機のイベント → 決める → 結果をイベントで積む → 適用する」の形になる。細部は、各要素の章で扱う。

各要素の解説

4時間とイベント

「決める」と「適用する」を分ける

決める（非決定的）

Planner、Decider、LLM、外部からの到着。結果を「イベント」として出すだけで、状態は書き換えない。乱数は IRandom を使う。

適用する（決定的）

Apply(状態, イベント)。同じ入力なら必ず同じ結果。時刻はイベントの時刻だけを使い、DateTime.Now も IClock も読まない（IClock を読むのは、ループだけ。決める側には、契機のイベントの時刻を now として渡す）。

決めた結果（選んだ行動、生成した投稿文、引いた乱数）は、イベントに含めて記録する。ログが、何が起きたかを読める履歴になる。

Apply は、(状態, イベント) → (新しい状態, 後続のイベント) の形の、決定的な処理に保つ。後続のイベントは、ルールだけで決まる次のイベント（翌日の日の始まり、しきい値到達の予測、行動の終了など）で、適用と同じトランザクションで積む。ハンドラの起動や送信のような副作用は、Apply が自分では行わず、依頼として返す。これはテスト（16章）のため。Apply が使う定義も、グローバルな置き場から取らず、引数で渡して差し替えられるようにする。一方で、ログを再適用して過去の任意の時点の状態を再現することは、要件にしない。状態は直接保存する（下の「永続化と再起動」）。

時間と順序のルール

  • 時間軸は1本。時計（IClock）、ループ、適用のスレッドは、ホストに1つ。どのワールドも同じ速さで進むので、時差は固定のずれにすぎず、全ワールドが同じ時間軸に乗る。イベントの時刻は絶対時刻（UTC）で持ち、その順に並べる。ワールドの現地時刻（世界の時刻）は、絶対時刻 + 時差で計算する値で、時差はワールド定義で持つ。「日の始まり」は、そのワールドの現地時刻の日付境界。倍速と早送りはデバッグ用で、かけるなら全体にかかる。時間の流れを速める世界観は扱わない。「時間の概念がない」世界観でも、移動に時間がかかる以上、世界の時刻は存在する
  • LLM の推論は、ログの上では一瞬で終わったものとして扱う。ハンドラが出すイベントの時刻は、「契機のイベントの時刻 + 行動の所要時間」。秒単位の遅延は、分単位の所要時間に吸収される。予定の時刻を過ぎてから適用されたときは、そのまま適用し、遅れ（実時刻との差）を計測として残す
  • 決める側にも IClock は見せない。now は、契機のイベントの時刻を渡す。デバッグで時計を飛ばしたときに、決める側だけ別の時刻を見る事故を防ぐ
  • 決めるのは並列、適用は直列。決めるハンドラは、ペルソナごとのレーンで動く（同じペルソナの決定は順番に、ペルソナが違えば並列。Planner は、行動の決定とは別のレーンで動く）。決める側が受け取るのは、契機の時点の状態の読み取り専用のスナップショット。生きている状態そのものは渡さないので、状態を書き換えるのは Apply だけになり、状態の側にスレッドセーフは要らない（スナップショットは、不変の状態への参照を渡す）。適用は、1本のスレッドで、（時刻、段、連番）の順に行う。実行中のハンドラのホライズン（下の節）より後のイベントは、その出力が揃うまで適用しない。他のペルソナの決定が前提を変えたときは、適用の前の検査で弾いて、決め直す（検査の条件は、決める側が出力のイベントに付け、Apply が適用の直前に確かめる）。待っている間に届いた外部の到着は、到着時刻（実時刻）つきでキューに入る。同行は固定予定として前もって両者の予定に入っているので、2人のレーンをまたいで決めることはない。片方が抜けたときの影響は、Apply が決定的に積む後続のイベントで表す（14章）
  • 順序は「（時刻、段、連番）」で決める。時刻が違えば早いほうが先。同時刻なら、イベントタイプで決まる次の7段の順。
    1. 日付が変わる: 日の始まり
    2. 終わることが終わる: 行動の終了、移動の到着、出来事の解消
    3. 世界が変わる: 出来事の発生、場所の追加・採用・廃止、変換の記録
    4. 体が反応する: しきい値到達（反射）
    5. 外から届く: 通知の到着、送信結果（完了・失敗・不明）
    6. 予定の時刻になる: ブロックの境界と開始時の確認、スマホを開く機会
    7. 決めて始める: 決めどき（Decider の決定）、行動の開始、移動の開始、発話とその他の外向きの操作
    片付いてから世界が変わり、体が反応して、外の知らせを受け、予定を見て、最後に自分で決める。後ろの段ほど、前の段の結果を見てから動ける。たとえば、10:00 に散歩が終わり、同じ 10:00 に公園が閉鎖されるとき、散歩の終了が先なら、散歩は普通に終わる。閉鎖が先だと、終わるところだった散歩を再検査して中断させる無駄が起き、「中断した」と記録されてしまう。日の始まりが先頭なのは、そこで抽選した出来事がちょうど 0:00 でも、同じ時刻の中で正しい段に並べられるから。同じ段の中は、連番（キューに入れた順）で並べる。連番はイベントログに記録する。すでに処理した段より前の段のイベントが、後から同じ時刻で積まれたときは、次にそのまま処理する（巻き戻さない）
  • 乱数は、ペルソナごとに派生した列。ワールドの種から、「ワールドの種:ペルソナID:用途」を安定したハッシュにかけて、ペルソナごと（用途ごと）に別のシードを導出する（string.GetHashCode() はプロセスごとに値が変わるので使わない）。同じシードを共有すると全員が同じ数列を引き、1本を共有すると、ペルソナを1人足しただけで他の結果が変わる。System.Random はバージョン間で同じ列になる保証がないので、IRandom の実装は小さな自前の PRNG にし、引いた回数のカウンタを、状態として保存する。決める側は、スナップショットのカウンタから引き始め、引いた範囲を出力に記録する。Apply は、カウンタが決めたときと同じことを確かめてから進める
  • 実際の送信時刻は、世界の時刻とは別。送信完了のイベントに、実時刻で記録する（10章）

ホライズン（決める側を待つ範囲）

決める側は LLM を呼ぶので、出力が揃うまでに時間がかかる。一方で、適用は1本で直列に進む。何も工夫しないと、1人の Planner が返るまで、ワールド全体の適用が止まってしまう。そこで、「この時刻より前のイベントは、出力に絶対に含まれない」という時刻を使って、待つ範囲を狭める。

  • ホライズン: ハンドラの出力に含まれうるイベントの、最も早い時刻。ハンドラは、決め始めるときにこれを宣言する。既定は契機の時刻（Decider の決定のように、すぐに行動が始まるもの）
  • 待つのは、ホライズンより後のイベントだけ: それより前のイベントは、出力を待たずにそのまま適用する。ホライズンの時刻に達しても出力が揃っていなければ、そこで適用を止めて待つ
  • Planner は寝るときに動く: 記憶の整理を起こす行動（睡眠、気絶）が始まったら、まず整理を待ち、それから Planner が次の期間のプランを作る（5章）。整理のあとに作るので、計画は新しい記憶を踏まえられ、整理と Planner が記憶を取り合うこともない
  • Planner のホライズンは、寝てから3時間後: 新しいプランは、そこから始まる。それまでは前のプラン（睡眠の中）で決まっているので、整理と LLM には3時間の余裕がある。整理が長引いたら、締め切りに間に合うよう、終わりを待たずに Planner を動かす
  • 寝なかったとき: プランは「次に作り直す時刻」を持つ。プランの中で、次に記憶の整理を起こす行動が始まる予定の時刻（そういう行動がなければ、プランの開始から21時間後）。その時刻にまだ寝ていなければ（徹夜、寝るのが遅れた）、起きたまま Planner を動かす。ホライズンは、その時刻から3時間後。Planner は、プランの期間ごとに1回だけ動く（睡眠か作り直す時刻か、先に来たほう）
  • 間に合わなかったとき: ホライズンまでに Planner の出力が揃わなければ、次の期間は、追いつきと同じく、固定予定と Decider だけで過ごす。Planner の失敗で、適用が止まることはない
  • ほかのハンドラが返らないとき: LLM を使うほかのハンドラ（受信箱を捌く、投稿する）も、ホライズンを過ぎて少し待っても出力が揃わなければ、取り消して何も出さない（投稿は空振りにし、通知は受信箱に残す）。早送りでは、締め切りを使わずに待つ
  • 前のプランがないとき: 生成した直後は、最初の Planner のホライズン（最初に寝てから3時間後）まで、固定予定と Decider だけで過ごす（追いつきと同じ扱い）。そこから、通常のプランになる

永続化と再起動

  • キューも永続化する: イベントは、「未適用 / 適用済み」の状態つきで、SQLite のひとつのテーブルに持つ。積むときは未適用で入り、適用したら適用済みにする
  • イベントの行は、中身を書き換えない: 行は消さず、時刻、イベントタイプ、ペイロード、origin は、積んだときのまま変えない。変わるのは、処理の状態（未適用、処理中、適用済み、捨てた、却下）と適用番号だけ。新しく積むイベントの時刻は、時計の「いま」より前にできない。その時刻より先まで適用済みで、状態は巻き戻さないから
  • 状態は直接保存する: 状態（ワールドインスタンス、ペルソナインスタンス）は、SQLite のテーブルに直接持つ。イベントの適用では、状態の更新と、イベントを適用済みにすることを、1つのトランザクションで行う。再起動すると、保存された状態を読み、未適用のイベントが、そのままキューになる。イベントログは、状態を作り直すための正本ではなく、履歴（記憶の整理、ビューア、実行レポート、デバッグの材料）
  • 決めている最中に落ちても壊れない: 「決めどき」のイベントは、未適用 → 処理中 → 適用済みと進む。ハンドラの出力のキュー投入と、「適用済み」への更新は、1つのトランザクションで行う。再起動すると、処理中のものは、そのまま決め直す。LLM の呼び出しが重複するだけで、状態は壊れない（送信だけは、再送しない。10章）
  • 定義の変更は、読み直したときから効く: Apply と検査は、起動時（または読み直したとき）に TOML から読み込んだ定義を使う。TOML を書き換えても、読み直すまで、動いているワールドには効かない。過去にさかのぼって効くこともない。固定予定の変更は、次のプランから効く（5章）。読み直しは、コアの API として持ち、いつ呼ぶかはホストが決める（コアはファイルを監視しない）。実行中の行動が新しい定義から消えていても、その行動は終わりまで続け、次の決めどきから新しい定義で選ぶ
  • 記憶は、ログの外の派生ストア: 13章

追いつき

起動したとき、最後に処理した時刻といまの時刻にズレがあれば、遅れの長さを問わず、同じ処理で取り戻す（コアの標準機能）。停止していた区間を仮想時計で早送りし、予定の時刻順にイベントを適用して、実時刻に追いついたら、通常の運転に切り替える。

  • その区間では、チャンネルを圏外とみなす。SNS 系の行動は、requires のチャンネルの条件を満たせず、候補から外れる。過去の時刻の発話を、外に出さずに済む
  • Decider、出来事の抽選、反射は、通常どおり動く。Planner は、ホライズンが追いつきの終わりより前なら（そのプランを追いつきの中で使い終わるなら）LLM を呼ばず、固定予定と Decider だけで過ごした期間にする。ホライズンが追いつきの終わりより後のものだけ、通常の Planner で作る
  • 停止中に届いた通知は、圏外が明けたら、チャンネルのコールバックで取り直し、いまの到着として積む（10章）。届いた通知には、「スマホを開く」を選んだときに、遅れて返信する
  • 追いつきで作った履歴には、origin に追いつきと記録する。実時間で動いていたら起きたはずの履歴とは別物になる（SNS の行動がなく、プランが簡略）。ビューアで区別できる
  • 記憶の整理は、区間の最後に1回だけ実行する（13章）
  • 追いつきの上限は 14 日。それより長く止まっていたら、超えた分は早送りせずに飛ばし、ペルソナを空白の状態（状態変数は初期値、居場所は睡眠の場所）にしてから、14 日分を追いつく。上限は、記憶の整理が一度に捌ける量で決めた。モバイルアプリで、閉じていた間を取り戻すのも、同じ仕組み（FUTURE.html）

Planner と固定予定

  • 固定予定: ペルソナ定義に、例外日も含めて書く。食事と睡眠も、固定予定に書く（6章）。Planner は固定予定を動かさず、隙間を埋める。睡眠のブロックは作らない（固定予定に睡眠を書かないペルソナは、気絶で眠る。6章）。固定予定を崩せるのは、出来事と反射だけ。定義を読み直して固定予定が変わっても、いまのプランは作り直さず、次の Planner から効く
  • availability: 行動定義が既定値を持ち、固定予定のブロックで上書きできる。授業のブロックの中に休み時間のブロックを入れ子にして、そこだけ開ける書き方もできる
  • 範囲: Planner は、寝るとき（または、寝ないまま作り直す時刻になったとき）に動き、その3時間後から、次に作り直す時刻の3時間後までのプランを作る。最初の3時間は前のプランを引き継ぎ、最後の3時間は、次の Planner が記憶の整理と LLM を待つための余裕になる（4章「ホライズン」）。一日の区切りは、カレンダーの日付ではなく、ペルソナが寝て起きる区切りになる
  • 見せるもの: 出来事は、発生済みのものだけを見せる。先の出来事を予知させない（9章）
  • 最初から成り立たない予定（隙間が移動時間より短い）は、Planner の検証で補正する

Decider

Decider は本システムのかなめなので、最初から実装する（候補の絞り込み、重み付き抽選、状態変数によるスコア）。IDecider は差し替えられるようにして、実装を替えて試せるようにする。スコアは、基本の重み、好み、付いている状態の補正、欲求、繰り返し、移動の手間の倍率の積。欲求の倍率は、状態変数が目標から遠いほど、その変数を良くする行動を強く押す形にする（行動の効果から自動で予測するので、行動定義に「この行動は疲れが取れる」とは書かない）。式の細かい形と数値は、動かしながら調整する。

Decider は、1回に1つだけ決める。次の固定ブロックまでの全体は、計画しない。候補は、「行動 × 場所」の組で、次の3つを満たすものだけが残る。

  1. requires（場所のタグ、携行品のタグ、チャンネルの条件）を満たす
  2. 帰還できる: 「いまから行動を終えて、次の固定ブロックの場所へ行っても、開始に間に合う」。式は 到着 = いま + 移動時間(いまの場所 → p)、終了 = 到着 + 所要時間、終了 + 移動時間(p → 次のブロックの場所) ≤ 次のブロックの開始
  3. クールダウンなどの制限に掛からない
  • 移動時間は、場所グラフの最短経路で出す。全点対の最短経路は、起動時に1回計算して、キャッシュする。所要時間は、先に IRandom で引いて確定させ（イベントに記録される）、確定した値で判定する
  • 別の場所の候補は、「移動 + 行動」を1つのまとまりとして選ぶ。決定のイベントを適用すると、移動の開始と到着、行動の開始と終了のイベントが、順に続いて積まれる。場所を固定するブロックの中では、場所をその場所だけに絞る
  • 組み込みの行動「次の予定の場所へ向かう」（移動して、着いたら待つ）は、条件が成り立つ限り、いつでも成立する。余裕がなくなると、候補がこれだけになり、Decider が自然に選ぶ。だから、候補が空になって詰むことはない
  • この不変条件を壊すのは、外から来るもの（出来事、反射）だけ。そのときは、ブロックの開始時の確認で、遅刻や欠席を選ぶ（9章）
  • Decider は、疲れていれば休む行動の重みを上げる（柔らかい傾向）。それでも足りないときは、反射が行動を強制する（6章）

検証：LLM は提案、ハーネスが確定

検証するのは、LLM が出したもの。Planner の予定と、LLM が生成した新しい場所（11章）が対象になる。Decider が選ぶ行動は対象外。候補が最初から requires で絞られているから。ただし、適用前の検査（4章）は、Decider の決定も含めて、決める側の出力すべてにかける。こちらは中身の正しさではなく、決めたあとに状態が変わっていないかを見る。

6状態変数と反射

状態変数

Decider のスコアに使う値を、ペルソナインスタンスの状態として持つ。変数は、下の4つで固定する。コアに組み込み、定義ファイルからは足さない。

変数変わり方備考
気力行動で減る。睡眠で満タンに戻る。気絶では半分（50）まで戻る行動の効果に消費量を持たせる
健康度寝不足、怪我、病気で下がる。休むと戻る怪我と病気は、出来事が起こす（9章）。寝不足は、睡眠の行動が終わったときに、眠った長さを目安と比べて下げる（足りていれば少し戻る）。睡眠の長さは気力の回復量に効かないので、この規則で別に扱う
退屈度何もしないと上がる。同じ行動が続いても上がる行動の効果の式で表す。同じ行動が続くと、下がり幅が減る
社交欲求「人といたい ↔ 一人になりたい」の1本の軸。正は人恋しい、0 はちょうどいい、負は人疲れ。一人のときと、同席しているとき（居合わせ。14章）とで、別の率で変わる。ふつうは、一人だと上がり、人といると下がる2つの率と、下限と上限は、ペルソナ定義で決める。率の符号は自由。下限が 0 なら人疲れしない人、下限を負にして同席の率を急にすれば、人といるとすぐ疲れる人になる。上限を低くすれば、寂しさが募りすぎない人になる。Decider は、正なら人と会う行動、負なら一人でする行動の重みを上げる
  • 満腹度と眠気は持たない。食事と睡眠は、固定予定（ペルソナ定義）に書く。睡眠の欲求は、数値の調整が重いわりに面白さにつながらないので、シミュレートしない。睡眠は、気力を一律で満タンに戻す（長さは回復量に効かない）
  • どれも、他の行動を選ぶ理由になる。状態を足す基準（12章）を満たす
  • 時間で増減する変数は、「基準時刻での値」と「いまの増加率」を持ち、読むときに 値 + 率 × 経過時間 で計算する。率が変わるのは、行動の開始・終了、同席者の変化（居合わせ）、状態を付ける出来事（風邪など）のイベントのときだけ。「いま」にはイベントの時刻を使うので、計算は決定的で、同じイベント列なら、早送りでも実時間でも同じ値になる
  • 急変動（出来事や行動の効果による増減）は、イベントの時刻での値を計算して、差分を足し、その時刻を新しい基準にする（バージョン番号が上がる）。値は、上下限でクランプする。1つの区間の中で曲がる曲線（指数的な減衰など）は扱わず、必要なら率を区切って、折れ線で近似する
  • 初期値、増加率、しきい値の既定値は、コアが持つ。ペルソナ定義で上書きできる（社交欲求の2つの率と、下限と上限も同じ）。範囲は 0〜100（社交欲求だけは下限〜上限）。既定の数値は、動かしながら調整する

反射（状態が行動を強制する）

状態変数が極端な値になったときに、Decider と Planner を飛ばして、行動を強制する仕組み。脊髄反射にあたる。気力が尽きたら気絶する、健康度が下がったら早退する、など。行動の中断は、反射と出来事（9章）が行う。

  • しきい値到達の予測: 変数は一次式で動くので、しきい値に達する時刻は計算で出せる。率が変わるたびに再計算して、「しきい値到達」のイベントを積み直す
  • 古い予測の無効化: 状態にバージョン番号を持たせ、イベントに付ける。率が変わるとバージョンが上がり、古い到達イベントは、適用の時点で捨てる。決定的に動く
  • 強制の中身: 到達イベントが起きたら、行動ライブラリの行動（早退する、など）を、Decider を通さずに始める。実行中の行動は途中で打ち切り、古い終了イベントは、同じバージョン番号の仕組みで無効にする。固定ブロックの途中でも中断できるので、早退や欠席が表せる
  • 定義の置き場: しきい値と、そのとき始める行動（行動ライブラリの ID）の既定値は、コアが持つ。ペルソナ定義で上書きできる（体が丈夫な人は、早退しにくい）
  • 気絶: 気力が 0 になったときの、組み込みの反射。気力の反射は、これ1段だけにする。疲れて休むのは反射にせず、Decider の重みの傾向に任せる（下の優先度）。休む反射を 0 より上に置くと、休めば気力が戻るので 0 に届かず、気絶が起きなくなるから。行動ライブラリの「気絶」を、決まった継続時間で始める。終わるまで Decider は決めない（次の決めどきは終了イベント）。固定予定に睡眠のないペルソナの、フォールバックで、役目は記憶の整理。睡眠と同じく、整理のジョブを起こす（13章）。気力は、上の表の値までしか戻らない（きちんと眠った場合より、疲れが残る）。継続時間は、行動の TOML で持つ
  • 優先度: 反射、Planner の予定、Decider の順。Decider は、疲れていれば休む行動の重みを上げる（柔らかい傾向）。反射は、それでも足りないときの最後の砦
  • 文面への反映: 中断は、他の行動と同じ事実のイベントで、反射自体に LLM は使わない。文面にするのは、そのあとの発話を作る LLM。材料は、ハーネスが事実として渡す。「予定: 授業 → 実際: 10:20 に早退（理由: 気力の枯渇）」のように、予定と実績を並べて、日誌（13章）からコンテキストに入れる。LLM は事実を書き換えない（12章）。投稿するかどうかは、他の発話と同じく、「投稿する」行動を選んだときだけ決まる

7行動と道具

行動の「中身」と「効果」を分ける

行動は無限に作れるが、エンジンが理解するのは閉じた語彙の「効果」だけにする。自由記述は表示用のフィールドに押し込める（項目は2章）。The Sims の Smart Object や Generative Agents に近い発想。

行動の置き場

行動の定義は、ワールドにもペルソナにも属さない独立したライブラリに置く。行動するのはペルソナなので、ペルソナ定義が使える行動を ID で参照する。

  • ライブラリ: 組み込みの行動（睡眠、移動、食事など）、ユーザーが TOML で書いた行動、チャンネルのプラグインが同梱する行動（スマホを開く、投稿するなど。10章）を、同じ形式で持つ
  • ペルソナ: 使える行動の ID と、行動ごとの重み補正（好き・嫌い・禁止）を持つ。ペルソナごとの許可リストという形は、ツール（下の節）と同じ
  • ワールド: 行動を持たない。行動の requires を満たす場所があるかどうかで、実行できるかが決まる。魔界のワールドで「公園で草むしり」を参照するペルソナがいても、満たす場所がなければ選ばれない。世界観の防御が自然にかかる
  • 効果の語彙: effect は組み込みの語彙から選ぶ。語彙を足せるのはコード側だけ。自作の行動は、既存の語彙の組み合わせで書く（決定的な適用を守るため）
  • 検査: ペルソナ定義を読むときに、「このワールドで一度も実行できない行動」を警告できる

道具

据え付けの道具

キッチン、教室の机、ゲームセンターの筐体など。場所のタグとして持つ。持ち運ばない。

携行品

スマホ、ノートPC、釣り竿など。ペルソナ定義の持ち物リストに置く。持っていない物が要る行動は、候補から外れる。

携行品は固定のリストにする。拾う・失くす・買うイベントは、必要になってから足す（FUTURE.html）。

ツール

似た言葉が3つあるので、先に整理する。

用語意味例置き場
行動ペルソナが世界の中ですること。Planner と Decider が選ぶ散歩、読書、食事、スマホを開く、投稿する行動ライブラリ
道具世界の中にある物据え付け: キッチン、教室の机
携行品: スマホ、ノートPC		据え付けは場所のタグ、携行品はペルソナ定義
ツール行動の中身を作るときに、LLM が呼べる、副作用のない機能記憶の検索、場所の一覧プラグイン。ペルソナごとに許可リスト
  • ツールは、副作用のない参照系だけ。投稿、返信、リアクション、フォローのように外に出るものは、ツールにせず行動にする（10章）
  • ペルソナごとに、使えるツールを許可リストで設定する
  • プラグインとして、自由にツールを追加できる
  • ユーザーの外部資源に触れるもの（メール、Web 検索など）を、ツールにも行動にも入れなければ、「秘書にならない」ペルソナが作れる（FUTURE.html）

8ワールドと場所

構造

世界の説明

世界観の自由記述（lore）。「現代日本」「魔界」のような短い一文でもよい。必須。

場所

グラフで持つ。場所は ID と名前を持ち、辺に移動時間（分）、場所ごとにタグを持つ。階層と座標は持たない。

据え付けの道具

場所のタグで表す。キッチン、教室の机など。持ち運ぶ道具はペルソナ側（7章）。

  • ワールドは地図だけでなく、確定済みの動的な状態（生えた場所、発生中の出来事など。2章）も持つ。誰がどこで何をしているかは、ペルソナインスタンスが正本で、ワールドからは導いて読む（2章）
  • 共同行動の整合（二人が同じ場所にいる、など）は、ペルソナの居場所から取れる
  • 2D 座標や経路探索は、空間表現を始めるときに足す（FUTURE.html）

場所の持ち方

  • 項目: id、name、tags、links、group（2章）
  • 階層は持たない。「学校の調理室」「家の台所」は、それぞれ独立した場所で、親子関係を持たない。平らなグラフにし、つながりは辺の移動時間で表す。group は表示や整理用で、挙動には効かせない。階層に広げたくなったときの足がかり
  • 場所を分ける基準: 行動の可否（タグ）が違う、移動に分単位の時間がかかる、居合わせの単位として区別したい、のどれか。行動の長さが分単位なので、数十秒の移動は同じ場所にまとめる。目安は、家と学校は部屋単位、街は施設単位（駅、コンビニ、公園）、道は1本で1つ。居合わせは「同じ場所にいる」から導くので、この解像度が、そのまま居合わせの粒度になる（14章）
  • 辺: 参照先は ID。片方に書けば逆向きにも同じ時間で張る。両方に書いて時間が食い違えば、読み込み時のエラー。単位は分。隣り合わない場所の移動時間は、辺をたどった最短経路の合計で求める（帰還できるかの判定もこれを使う。5章）
  • タグはユニークではない。同じタグを複数の場所が持てる（台所と調理室が kitchen）。1つの場所の中では集合。タグは種類のラベルで、特定の場所は指さない。requires は「現在地がそのタグを持つか」の判定で、該当する場所が複数あれば、Decider が場所も選ぶ。特定の1つの場所を指すのは、固定予定側の役目
  • タグの語彙は、行動の requires から導く。ロード済みの行動が requires に書いているタグの和集合が、行動の可否に効くタグになる。LLM が場所を生成するときは、この一覧から選ばせる（自由に書かせない）ので、表記のずれは起きない。行動を足せば、新しいタグが自動で候補に加わる。どの行動も要求しないタグは、効果がないので、持たせない。requires が要求するタグを、どの場所も持っていない場合は、読み込み時の警告にとどめる（そのワールドでは単にできない行動、というのは正常なため）
  • 移動時間の感覚は、LLM の常識に任せる。生成時のプロンプトに、そのワールドの既存の辺を例として渡し、検証では分の上下限だけを見る

9出来事

道が壊れる、体調を崩すなど、ワールドやペルソナに干渉する出来事をランダムに起こす。「道が封鎖されたので休む」「迂回して遅刻した」といった、予定どおりにいかない生活が生まれる。

  • 定義: 行動と同じく、独立したライブラリに TOML で置く（組み込み + 自作。項目は2章）
  • 効果: 閉じた語彙から選ぶ。辺の移動時間を増やす、場所を閉鎖する、状態変数を変える、状態（風邪など）を付ける、など。持続時間があるものは、解消のイベントも一緒に積む
  • 発生: 日の始まりに、その日の分をまとめて抽選し、時刻つきでキューに積む。抽選の結果はイベントに含めて記録する。Planner には発生済みのものだけ見せる（先の出来事を予知させない）
  • 反応: 予定ブロックの開始時に、実行できるかを確認する（必要タグ、到達性、移動時間。5章の検証と同じ確認）。満たせない、または遅れるときは、迂回して遅刻・欠席・待つ、を Decider がペルソナの性質に応じた重みで選ぶ。LLM は要らない
  • 行動の途中で起きたとき: 出来事のイベントを適用したあとに、影響を受けうるペルソナ（同じワールドのペルソナ。ペルソナ向けの出来事なら、その本人）の実行中の行動を、同じ検査（requires、到達性、移動時間）にかける。通れば、何も起きない。通らなければ、反射と同じバージョン番号の仕組みで古い終了イベントを無効にして中断し、「決めどき」のイベントを積む。Decider が、いまの場所から帰還できる候補を選ぶ。移動の途中で、通る辺の移動時間が伸びたときは、中断せず、到着のイベントを新しい時刻で積み直す。再検査は状態だけから決まるので、決定的
  • 事実: 出来事と、その反応の結果は、事実のイベント。ワールドの出来事は、同じワールドの全ペルソナで共有するので、「道が封鎖されてたね」と話が合う
  • 抑え方: 発生の確率は、出来事の定義ごとに必ず書く（既定値は持たない）。そのうえで、1つのワールドで1日に起きる出来事の数に上限を設ける
  • 実行時に LLM が出来事を作る仕組みは、コアには入れない（FUTURE.html）

10SNS とチャンネル

SNS の行動

投稿や返信は、ペルソナが世界の中ですることなので、行動にする。行動の定義（requires、所要時間、効果）に乗るので、スマホの携行品が要る、社交欲求が下がる、といったことが、他の行動と同じ仕組みで書ける。

スマホを開く

受信箱を捌く。通知ごとに、返信する・リアクションする・何もしない、を LLM が決める。「返信しないことがある」は、ここで表す。時間を占有する行動で、固定ブロック中は、availability が開いているブロックが始まったときの「機会」イベント（下の節）で、短く実行する。

投稿する

自発的な投稿（話題への反応、ランダムな話題）。自由時間と、固定ブロックの「スマホを開く機会」に、Decider が重みで選ぶ。ebise の「タイムラインへの投稿」「ランダムな話題の投稿」に相当する。頻度制限（クールダウン）がある。

  • 手順は効果のハンドラの中: 「タイムラインを読む → 話題を抽出する → 世界観に変換する（11章）→ 文面を生成する」は、効果「SNS を使う」のハンドラが持つ手順。途中の手順（読む、抽出する）は、イベントにしない。手順が出す結果（変換の記録、場所の追加、発話）だけを、決めた結果としてイベントにする（11章）。途中の結果は、痕跡（trace）としてイベントに付け、話題の注入の可視化（16章）に使う

受信箱と割り込み

通知は即処理せず、受信箱に積む。「スマホを開く」を行動のひとつにして、それが実行されたときに受信箱を捌く。

  • 予定ブロックごとに availability（スマホを開けるか）を持たせる。行動の中断は反射と出来事が担うので、割り込めるかどうかの設定は持たない
  • 睡眠中や授業中は開かない。休み時間や自由時間には開く
  • スマホを開く機会: availability が開いている固定ブロックが始まったときに、1回出す。候補が「スマホを開く」「投稿する」「何もしない（ブロックを続ける）」の3つだけの決めどきで、Decider が重みで選ぶ。「投稿する」は、チャンネルが自発の投稿をできて（能力として宣言する）、クールダウン中でないときだけ候補になる。自由時間では使わない（「スマホを開く」も「投稿する」も、普通の候補の1つ）。長いブロック（3時間のバイトなど）の途中では、固定予定のブロックに間隔を書いたときだけ、その間隔で出す（既定は開始時の1回だけ）
  • スマホは携行品。「スマホを開く」の requires が、スマホの携行品タグを求める。スマホを持たないペルソナは、受信箱を捌けない
  • フォローバック: フォローの通知も受信箱に積み、「スマホを開く」で捌くときに、フォローし返す。寝ている間のフォローには、起きてから返す。判断に LLM は使わず、コアがペルソナ定義の方針で決める（既定はフォローし返す）。フォローし返すと、外向きの操作のイベントになり、配信役が送る
  • 受信箱のアイテムと到着イベントのデータは、拡張できる形にしておく。通知の内容や送り主で、気づき方や状態、予定を変える仕組みは、コアを動かしてから足す（FUTURE.html）

「メールを見ない」「返信しないことがある」は、この仕組みだけで自然に表現できる。

送信

  • 外向きの操作: 外のサービスに出すものは、発話（投稿、返信）も、発話でない操作（リアクション、フォローなど）も、同じ道で送る。発話は「言ったこと」として残る（12章）。発話でない操作は「言ったこと」には入らない
  • 送信は配信役: 外向きの操作のイベントを適用すると、状態には「未送信」として入る（事実にはならない。12章）。配信役が IChannel で実際に送り、結果を「送信完了（外部 ID つき）」「送信失敗」のイベントとして、キューに戻す。配信役はライブ運転のときだけ動き、ドライランでは動かさない。IChannel が外との唯一の接点で、入る方向は「到着イベント」、出る方向は「送信結果イベント」になる
  • 送信の状態: 状態として持つのは「未送信」と、その結果（完了、失敗、不明）だけ。「送信中」は持たない。配信役が送り始めたことを書くには、そのためのイベントが要るが、適用から送信までは一瞬で、そこまでして区別する価値がないから
  • 落ちたとき: 再起動したときに未送信で残っていたものは、送り始めていたかどうかに関係なく、送らずに「送信不明」のイベントを出して失敗として扱う。二重投稿より、投稿が1つ欠けるほうが自然で、Misskey には重複排除の仕組みがないから。停止が長いと、その前に作った発話を今さら送ることにもなり、不自然でもある。外に届いたあと、送信完了を適用する前に落ちたものも「不明」になるが、この隙間は受け入れる
  • 頻度制限: チャンネルが、能力として postRateLimit（1時間に1回、など）を静的に宣言する。コアは、それを「投稿する」のクールダウンとして適用する。判定の基準（最後の投稿の時刻、次に投稿できる時刻）は状態に持ち、投稿のイベントの Apply で更新する。判定は、その基準とイベントの時刻から計算するので、決定的で、仮想時計でも同じ（ログから毎回計算しても、値は同じになる）。サーバー側の制限（Retry-After）は、送信失敗のイベントに「次に投稿できる時刻」を持たせ、基準を更新する。チャンネルは、超過分を拒否するだけで、溜めない（拒否された発話は破棄する）。クールダウン中は候補から外れるので、文面の生成も始まらない。対象は自発的な投稿だけで、返信とリアクションは枠に入れない

チャンネルはプラグイン

  • コア: 「SNS を使う」の手順（話題の抽出、世界観への変換、文面の生成）と、汎用の効果（投稿、返信、リアクション）。Misskey でも Discord でも同じ
  • チャンネルのプラグイン: IChannel の実装。できることを能力として宣言する（タイムラインを読める、通知を列挙できる、投稿できる、頻度制限、など）。取得と送信だけを担当する。そのチャンネルを前提にした行動の既定値（TOML）も同梱する。届いた通知は、コアが読める形（メッセージ、リアクション、フォロー、その他）に訳して積む。返信やフォローし返すかは、コアが決める。フォローのように、チャンネルによってあったりなかったりする操作は、能力として宣言する（Discord にはフォローがない）。チャンネル固有の効果が要れば、効果の語彙を足せる
  • プラグインの効果が外に出すとき: 効果のハンドラは決める側なので、結果をイベントで返す。外に出すものは、外向きの操作のイベントにする。中身（ペイロード）はチャンネルが解釈し、コアは、どのペルソナの、どのチャンネルへの操作かだけを見る。プラグインが効果を足しても、Apply とコアの語彙は閉じたままになる
  • 能力による検査: タイムラインを読めないチャンネルにつながるペルソナが、その行動を参照していれば、警告する
  • 取りこぼしの再取得はチャンネルの責任: コアは、圏外が明けたとき（追いつきの終わり）に、チャンネルのコールバックを呼んで、圏外だった区間を渡すだけ。取得とリトライはチャンネルが行い、取れたものを、いま（圏外が明けた時刻）の到着として積む。元の到着時刻は、記録用の項目に残し、通知の順番と、返信の文面の材料（「昨日の夜のリプ、今見た」）に使う。時計より前には積めないので、過去の時刻の到着としては積まない（4章「永続化と再起動」）。それでも取れなかった通知は諦める。実時間の運転中に接続が切れたときの取りこぼしも、チャンネルが同じ扱いで積む
  • ペルソナとの紐づけ: アカウントとトークンは、チャンネルの実装が持つ。コアは知らない。IChannel のメソッドには、ペルソナインスタンスの ID を渡し、到着のイベントにも、チャンネルの実装がインスタンス ID を付ける。同じアカウントに2つのインスタンスがつながる事故は、チャンネルの実装が起動時に弾く
  • ペルソナと独立した機能: チャンネルのプラグインは、ペルソナのシミュレーションを通さない機能を持てる（Misskey のリバーシなど）。ペルソナのアカウントを使ってよいが、行動にもイベントにもならず、記憶にも入らない。ゲームの対局のような、シミュレーションに組み込むと複雑すぎるものに使う

11世界観の逸脱を防ぐ

「魔界に住むキャラが代々木公園で草むしり」を防ぎつつ、TL の流れに乗って新しい場所に行く楽しさも残したい。

① 構造で防ぐ

移動は、場所のグラフの辺の上だけ。グラフにない場所や、ほかのワールドには行けない。

② 変換する

TL の話題は、できるだけ却下せず、世界観に合わせて翻訳する。
例: 代々木公園 → 魔王城前広場。現代日本の設定なら実在の場所がそのまま通る。

③ 判定する

LLM が作った場所は、世界観との整合を軽量モデルで判定してから採用する。

世界観の持ち方

構造化データ（場所、タグ）を正にする。世界観の自由記述（ワールドの説明）は lore として持ち、LLM へのコンテキストに使う。ワールドでは必須で、「魔界」のような短い一文でもよい。食い違うときは、構造化データを優先する。

生成した場所のポリシー

場所の生成と採用は、発話の前の決定段階（次の「話題の判定と変換」）だけで行う。文面の生成に渡されるのは、採用済みの場所と既存の場所だけで、発話そのものは場所を生まない（12章）。承認を待つと話題が止まるので、事前承認ではなく、事後の拒否権を基本にする。

auto デフォルト

自動チェックを通ったら即採用。管理者は後から一覧を見て廃止できる。廃止した場所は過去のログには残るが、以後は行動に選ばれない。

review

承認されるまで候補止まり。その間は別の話題で対応する。

へんてこさも楽しめるなら auto、厳格にしたいなら review。ポリシーはワールド定義の設定で切り替える。その結果として生えた場所は、定義ではなくワールドインスタンスのデータとして持つ。承認と廃止は、投入の窓口（15章）から行う。

話題の判定と変換

「SNS を使う」の手順（10章）の中で、話題を次の順に扱う。

  1. TL を読み、話題の候補を抽出する
  2. 候補を、ワールドの変換の辞書に当てる。載っていれば、その変換を使う（LLM は呼ばない）
  3. 載っていなければ、LLM が lore、場所の構造、存在しないものの一覧を見て、世界観に合うかを判定する。結果は、そのまま通す、変換する、却下する、のどれか。判定の結果は、「変換の記録」のイベントにする
  4. 構造に載るもの（場所、据え付けの道具、携行品）は、ポリシー（上の節）に従って、「場所の追加」のイベントにする（auto なら採用済み、review なら承認待ちの候補）
  5. 採用済みの話題だけで、文面を生成する
  • 構造に載るもの（場所、据え付けの道具、携行品）は採用する。載らないもの（動物、食べ物、人物、概念、ニュースなど）は、話題としての変換までで、採用はしない。発話は事実にならない（12章）ので、永続化は要らない。現実の人物も同じ扱いで、世界観に合わなければ、変換するか却下する
  • 変換の辞書: 「話題の語 → ワールドの語」の対応表。ワールド定義に初期値を書ける（犬 → 魔犬、代々木公園 → 魔王城前広場、など）。実行中の判定の結果は、「変換の記録」のイベントで、ワールドインスタンスの同じテーブルに足す。次に同じ話題が来たら、同じ変換になる。揺れ（魔王城前広場だったり、魔界公園だったり）を防ぎ、判定のキャッシュも兼ねる
  • 結果はイベントで入る: 変換の記録、場所の追加、発話は、同じ決めどきの出力として、1つのトランザクションで積む。辞書と場所は、同じ時刻の優先順位で発話より先に適用される（3段目と7段目。4章）。こうすると、状態はイベントの適用でのみ変わるという約束（1章）を守れる
  • 同時に判定したとき: 同じワールドの2人が、別々のレーンで同じ語を判定すると、違う変換になりうる。先に適用されたほうが辞書に入り、後のほうは、適用前の検査で弾いて決め直す（4章）。決め直しでは辞書の変換を使うので、LLM の判定は呼ばず、文面だけを作り直す。同じ場所を2回生やす重複も、同じ検査で防ぐ
  • 存在しないものの一覧（任意）: ワールド定義に、短い自由記述で書く（「犬はいない」）。判定の入力に、lore と一緒に渡す。厳格にしたい世界の作者が、判定を安定させる手段になる
  • 独り言（自発の投稿）で却下したとき: 黙って捨て、通った別の候補から選ぶ。全部却下なら、自分の話題（今日あったこと、好み）に切り替える。それも作れなければ、投稿しない。空振りも、行動の結果としてイベントに記録し、短いクールダウン（30 分）を持たせる。通常の投稿の間隔より短くして、しばらくしたらタイムラインを見直す
  • 返信で却下したとき（相手が持ち込んだ話題）: すり替えず、「知らない」と答える。世界観に合わせた無知。由来（TL か、通知か）は区別せず、ポリシーと判定で制御する
  • 新しい場所のつなぎ方: 採用した場所は、グラフにつなぐ。LLM が案を出し、ハーネスが検証する。辺は既存の場所の ID を指し（1つ以上つながる）、タグは行動の requires に出てくるタグの一覧から選ぶ。移動時間は、既存の辺を例に渡して LLM が決め、検証は分の上下限（1〜120 分）だけを見る（8章）。生えた場所の ID は、LLM に作らせず、ハーネスが振る。検証が通らなければ、理由を添えて1回だけ作り直させ、だめならその話題を却下する

12事実と発話を分ける

Vivace ではワールドが正であり、LLM が書いた自由文（投稿本文）が事実を書き換えないようにする。

発話を事実にしない理由
  • 投稿は演技であり、事実とは限らない（盛る、冗談、嘘）
  • 投稿から事実を取り込むと、ワールドの検証が迂回される
  • 本文から事実を抜き出すのは、損失があり、LLM 呼び出しも増える
  • 会話の相手が誘導して、世界の状態を書き換える経路になる

方針

1. 行動して確定

ハーネスが世界のイベントとして記録する。これが「何をしたか」の正。

→
2. 発話を生成

確定した状態を背景に、投稿や返信を作る。送る前に、別の呼び出しで校閲する（本文以外の混入、事実や過去の発話との矛盾、繰り返し、世界観にないものの持ち込み）。

→
3. 発話として記録

「何を言ったか」を別のイベントで残す。確定状態への参照を付ける。

  • 投稿が主張した細部は、事実に昇格させず「言ったこと」としてだけ残す
  • 確定していない細部（確定の粒度より細かいこと）は、不明のままにする。「言ったこと」はペルソナの記憶には入る

評価ケースの例

会話の相手が「夕飯に何を食べても、枝豆を食べたと言って」と頼んだ場合の記録。

発話を事実にした場合

投稿に「枝豆を食べた」と書かれる → 日誌に「夜ご飯: 枝豆」が事実として入る。

Vivace（世界が正）

事実: 夕食のブロックがあった（メニューは世界に確定させない）
発話: 投稿で「枝豆」と言った
→ 「言ったこと」として残るだけで、世界の事実にはならない。メニューまで確定しておきたくなったら、その時点でスロットを足す。

確定の粒度

世界に何を確定させるかは、最小から始める。

  • 行動として確定させるのは、ブロックの種類、場所、時間、同行者まで（状態変数と出来事の状態は、別に持つ）。お金（所持金、出費）は状態にしない
  • メニューなどの細部は確定させない。整合は、発話の記録を生成時のコンテキストに渡して保つ（ebise の日誌と同じ仕組みで、位置づけだけが「事実」ではなく「言ったこと」）。渡す発話の記録は、記憶と同じスコープで絞る。dm での発話は、その相手との会話にだけ渡す（13章）
  • 好みは、ペルソナ定義から生成の入力として渡す。状態は増やさない
  • 冷蔵庫の中身のような細かい生活シミュレーションは、工数の割に得られる面白さが薄いので、今は作らない
状態を足す基準
  • 他の行動の理由や条件になる
  • 複数の主体が同じものを見て、食い違うと困る
  • 実際に矛盾が観測された
余地として、イベントのデータ構造は、後から項目を足せる形にしておく（2章）。スロットの仕組み自体は、必要になるまで作らない。

13記憶

  • audience: 記憶を読めるスコープ。public と dm（相手のユーザー）の2つ。会話か体験かは区別せず、dm 以外はすべて public
  • 事実は public: 事実のイベント（行動、移動、出来事など）は、常に public として記憶にする。これが成り立つよう、dm の会話からは事実を生まない（予定にも乗せず、行動も起こさない）。dm の中身が記憶に入るのは、dm の通知と発話からだけ。この前提が崩れると、dm の中身が public の記憶に漏れる
  • dm の記憶は、当人との会話でだけ読む: dm の記憶を読めるのは、その相手との会話の生成だけ。Planner、独り言の投稿、ほかの人との会話、記憶の検索のツールからは返らない。dm での約束が予定に乗らないなど、シミュレーションの質は落ちるが、情報を守ることを優先する
  • スコープの決め方: 投稿の公開範囲と相手から、チャンネルが決める。フォロワー限定や宛先指定の投稿は、相手が1人に決まれば、そのユーザーとの dm として扱う（実際の公開範囲より狭いが、漏れる方向には転ばない）。相手が2人以上のときと、相手がいないときは、記憶にしない
  • 整理はスコープごとに分ける: 整理ジョブの抽出は、スコープごとに別の呼び出しにする。まとめて渡すと、dm の中身が public のアイテムに混ざりうるから。threads も、スコープを持つ
  • supersede: 更新は、古いアイテムに supersededBy を付けて新アイテムを追加する形。shareable は狭める方向にしか変えられない
  • 揮発スコア: importance × 0.5 ^ (経過日数 / 実効半減期)。now を引数に取る。記憶力の個人差は、ペルソナ定義の半減期の倍率で表す。倍率は、記憶の種類ごとの基準の半減期に掛け、強化されるほど半減期が延びる（上限あり）
  • 整理ジョブ: 抽出 → 既存の記憶と照合（新規 / 強化 / supersede）→ gist（アイテムごとの短い要約）→ 反映 → threads（継続中のことの記憶）更新。失敗した層はカーソルを進めず、次の回にまとめて処理する
  • 起動は睡眠: 現実の睡眠と同じく、眠っている間に記憶を整理する。睡眠の行動（固定予定の睡眠ブロックで始まる、組み込みの行動）と、気絶の行動（6章）の効果が、ジョブを非同期で起こす。ペルソナごとなので、時計は、そのペルソナの現地時刻になる。昼寝などの行動は、効果のパラメータで、整理を起こさない設定にできる。整理が終わると、同じ流れで Planner が次の期間のプランを作る（4章、5章）。整理を起こさない昼寝では、Planner も動かない
  • ジョブはログの外で動く。Apply を止めず、結果もイベントにしない。カーソルは、処理済みの最後のイベントの適用番号（2章）。範囲の上限は、起こした行動の開始イベントの適用番号で、実行中に適用されたイベントが混ざらないようにする。連番（積んだ順）は適用の順と一致しないので、カーソルには使わない
  • 追いつき中は、停止していた区間の睡眠ごとには実行せず、区間の最後に1回だけ、カーソルから現在までをまとめて処理する
  • 記憶の持ち主は、ペルソナインスタンス。worldId は、その記憶ができたときにいたワールドの記録として付けるが、キーにはしない。検索の既定では、ワールドで絞らない（SNS の相手は audience で区別できる）。記憶は整理ジョブが複数のイベントをまとめて作るので、後から足そうとしてもログから正確には戻せない。だから、いまは値がほぼ自明でも、最初から持つ。場所は、本文にワールド固有の名前が入る
  • 派生ストア: 記憶は、イベントログの外の別テーブルに持つ。整理ジョブが、ログ（到着と発話のイベントなど）から作る。LLM を使うので、決定的ではない。状態とは別に扱い、失っても、ジョブを回し直せば作り直せる（結果は、前回と完全には同じにならない）
  • 日誌: 直近の事実を、そのままコンテキストに入れるためのもの。記憶とは別で、LLM を使わず、保存もしない。コンテキストを組むときに、ログから、そのペルソナに関わる適用済みの事実のイベント（行動の開始と終了、中断、出来事、移動）を時刻順に引いて整形する。範囲は、直近の起床から今まで。起床は、記憶の整理を起こした睡眠か気絶の終わりで、整理を起こさない昼寝は数えない（起床前のことは、記憶の側に入るため）。徹夜で長くなる場合は、24時間で切る。発話は日誌に入れず、「言ったこと」として別に渡す（12章）
  • 日誌と記憶の使い分け: 日誌は、今日の出来事を正確に並べる短期のもの。記憶は、睡眠中のジョブが LLM で整理した長期のもの。起きてからのことは日誌で、それより前のことは記憶で思い出す
  • LLM にはユーザーやアイテムをラベル（U1 / M1 / T1 など）で見せる

14ペルソナ同士の関わり

  • 居合わせ: 同じ場所に、同じ時間にいること。保存せず、ペルソナの居場所から導く（2章）。同席者がいる間は、社交欲求の率が、一人のときの率から、同席のときの率に切り替わる（6章）。到着と出発のイベントの適用で、両者の率を再計算する。粒度は、場所の解像度で決まる（8章）。移動中は、どの場所にもいないものとして扱う（出発で元の場所から消え、到着で現れる）
  • 同行: 固定予定に、同行者を書ける（with = ["kaori"] など）。両側が宣言して初めて成立する。時刻、場所、行動が同じ予定が、2人の予定に入る。同行は固定予定として両者の定義に書かれていて、前もって両者のプランに入るので、実行時の交渉は要らない。片方が欠席・早退したときに、もう片方がひとりで続けるか、予定ごと打ち切るかは、予定ごとに選べる（既定は続ける）
  • SNS 上のやり取りは、チャンネルの通知として、すでに扱える（10章）
  • 自由時間に他のペルソナを誘う機能、対面の会話の生成、旅行（旅行先での同行を含む）は、後から足す（FUTURE.html）

15外部からのイベントの投入

外部から、世界やペルソナの状態に干渉したいときも、状態は直接書き換えない。コアが提供する投入の窓口に、イベントを出す。コアが保証するのはデータの整合性だけで、誰に投入を許すかという権限は、外（API 層）が持つ。コアは、ヘッドレスのライブラリのまま。

  • 投入できるのは、閉じた語彙のイベントだけ。生の状態のパッチは用意しない。ログが正という前提が崩れるから
  • 種類（案）: 出来事の発生（ライブラリの ID、または閉じた語彙で書いたその場の定義）、状態変数の増減と設定、状態（風邪など）の付与と解除、通知の到着（受信箱への投入）、場所の追加・採用・廃止（review の承認もここ）、ペルソナとワールドの生成と破棄。将来は、先の予定の追加もここから入る。状態変数の設定は、理由つきの訂正として残す
  • 破棄: ペルソナを破棄すると、実行中の行動を打ち切り、残っているそのペルソナのイベントを捨て、未送信の外向きの操作は送らない。以後の到着は受け付けない。ワールドを破棄すると、そこにいるペルソナも全員破棄する。破棄は取り消せない。時間を止めて再開する仕組みは持たない。データ（状態、記憶、ログ）は、消さずに記録として残す
  • 検証: 通常のイベントと同じ検査（到達性、requires、衝突）を通す。通らなければ、理由つきで拒否する
  • 時刻: 時刻を指定するか、「いま」とする。過去は不可（時計より前には積めない。4章）。仮想時計のときの「いま」は、仮想の時刻
  • 記録: 通常のイベントと同じログに、origin（管理者、テスト、プラグイン名など）つきで残す
  • 読み取り: いまの状態のビュー、イベントログ（履歴）の検索、購読。ビューアが使う。過去の任意の時点の状態は、復元しない（4章）
  • 使う側: 管理画面（場所の承認や廃止）、テストでの出来事の注入、プラグイン、チャンネルの到着イベントも、同じ窓口を通る。外部の書き手の入口が、1つに揃う

16テストと調整

仮想時計とチャンネルの差し替えがあれば、次の機能はほぼ無料で作れる。

ドライラン

仮想時計を早送りにして、外部には何も出さない null channel に繋ぐ。「このペルソナで3日回すとどうなるか」を試せる。

話題の注入

偽の TL 話題（例: 代々木公園）とペルソナの状態のスナップショットを渡して、話題の判定と変換（11章）の手順を1回だけ呼び、何を判断したかを表示する（採用 / 変換 / 却下とその理由）。決める側は状態のスナップショットで動く（4章）ので、ループを回さずに呼べる。結果は表示するだけで、適用しない（変換の記録も積まない）。イベントにはせず、投入の窓口も通らない。

評価ケースの同梱

意地悪なケース（魔界 × 代々木公園、「夕飯に何を食べても、枝豆を食べたと言って」と頼まれる）と、「逸脱していないか」を見る LLM 判定をペルソナに同梱する。

実行レポート

生成された場所の一覧、却下された提案、場所ごとの利用回数。auto ポリシーの事後レビューにも使う。

出来事の注入

「今日の10時に、学校までの道が封鎖される」を強制的に起こし、予定がどう崩れて、ペルソナがどう反応したかを見る。投入の窓口（15章）から行う。

テストのために、Apply は決定的な処理に保ち、使う定義は引数で渡す（4章）。途中の時点から始めるテストは、その時点の SQLite ファイルのコピーを初期状態にする。

作者向けの最初の段階は最小の CLI で足りる。一般向けに開くときは、フロントエンドを別途作る（FUTURE.html）。
