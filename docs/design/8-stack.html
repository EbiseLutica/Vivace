8.1確定

項目内容
言語とランタイムC# 14 / .NET 10（net10.0、Nullable 有効などの共通の設定は Directory.Build.props にまとめ、各プロジェクトが継承する）
実行時の状態の保存先SQLite（VISION 1章）

8.2ライブラリ

用途候補選ぶ理由（どの設計から来るか）
SQLite のドライバMicrosoft.Data.Sqlite（10.x）.NET の標準。既定の同梱 SQLite（e_sqlite3）に JSON 関数が入っていて、JSON の列を絞り込める（D3 3.8）
SQL の書き方手書きの SQL（ORM なし）テーブルは十数個、書き込みはエンジンの StorageBatch だけ（D4 4.2）。リフレクションに頼らないので、モバイル（NativeAOT）でも動く
TOMLTomlyn（2.x、TOML 1.1）構文木を持ち、未知のキーの警告に行と列を出せる（D7 7.2）。NativeAOT 対応をうたっている
JSONSystem.Text.Json + ソース生成BCL。ペイロードの record の読み書き（D3 3.9）。ソース生成で AOT でも動く
不変のコレクションSystem.Collections.ImmutableBCL。状態を不変にして、スナップショットを参照で渡す（D3 P-21）
コマンドのキューSystem.Threading.ChannelsBCL。エンジンを唯一の書き手にするアクター（D1 P-01）
ハッシュSystem.Security.Cryptography.SHA256BCL。乱数のシードの導出（D5 5.9）
ログMicrosoft.Extensions.Logging.Abstractionsコアは抽象だけに依存し、出力先はホストが選ぶ
計測System.Diagnostics.MetricsBCL（D7 7.3）
LLMコア独自の ILlmClient と、その実装。いまは Anthropic の公式 C# SDK を直接使う（8.4 の A）D4 P-26
テストxUnit v3（4.x、xunit.v3.mtp-v2）+ Verify（32.x、Verify.XunitV3）シナリオのテストは、イベントの列のスナップショットを比べる（D7 7.4）。xUnit は 4.0 で Microsoft Testing Platform v2 が既定になったので、.NET 10 SDK では global.json の設定が要る。Verify は 33.0.0 から、NuGet のパッケージのライセンスが MIT から OSMF EULA に変わり（ソースは MIT のまま）、SponsorCheck（SC021）が、ライセンスの申告か免除の宣言がないとビルドを止める。免除の宣言には期限（最長12か月）があるので、32.x に留めた。Verify.XunitV3 32.0.1 が xunit.v3.extensibility.core に求めるのは 3.2.2 以上で、4.0.2 はその範囲内。Verify が使う xunit の型9個とメンバー9個は、4.0.2 にすべてある（名前で確かめた）。xunit か Verify を上げるときは、Verify を使うテストを回す。組み合わせが壊れたときに自前の比較へ差し替えられるよう、テストは Verify を直接呼ばず、Vivace.Tests の1つのヘルパーを通す。Verify の呼び出しをそこ1か所に閉じ込め、Vivace.Testing は CLI の dry-run からも使うので、テストフレームワークを参照させない（J-136）
CLISystem.CommandLine（2.0 系）2.0 で安定版になった。CLI（D7 7.5）のコマンドの解析だけに使う
デーモンの管理用 APIASP.NET Core の Minimal API（共有フレームワーク）.NET に同梱なので、パッケージを足さない。ルーター、JSON、Server-Sent Events（.NET 10）、Unix ソケット（Kestrel）が使える。HttpListener は、Microsoft が新しい開発に勧めていないので使わない（D7 P-54）
Misskey のクライアント自前の薄いクライアント（HTTP + WebSocket）使う API は投稿、返信、リアクション、フォロー、通知の取得、タイムラインの取得、ストリーミングくらい。以前に作った Misskey.NET は 2023 年から更新がないので、移すなら必要な部分だけにする

パッケージのバージョンは、どのプロジェクトも Directory.Packages.props で一括して固定する。

決定 P-51　ライブラリの選定 上の表。BCL で足りるものは BCL を使い、外のパッケージは Microsoft.Data.Sqlite、Tomlyn、ログの抽象、テストの道具、CLI の解析にとどめる。コア（Vivace.Core）が参照する外のパッケージは、Tomlyn とログの抽象の2つだけになる（D4 4.1）。

8.3使わないもの

もの使わない理由
EF Coreイベントテーブルは追記と状態の更新だけで、変更追跡もマイグレーションの生成も要らない。トランザクションの境界（D1 1.9）を自分で決めたい
NodaTime などのタイムゾーンのライブラリワールドの時差は固定のずれで、夏時間を扱わない（VISION 4章）。DateTimeOffset と TimeSpan で足りる
System.Randomバージョン間で同じ列になる保証がない（VISION 4章）。自前の SplitMix64（D5 5.9）
ベクトル検索記憶の検索は、タグと主題の一致から始める（D6 P-43）
DI コンテナ（コアの中）コアはビルダーで組み立てる（D4 4.6）。ホストが DI を使うのは自由

8.4LLM の PoC

VISION 1章「LLM クライアントの実装は、詳細設計で PoC をして選ぶ」。候補は2つ。

A. Anthropic の公式 C# SDK を直接

NuGet の Anthropic（10 系以降が公式。ベータ）。プロンプトキャッシュなど、Claude の機能をそのまま使える。

B. Microsoft.Extensions.AI の IChatClient 越し

公式 SDK は AsIChatClient() で IChatClient を返す。構造化出力（ChatResponse<T>）やツールの往復を、M.E.AI の仕組みで回せる。ほかのプロバイダにも替えやすい（FUTURE.html のモバイルの BYO キー）。

どちらでも、コアから見えるのは ILlmClient だけ（D4 4.4）。PoC では、次を確かめる。

  1. 構造化出力：Planner と判定の出力スキーマで、形の崩れた出力がどのくらい出るか
  2. ツールの往復：記憶の検索のツールを、ペルソナと audience のコンテキストつきで呼べるか（D4 4.4）
  3. プロンプトキャッシュ：ペルソナの lore とワールドの lore を固定の前置きにして、キャッシュが効くか。1人1日 30〜100 回の呼び出し（D6 6.9）の費用に直結する
  4. 使用量：トークン数とモデル名を、呼び出しごとに取れるか（痕跡と実行レポート）
  5. 取り消し：CancellationToken で、締め切り（D1 1.6）に呼び出しを止められるか

B で 3 が効かない、または A に比べて手間が大きければ A にする。どちらも満たすなら、プロバイダを替えやすい B にする。

M2 の PoC の結果

M2 では A だけを作り、投稿の文面が作れることと、失敗と時間切れを扱えることを、本物の API で確かめた（2026-11-19、SDK 13.10.0）。B との比べと、上の 1〜3 は、構造化出力とツールを作るときに、困ったら確かめる。それまでは A を使う。

確かめたこと結果
投稿の文面vivace run --speed 600 で約1日半回し、2人で 15 件の投稿が作れた。失敗は 0 件。応答は Main（claude-sonnet-5-5）で 3〜7 秒ほど
使用量（4）モデル名と、入力と出力のトークン数が、呼び出しごとに取れる。短い指示で入力 67、出力 160〜260 トークンほど
応答の切れ応答の上限を 16 トークンにすると、停止理由 max_tokens で失敗になる
時間切れ1回の呼び出しの時間切れ（J-180）は、SDK から TaskCanceledException で上がる。呼び出し元の取り消しではないので、エンジンは代わりの出力（post.skipped）にする
取り消し（5）CancellationToken を取り消すと、その時点で呼び出しが止まる
キーとモデルの誤りキーが違うと 401、モデルがないと 404 の例外になる。vivace run は止まらず、投稿ごとに post.skipped を残し、標準エラーに1行書く

拒否（停止理由 refusal）は、本物の API では起こせなかった。偽の HTTP の応答でだけ確かめている。
