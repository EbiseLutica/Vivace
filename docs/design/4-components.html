4.1アセンブリ

  • Vivace.Core：ドメイン型、定義の読み込みと検証、Apply、エンジン、Decider、Planner の手順、効果のハンドラ（受信箱、投稿）、コンテキストの組み立て、記憶の整理、ポート。依存は TOML のライブラリとログの抽象だけ
  • Vivace.Storage.Sqlite：SQLite の実装を分けて、コアから SQL を追い出す。モバイルで別のストレージを使うときも、コアは変えない（VISION 1章）
  • Vivace.Llm.*：LLM の実装。どの SDK を使うかは、PoC で決める（D8）
  • Vivace.Testing：テストとドライランの部品。台本どおりに返す LLM、何も送らないチャンネル、仮想時計、シナリオを書くための補助

テストは別の Vivace.Tests に置き、7つには数えない（D8 8.2）。

決定 P-25　アセンブリの分け方 上の7つ。最初の到達点（ebise 相当）までは、これ以上分けない。API 層とフロントエンドは、そのときに足す（FUTURE.html）。

{

  • 連番はエンジンが振る（単独の書き手なので、起動時の最大値から数えればよい）。StorageBatch は、連番の決まったイベントと、変わった状態の行を持ち、CommitAsync は1つのトランザクションで書くだけ
  • IEventLog は、日誌（ペルソナの適用済みの事実を時刻順に）、「言ったこと」（スコープつき）、ビューアと実行レポートの検索を提供する

4.3チャンネル

public interface IChannel
{
    string Kind { get; }                                      // "misskey"
    ChannelCapabilities Capabilities { get; }
    Task StartAsync(VivaceEngine engine, CancellationToken ct);  // エンジンそのものを渡す（4.7）
    Task<IReadOnlyList<TimelineItem>> ReadTimelineAsync(PersonaId persona, int limit, CancellationToken ct);
    Task<SendResult> SendAsync(OutboundRequest request, CancellationToken ct);
    Task RecoverAsync(PersonaId persona, DateTimeOffset from, DateTimeOffset to, CancellationToken ct);
}

public abstract record SendResult
{
    public sealed record Sent(string ExternalId) : SendResult;
    public sealed record Failed(string Reason, bool SurelyNotSent, DateTimeOffset? RetryAfter) : SendResult;
}
能力意味使うところ
timelineタイムラインを読める投稿する（話題の抽出）
notifications通知を受け取れ、取りこぼしを取り直せる受信箱、圏外明けの再取得
post / reply / react / followそれぞれの外向きの操作ができるrequires、受信箱の判断の選択肢
postRateLimit投稿の間隔の下限（値つき）投稿のクールダウン（VISION 10章）
  • 通知の audience（public か、相手1人との dm か、記憶にしないか）は、チャンネルが決めて、到着の投入（notification.arrived、engine.InjectAsync）に入れる（VISION 13章）。Misskey では、ebise の audienceOf の規則（返信チェーンのうち最も狭い範囲に合わせる）をそのまま移す
  • 送信の再試行は、SurelyNotSent が真のとき（接続できなかった、など）だけ、配信役が短い間隔で 3 回まで行う。届いたかわからない失敗は、再試行せずに失敗にする（二重投稿より欠けるほうがまし。VISION 10章）
  • アカウントとトークンの対応は、チャンネルの設定として、ホストからチャンネルの実装に渡す。コアは知らない
  • このチャンネルにつながるペルソナは、engine.View から引く（ペルソナ定義の channels に、このチャンネルの種類があるインスタンス）

4.4LLM クライアント

public interface ILlmClient
{
    Task<LlmResult<T>> GenerateAsync<T>(LlmRequest request, CancellationToken ct);   // 構造化出力
    Task<LlmResult<string>> GenerateTextAsync(LlmRequest request, CancellationToken ct);
}

public sealed record LlmRequest(
    LlmTier Tier,                        // Main / Light（D6）。コアが目的から決めて入れる（P-53）
    string Purpose,                      // 目的。"planner"、"inbox.triage" など（D6 6.2）
    string System,
    IReadOnlyList<LlmMessage> Messages,
    IReadOnlyList<ITool>? Tools = null,
    double? Temperature = null,
    int? MaxOutputTokens = null);

public sealed record LlmResult<T>(T Value, LlmUsage Usage);   // モデル名、入出力のトークン数、所要時間

public interface ITool                   // 副作用のない参照系だけ（VISION 7章）
{
    string Name { get; }                 // "memory.search"
    string Description { get; }
    JsonElement ParameterSchema { get; }
    Task<string> InvokeAsync(ToolContext context, JsonElement arguments, CancellationToken ct);
}

// 目的ごとの取り決め。エンジンを組み立てるときに渡す（4.6）
public sealed record LlmPolicy(
    string Purpose,
    LlmTier? Tier = null,                // 段の上書き。省略すると、登録したときの既定の段
    RetryPolicy? Retry = null);          // 再試行の方針。省略すると既定（3 回、2 秒から倍）
  • モデル名はコアに書かない。Tier から実際のモデルへの対応は、LLM の実装の設定に持つ
  • ツールの呼び出しの往復は、実装の側で回す。ToolContext には、呼び出し元のペルソナと audience を入れ、記憶の検索が dm の記憶を返さないようにする（VISION 13章）
  • 再試行（指数バックオフ）は、コアの側で、目的ごとの方針で包む（D7）。実装は1回の呼び出しだけを担う
  • コアの中の処理とプラグインは、ILlmClient を直接呼ばず、エンジンの LLM のインターフェース（engine.Llm）を通して、目的の名前で呼ぶ。エンジンが段を決め、再試行で包み、痕跡と計測を残してから、ILlmClient を呼ぶ
決定 P-26　LLM クライアントは、コア独自の薄いインターフェースにする VISION 付録「LLM クライアントの抽象」への案。コアは Microsoft.Extensions.AI の IChatClient に直接依存せず、上の小さなインターフェースだけを持つ。理由は2つ。コアが求めるのは「目的」と「段」で、モデル名やプロバイダの設定ではないこと。テストの台本の LLM（目的ごとに決まった応答を返す）が書きやすいこと。実装の側で IChatClient を使うのは自由で、Anthropic の公式 SDK は IChatClient を実装している（D8）。
決定 P-53　目的は登録制にし、目的ごとの取り決めはコアのテーブルに集める

目的ごとの取り決め（段の上書き、再試行の方針）は、すべてコアの LlmPolicy のテーブルに持つ。LLM の実装が持つのは「段 → モデル名」の対応だけ。

目的は登録制にする。コアの目的（D6 6.2 の表）は、最初から既定の段つきで登録しておく。プラグインは、登録のときに AddLlmPurpose で申告する（名前はプラグインの名前で始める。4.7）。起動時に、LlmPolicy のテーブルにある目的が登録されていなければ、警告を出す（書き間違えると、設定が黙って効かないため）。登録されていない目的で呼ばれたら、既定の方針で呼んだうえで、ログに警告を出す（止めはしない）。

レビューで足した。目的を足す場所が「登録」の1か所に決まり、書き間違いが起動時に見つかる。

4.6公開 API

await using var engine = VivaceEngine.Create()
    .UseDefinitions("defs/")
    .UseStorage(new SqliteStorage("vivace.db"))
    .UseLlm(llm)
    .AddPlugin(new MisskeyPlugin(misskeyOptions))
    .UseLlmPolicies(policies)                   // 目的ごとの取り決め（4.4、P-53）
    .UseLoggerFactory(loggerFactory)
    .Build();                                   // 時計を省略すると実時間（SystemClock を作るまでは必須、J-161）

await engine.StartAsync(ct);                    // 起動と追いつき（D1 1.11）

InjectResult r = await engine.InjectAsync(request, ct);       // 投入 API
SimState view = engine.View;                                 // いまの状態（不変）
IAsyncEnumerable<LoggedEvent> feed = engine.Subscribe(ct);   // 適用済みのイベントの購読
IEventLog log = engine.Events;                               // ログの検索
ReloadResult rr = await engine.ReloadDefinitionsAsync(ct);   // 定義の読み直し
EngineStatus st = engine.Status;                             // 動いている / 止まっている（理由と、止まったイベントの連番）
await engine.RejectEventAsync(seq, reason, ct);               // 止まっているときに、問題のイベントを却下にする（D7 P-49）
await engine.ResumeAsync(ct);                                // 止まったエンジンを再開する

// ドライラン：仮想時計で、外に何も出さずに進める
await using var dry = VivaceEngine.Create()
    .UseDefinitions("defs/").UseStorage(SqliteStorage.InMemory())
    .UseLlm(llm).UseClock(new VirtualClock(start)).DryRun()
    .Build();
await dry.RunUntilAsync(start.AddDays(3), ct);

// 話題の注入：ループを回さず、判定と変換を1回だけ呼ぶ（VISION 16章）
TopicProbeResult probe = await engine.ProbeTopicsAsync(personaId, ["代々木公園"], ct);

// 定義の検証だけ（エディタから）
ValidationReport report = DefinitionLoader.Validate("defs/", plugins);
  • DryRun() は、チャンネルをすべて NullChannel に替え、配信役を止める
  • Subscribe は、適用済みのイベント（適用の記録の1件、LoggedEvent の Status = Applied）を、コミットのあとに適用の順で流す。登録は Subscribe を呼んだ時点で行う。購読ごとに容量つきのバッファ（Channel）を持ち、遅い購読者は、バッファ（いまは 1,024 件、J-160）があふれたら例外で終わらせて切断する（エンジンを止めない）。エンジンを破棄すると、購読は正常に終わり、破棄したあとの購読は何も流さずにすぐ終わる（J-159）
  • ビルダーの API は、いまは UseDefinitions（フォルダか、読み込み済みの DefinitionPack）、UseStorage、UseClock、UseDecider、UseHolidays、UseRandom、DryRun()。定義、保存先、時計は必須で、欠けていれば Build() が例外を投げる。定義のフォルダにエラーがあるときも例外にする。DryRun() は、チャンネルと配信役ができるまではフラグだけを持つ。エンジンの API は InjectAsync、View、Subscribe、RunUntilAsync、DisposeAsync で、中の SimEngine に任せる（J-161）
  • View は、いまは SimState（不変の状態）そのものを返す。読み取り用の StateView（4.5）は、ビューアや実行レポートを作るときに、要るものだけを足す（J-158）
  • プラグインにも、このエンジンそのものを渡す（4.7）。ホストに使えてプラグインに使えない API は作らない
  • DI コンテナには依存しない。ASP.NET Core などから使うときのための services.AddVivace(...) は、API 層を作るときに別のパッケージで足す
  • InjectAsync は、要求（InjectRequest）を投入 API で検査し、受け付けたら連番を、拒否なら理由を返す（D2 2.8）。RunUntilAsync の外では、ロック（System.Threading.Lock）を取ってその場で処理する。中では、コマンドを Channel に入れ、ループが各回の先頭で取り出す。ループが決める側の出力を待っている間も、コマンドが届けば起きて処理する。RunUntilAsync を抜けるときは、残ったコマンドをすべて処理してから、外の扱いに戻す。検査は、処理する時点（ループの中では取り出した時点）の状態とキューと時計の時刻で行う。時計の待ちは、いまはコマンドで起きない（SystemClock を作るときに D1 1.4 に合わせる、J-157）
決定 P-27　公開 API はビルダーとエンジンの1クラス 上の形。コアはヘッドレスのライブラリ（VISION 1章）なので、ホストの作り（CLI、Web、モバイル）を選ばない形にする。

4.7プラグイン

public interface IVivacePlugin
{
    string Name { get; }                                       // "misskey"。ID の名前空間になる
    void Register(IPluginRegistry registry);
}

public interface IPluginRegistry
{
    void AddChannel(IChannel channel);
    void AddEffectHandler(IEffectHandler handler);             // handler = "misskey.xxx"
    void AddNotificationRule(INotificationRule rule);          // 大分類が Other の通知を規則で捌く
    void AddTool(ITool tool);
    void AddDefinitions(string resourceName, Func<Stream> open); // 同梱の行動の TOML
    void AddHolidayCalendar(string name, IHolidayCalendar calendar);
    void AddLlmPurpose(string purpose, LlmTier defaultTier);   // LLM を呼ぶ目的の申告（4.4、P-53）
    VivaceEngine Engine { get; }                               // エンジンそのもの（動き出してから使える）
}

public interface IEffectHandler
{
    string Name { get; }
    Task<HandlerOutput> RunAsync(EffectContext context, CancellationToken ct);
}

public interface INotificationRule
{
    string Channel { get; }                                    // "misskey"
    IReadOnlySet<string> ChannelTypes { get; }                 // 捌く種類（"renote"、"pollEnded" など）
    RuleOutcome Handle(InboxItem item, RuleContext context);   // LLM は使わない
}

// 規則が出せるのは、発話ではない外向きの操作だけ
public sealed record RuleOutcome(ImmutableArray<OutboundOperation> Operations);
  • プラグインが足せるのは、ハンドラ、規則、ツール、行動の定義、チャンネル、カレンダーだけ。イベントタイプと、決定的な効果の語彙は足せない。外に出すものは、コアの outbound.* の中身（チャンネルが解釈する JSON）として表す（VISION 10章）
  • プラグインには、エンジンそのもの（VivaceEngine）を渡す。チャンネルは StartAsync の引数から、ほかの部品は IPluginRegistry.Engine から受け取る（エンジンが動き出してから使える）。読み取り、投入、読み直し、話題の注入まで、ホストと同じものが使える。投入の origin は、チャンネルの到着なら channel:<種類>、それ以外は plugin:<名前> を、プラグインが付ける（D2 2.9）
  • プラグインが守ること：エンジンの起動、停止、破棄、ドライランの時計（RunUntilAsync）には触らない。これらはホストの持ち物で、特にチャンネルの中から StopAsync を呼ぶと、エンジンがそのチャンネルの停止を待つので終わらなくなる。また、決める側のハンドラ（効果、規則、ツール）が判断に使うのは、コンテキストで渡されるスナップショットにする。生きている状態を読むと、決めた時点の前提とずれるから（D1 1.7）
  • 通知の規則：受信箱のうち大分類が Other のアイテム（D3 3.7.1）だけが、規則に回る。コアが、チャンネルと種類（ChannelType）で引いて、該当する規則に渡す。同じチャンネルの同じ種類に規則が2つ登録されたら、起動時のエラーにする（どちらが動くかを登録順で決めないため）。当たる規則がなければ、何もせずに処理済みにする
  • 規則が出せるのは、リアクションやチャンネル固有の操作のような、発話ではない外向きの操作だけ。本文つきの返信は、LLM がペルソナの声で書く道（Message）に限る。規則が定型文を返せると、ペルソナが言っていないことが「言ったこと」に混ざるから
  • チャンネル自身が片付ける通知（リバーシの対局の申し込みなど）は、受信箱に積まなくていい。受信箱に入れるのは、ペルソナがスマホを開いたときに捌くべきものだけ
  • プラグインが同梱する行動の ID は、プラグインの名前で始める（misskey.open_phone）
  • ペルソナと独立した機能：チャンネルのプラグインは、ペルソナのシミュレーションを通さない機能を、IChannel.StartAsync の中で動かしてよい（VISION 10章）。Misskey のリバーシは、ebise ではペルソナの機能だったが、Vivace では Misskey プラグインの中のゲーム機能として作る。対局はペルソナのアカウントで行ってよいが、ペルソナの行動、状態変数、イベント、記憶には関わらない（寝ている時間でも対局する）。シミュレーションに組み込むと複雑になりすぎるため。ただし、いまの状態はエンジン（engine.View）から読めるので、「睡眠中は対局を受けない」のような振る舞いは、プラグインの中で書ける（状態は読むだけで、変えない）
決定 P-28　プラグインは、ホストがコードで登録する フォルダに置いた DLL を読み込む方式（動的ロード）にはしない。最初のプラグインは Misskey だけで、ホストの CLI と一緒にビルドすれば足りる。動的ロードは、配布やバージョンの不一致、信頼の問題を連れてくるので、要るようになってから考える。
