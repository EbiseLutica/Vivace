2.1イベントの共通の項目

VISION 2章の項目を、次の形で持つ。保存の列は D3、状態の遷移は D1 を参照。

record SimEvent(
    long Seq,                    // 連番 = ID（P-10）
    DateTimeOffset Time,         // 絶対時刻（UTC）
    string EventType,            // イベントタイプ（"action.started" など）
    WorldId? WorldId,            // ID の型は D3 3.7
    PersonaId? PersonaId,
    EventPayload Payload,        // イベントタイプごとの中身（D3 3.9）。決めた結果もここに入る
    Guard? Guard,                // 適用前の検査（D1 1.7）
    long? BatchSeq,              // 同じハンドラの出力のまとまり（契機の決めどきの Seq）
    long? CauseSeq,              // このイベントを生んだイベントの Seq
    Origin Origin,               // 2.9
    JsonElement? Trace,          // 痕跡（2.9）
    DateTimeOffset? RealTime);   // 実時刻（送信完了、外部からの元の到着）
  • 段は、イベントタイプから一意に決まる（2.2）。だから項目としては持たず、保存もしない。並べるときに、イベントタイプから引く
  • バージョン番号は、イベントタイプごとの意味が違うので、ペイロードの中に持つ（行動のバージョン、状態変数のバージョン、プランのバージョン）。古いものを捨てる判定に使う
  • ワールドとペルソナは、オブジェクトではなく ID で指す。状態は Apply のたびに新しいオブジェクトに置き換わる（P-21）ので、参照で持つと古い時点の写しを指し続けてしまうから。中身が要るときは、その時点の状態から state.Personas[ev.PersonaId] のように引く
  • CauseSeq は、VISION にない項目。後続のイベントやハンドラの出力が、どのイベントから生まれたかを辿れるようにする。ビューアと実行レポートで「なぜこれが起きたか」を表示するのに使う
決定 P-10　イベントの ID は連番と兼ねる 1プロセス・1ファイルなので、連番（SQLite の INTEGER PRIMARY KEY）で一意に指せる。別に UUID を持たない。発話から確定状態への参照、記憶の出所、Cause は、すべて連番で指す。

ログを別のデータベースと突き合わせる用途（モバイルとの同期など）が出たら、そのときに UUIDv7 の列を足す。.NET 9 以降の Guid.CreateVersion7() で作れる。

段の意味と並びは VISION 4章のとおり。ここでは、各段に入るイベントタイプを確定させる。

決定 P-11　イベントタイプの一覧 上の表で確定させる。ペルソナとワールドの生成・破棄（persona.created など）は、「世界が変わる」の段に置く。状態変数の設定（vital.adjusted）と状態の付与（condition.attached）は、外からの投入でしか起きないが、出来事と同じく「世界が変わる」に置く。

2.3イベントタイプごとの Apply

「出す者」は、そのイベントを積む者。Apply は後続のイベント、ハンドラは決める側の出力、窓口は外からの投入（2.8）。

時間と予定

イベントタイプ出す者主な中身Apply
day.startedApply、窓口（ワールドの生成時）ワールド、現地の日付翌日の分を積む。出来事の抽選の StartHandler を出す（Planner は動かさない。D5 5.5）
plan.committedハンドラ（Planner）ペルソナ、期間（ホライズンから）、ブロックの列、由来（llm / fallback）、プランのバージョンプランを差し替え、バージョンを上げる。新しく入ったブロックの開始を block.started で積む。いま続いているブロックは、積み直さない（同じブロックが同じ時刻でプランにあれば、積まない。J-135）。いま動いているブロックが、プランにまだ始まっていなければ、今の時刻に始める。次に作り直す時刻を決めて、そこに plan.due を積む
plan.dueApply（plan.committed）ペルソナ、プランのバージョンバージョンが古ければ捨てる。このプランの期間の Planner がまだ動いていなければ（寝ていない）、起きたままの Planner の StartHandler を出す（D5 5.5）。段階2 では、同じ時刻に睡眠が始まるなら動かず、睡眠の開始が Planner を起こす（J-142）。Planner の期間のキーは、睡眠のブロック ID（J-141）。睡眠が始まれないときは、ブロックの開始で Planner を起こす（J-148）
block.startedApplyペルソナ、ブロック ID（自由時間は null）、プランのバージョンいまのプランに、そのブロックが同じ時刻で入っているかで見る（バージョンでは見ない。J-135）。同じブロックは一度だけ始める。移動中なら捨て、到着のときに確かめ直す（J-143）。自由時間なら決めどきを積む（決め中、行動中なら捨てる）。固定・計画のブロックなら、開始時の確認をする。満たせば action.started、満たせなければ決めどき（予定の乱れ）を積む。反射の行動の途中なら、それを打ち切らず、ブロックは始めない（反射の行動が終わったときに決める。D5 5.7）。スマホが開けるブロックなら phone.opportunity も積む
phone.opportunityApplyペルソナ、ブロック ID決めどき（スマホを開く機会）を積む。長いブロックで間隔が決まっていれば、次の機会も積む（D5）

決定と行動

イベントタイプ出す者主な中身Apply
decision.requestedApplyペルソナ、理由（下表）、ブロック ID状態は processing にする（決め中のフラグ Deciding を立てる。P-07、J-133）。StartHandler を出す（D1 1.8）。決め中に来たものは捨てる
activity.chosenハンドラ（Decider）行動、場所、経路、移動時間、所要時間、副行動か、乱数の範囲、候補の要約（痕跡）guard（行動のバージョン、実行できること、乱数の位置）を確かめる。行動のバージョンを上げ、乱数の位置を進める。場所が違えば travel.started、同じなら action.started を同じ時刻に積む。所要時間 0 の core.idle（何もしない）は、乱数の位置だけを進め、バージョンを上げず、後続を積まない（J-129）。待ちが 0 以下の次の予定の場所へ向かう行動は、移動だけで終わり、到着で決めどきを積み直す。同じ場所なら何も積まない（J-143）
block.respondedハンドラ（予定の乱れへの対応）ブロック ID、選んだもの（遅刻 / 欠席 / 待つ）遅刻は、ブロックの場所への移動を始める。欠席は、そのブロックを自由時間として扱い、決めどきを積む。待つは、出来事の解消かブロックの終わりの早いほうまで待機し、そこで開始時の確認をやり直す
travel.startedApply出発地、目的地、経路（辺の列）、到着の時刻、行動のバージョン移動中にする。居合わせが変わるので、社交欲求の率を出発地の全員について計算し直す。travel.arrived を積む
travel.arrivedApply場所、行動のバージョンバージョンが古ければ捨てる。居場所を書き換え、着いた場所の全員の率を計算し直す。続きの行動があれば action.started。続きの行動がなければ、着いた時刻に始まっていない固定ブロックがあれば block.started を、自由時間なら決めどきを積む（J-134、J-143）
action.startedApply行動、場所、所要時間、理由（chosen / block / reflex / late）、行動のバージョン行動中にし、率を切り替え、開始時の効果を当てる。action.ended を積む。効果に応じて StartHandler（受信箱、投稿）や Consolidate（睡眠、気絶）を出す。Consolidate を出すときは、このプランの期間の Planner がまだ動いていなければ、整理のあとに動く Planner の StartHandler も出す（D5 5.5）
action.endedApply行動、行動のバージョンバージョンが古ければ捨てる。バージョンは上げない（J-131。出力のハンドラは、同じ時刻でこのバージョンを見て適用されるため）。終了時の効果を当て、率を戻す。同じ時刻にブロックの開始がなく、自由時間の中なら、決めどきを積む。反射の行動が終わったときに、固定・計画のブロックの途中なら、決めどき（予定の乱れ。遅刻 / 欠席）を積む（D5 5.7）
決めどきの理由いつ候補
free自由時間のブロックが始まったDecider の通常の候補
ended自由時間の中で、行動が終わったDecider の通常の候補
interrupted出来事で行動が中断されたいまの場所から帰還できる候補
disruptionブロックの開始時の確認が通らない遅刻 / 欠席 / 待つ
phoneスマホを開く機会スマホを開く / 投稿する / 何もしない
retry出力が guard で却下された元の理由と同じ
決定 P-12　Decider の出力は activity.chosen 1件にし、移動と行動の開始・終了は Apply が積む VISION は「決定のイベントが、移動の開始と到着、行動の開始と終了のイベントを積む」としている。これを、Decider は選んだ結果を1件だけ出し、残りは Apply がチェーンのように積む形で実現する（2.4）。出来事で到着が遅れたときは、到着だけを積み直せば、その先の行動の開始と終了は、到着の Apply が新しい時刻で積む。先にすべてを積んでおくと、遅れたときに全部を無効にして積み直す必要がある。

SNS と外向きの操作

イベントタイプ出す者主な中身Apply
notification.arrived窓口（チャンネル）ペルソナ、チャンネル、通知の種類、送り主、audience、本文などの中身、元の到着時刻受信箱に積む。処理はしない（VISION 10章）
outbound.speechハンドラ（受信箱、投稿）チャンネル、投稿か返信か、本文、返信先、audience、確定状態への参照（連番の列）、チャンネルが解釈する中身「言ったこと」として残り、未送信の操作を作る。Deliver を出す
outbound.operationハンドラ（受信箱、プラグインの規則）チャンネル、操作の種類（コアの語彙は react と follow。チャンネル固有のものは other と中身で表す）、チャンネルが解釈する中身未送信の操作を作る。Deliver を出す。「言ったこと」には入らない
outbound.sent / failed / unknown窓口（配信役）、起動処理操作の ID、外部 ID、失敗の理由、次に投稿できる時刻操作の状態を書き換える。失敗に次に投稿できる時刻があれば、投稿のクールダウンの基準を更新する
inbox.handledハンドラ（受信箱）捌いた通知の ID と、それぞれの結果（返信 / リアクション / フォローし返した / 見た / 何もしない）受信箱の通知を処理済みにする。行動の途中で届いた通知は含まれないので、受信箱に残る
post.skippedハンドラ（投稿する）理由（話題が全部却下、生成の失敗、締め切り）空振りのクールダウンの基準を更新する（D6）
決定 P-13　発話と、発話でない操作を、別のイベントタイプにする VISION 10章は、両方を「外向きの操作」として同じ道で送る。送る道（未送信の操作の表と配信役）は共通にしたまま、イベントタイプだけを分ける。「言ったこと」を引くとき（日誌、記憶の整理、コンテキスト）に、イベントタイプだけで絞れるから。

2.5行動の効果の語彙

行動の TOML の [effects] に書けるもの。Apply が解釈する決定的な効果と、決める側のハンドラを起こす効果の2種類がある。

決定的な効果

キー意味例
rate.<変数>行動の間の、その変数の増加率（1時間あたり）。書いた変数は、既定の率の代わりにこの率を使うrate.energy = -8
on_start.<変数> / on_end.<変数>開始時 / 終了時の増減on_end.boredom = -30
restore.<変数>終了時に、その値にする（増減ではなく設定）restore.energy = 100
repeat_decay同じ行動が続いたときの、退屈度の下がり幅の減り方（VISION 6章）。直前に同じ行動を k 回続けていたら、退屈度の減少に decayk を掛けるrepeat_decay = 0.6
sleep睡眠として扱う。consolidate（記憶の整理を起こすか）と debt（寝不足の判定をするか）を持つ。起床の判定（日誌の範囲）にも使うsleep = { consolidate = true, debt = true }

ハンドラを起こす効果

キー意味出力
handler = "sns.inbox"受信箱を捌く（VISION 10章）outbound.speech outbound.operation inbox.handled
handler = "sns.post"話題の抽出から文面の生成まで（VISION 10章、11章）term.recorded place.added outbound.speech post.skipped
handler = "<プラグイン>.<名前>"プラグインが足すハンドラコアのイベントタイプ（中身はチャンネルが解釈する）

組み込みの行動

ID中身schedule_only
core.go_to_next次の予定の場所へ向かい、着いたら待つ。条件が成り立つ限り、いつでも候補に入る（VISION 5章）。所要時間は持たず、待ちは次の予定の開始まで。なければプランの終わり（J-112）いいえ（Decider が必ず足す）
core.idle何もしない（スマホを開く機会の「ブロックを続ける」、待機）。スマホは開ける（J-100）はい
core.sleep睡眠。rate.energy = 0、restore.energy = 100、sleep = { consolidate = true, debt = true }はい
core.faint気絶。所要時間は固定。restore.energy = 50、sleep = { consolidate = true, debt = false }はい
core.go_home_rest早退して家で休む。家（ペルソナ定義の home）へ移動して、休むはい

schedule_only は、行動の定義に書けるフラグで、ユーザーの行動にも使える（D3 3.6）。付いた行動は、固定予定のブロックと反射からだけ始まり、Decider と Planner の候補にならない。昼寝のように、自由時間に選ばれてよい休む行動は、フラグを付けず、記憶の整理も起こさない別の行動として書く。

決定 P-14　行動の効果の語彙 上の3表で確定させる。率は「足す」ではなく「置き換える」にする。睡眠中は気力が減らない、のような表現が、打ち消しの数値を書かずに済むから。社交欲求の既定の率は、居合わせ（一人か、同席か）で変わる（D5）。行動が rate.social を書けば、居合わせに関係なく、その率を使う。

2.6requires と制限の語彙

キー意味
requires.place_tags場所が、これらのタグをすべて持つ。空なら、どの場所でもよい
requires.itemsペルソナが、これらの携行品のタグをすべて持つ
requires.channelペルソナが、この能力を持つチャンネルにつながっていて、圏外ではない。{ capability = "post" } など。能力の語彙はチャンネルの章（D4）

limits.max_per_day現地の1日（0:00 から）に、この回数まで
limits.hours現地の時刻がこの範囲にあるときだけ（["06:00", "23:00"]）

  • 制限の判定に要る「前回の時刻」「今日の回数」は、ペルソナインスタンスの状態に、行動ごとに持つ（D3）。ログを毎回引かずに済み、Apply の中で決定的に更新できる
決定 P-15　制限に max_per_day と hours を足す VISION は「クールダウンなどの制限」とだけ書いている。クールダウンだけでは、「深夜 3 時に銭湯」「1日に5回カフェ」を防げないので、回数と時刻の範囲を足す。場所の営業時間は持たない（行動の時刻の範囲で足りるうちは）。

キー対象意味戻し方

slow_placeワールドその場所につながる辺の移動時間を増やす（add 分、または factor 倍）。道の工事や渋滞解消で戻す

conditionペルソナ状態（風邪など）を付ける解消で外す

対象の場所は、place = "id" で決め打ちするか、place_tag = "road" で、そのタグを持つ場所から抽選する。抽選の結果は、イベントに記録する。

状態（コンディション）

風邪のような、ペルソナに付く状態は、出来事のライブラリの中に [[condition]] として定義する。

2.8投入できるイベント

投入の窓口（VISION 15章）が受け付けるイベントタイプ。時刻は指定するか「いま」。過去は不可。

イベントタイプ検査
incident.occurredライブラリの ID があるか、その場の定義が語彙だけで書かれているか。対象が存在するか。窓口からの投入は抽選せず、窓口で場所と効果を確定して渡す（場所のタグからの抽選は窓口ではしない）
vital.adjusted変数が4つのどれかか。理由が書かれているか（訂正として残す）
condition.attached / detached状態の ID があるか
notification.arrivedペルソナがそのチャンネルにつながっているか
place.added / adopted / retired場所の検証（D6「新しい場所のつなぎ方」と同じ）
persona.created / destroyed定義があるか。生成先のワールドが生成済みで、破棄されていないか。破棄なら、インスタンスがまだ破棄されていないか
world.created / destroyed定義があるか。破棄なら、まだ破棄されていないか

エンジンは、投入の要求をコマンドとして受け、処理する時点で窓口に検査させ、結果（受け付けたイベントの連番、または拒否の理由）を返す。いつ処理するかは D4 4.6。誰に投入を許すかは、コアの外（API 層）が決める。

要求（InjectRequest）は、イベントタイプ、中身、時刻の指定（省略可）、出所だけを持ち、キューに入る前の下書き（EventDraft）には依存しない。要求 → 検査 → 下書き、の一方向にする。窓口（InjectionValidator）は、時刻を決め（省略なら、エンジンが処理した時点の時計の時刻）、過去の時刻を拒否し、その型のルールに検査を任せ、通ったら下書きを作る（J-154、J-156）。

  • 窓口が受け付けるのは、Apply のルールの表にあり、そのルールが投入の検査を持つ型だけ。型ごとの検査は、その型のルール（EventRule）の仮想メソッドに置き、既定は「未対応の型」で拒否する。表にない型も同じ理由で拒否する。上の表の型は、その型のルールを作るときに、適用と投入の検査を同じクラスに並べて足す。いまの段階で受け付けるのは world.created と persona.created だけ
  • guard の評価は、型に紐づかないので、ルールに置かずに Apply の入口（EventApplier）に置いたままにする
  • persona.created の「生成先のワールドが生成済み」は、要求の時刻以前の world.created（同じ居住ワールドの定義）がキューにあれば、生成済みとみなす。ワールドとペルソナを同じ時刻に続けて投入できるようにするため。同じ時刻なら、段が同じで先に積んだ world.created が先に適用される。要求より後の時刻の world.created しかなければ、ペルソナが先に適用されて捨てられるので、拒否する（J-155）

2.9origin と痕跡

origin意味
sim通常の運転で、Apply かハンドラが積んだ
catchup追いつきの間に積んだ

後続のイベントは、契機のイベントの origin を引き継ぐ（追いつきの中で積まれたものは、すべて catchup）。

痕跡（trace）は、イベントにしない途中の結果を、JSON で付ける。Decider の候補とスコアの上位、話題の抽出と判定、LLM の呼び出しの記録（目的、モデル、トークン数、所要時間）など。ビューアと実行レポートが読む。中身の形は、ハンドラごとに決め、Apply は読まない。
