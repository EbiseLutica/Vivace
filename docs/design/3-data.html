3.13つの層

ホストの設定（SQLite のファイルの場所、LLM の API キー、チャンネルのアカウントとトークン）は、定義に含めない。ホストのアプリが持ち、コアには構築時に渡す（D4）。

3.2定義ファイルの配置

defs/
  worlds/*.toml        1ファイルに1ワールド
  personas/*.toml      1ファイルに1ペルソナ
  actions/*.toml       [[action]] を何件でも
  incidents/*.toml     [[incident]] と [[condition]] を何件でも
  • 組み込みの行動（core.*）と、プラグインが同梱する行動（misskey.* など）は、アセンブリに埋め込んだ TOML から読む。形式はユーザーの TOML と同じ
  • ID は、英小文字・数字・_ と、名前空間の . だけ。ユーザーの定義は名前空間なしで書く。同じ ID が2つあれば、読み込みのエラー
  • 未知のキーは、エラーにせず警告にする（VISION 2章「スキーマは、未知のフィールドで壊れないように」）。タイプミスに気づけるよう、警告にはキーの場所を出す
  • 時間の長さは、"45m"、"1h30m"、"3d" のように単位つきの文字列で書く。時刻は "HH:mm"（現地時刻）、年をまたぐ期間は "MM-DD"
決定 P-17　定義ファイルの配置と ID の名前空間 上のとおり。ワールドとペルソナは、1ファイル1件にして、ファイルの差分と編集の単位を揃える。行動と出来事は、似たものをまとめて書けるよう、1ファイルに何件でも書けるようにする。

3.3ワールド定義

id = "tokyo"
name = "東京の郊外"
lore = """
現代日本の東京。主人公たちは高校生で、郊外の住宅地に住んでいる。
"""
utc_offset = "+09:00"            # 時差
generated_places = "auto"        # auto | review（VISION 11章）
not_exist = "魔法や超常現象は存在しない。"   # 存在しないものの一覧（任意）

[calendar]
holidays = "jp"                  # 祝日の暦の提供元（P-18）。省略時は祝日なし
events = { "12-24" = "クリスマスイブ", "10-31" = "ハロウィン" }   # 年中行事（Planner への手がかり）

[[term]]                         # 変換の辞書の初期値
from = "代々木公園"
verdict = "pass"                 # pass | convert | reject

[[place]]
id = "kaori_room"
name = "香織の部屋"
tags = ["bed", "desk"]
group = "家"
links = { home_living = 1 }      # つながる場所の ID と移動時間（分）

[[place]]
id = "home_living"
name = "居間"
tags = ["sofa", "tv", "kitchen"]
group = "家"
links = { street_home = 1 }
  • 辺は、片方に書けば逆向きにも張る。両方に書いて時間が食い違えば、読み込みのエラー（VISION 8章）
  • 場所のタグのうち、どの行動の requires にも出てこないものは、読み込み時に警告する（効果がないので）
決定 P-18　祝日と年中行事は、ワールドの暦に持つ ebise は、内閣府の祝日 CSV を取得して、学校の休みを判定していた。魔界に日本の祝日はないので、祝日はワールドが決めるものにする。calendar.holidays は提供元の名前で、コアは IHolidayCalendar の口だけを持ち、日本の祝日は別のパッケージ（または同梱のデータ）で提供する。年中行事は、ワールド定義に直接書く。

3.5固定予定

ebise の書き方（期間ごとのセット、曜日、祝日に休むか、睡眠のブロック）を引き継ぎ、TOML で書きやすい形にする。

[[schedule.period]]              # 期間（毎年繰り返す）
id = "summer"
from = "07-21"
to = "08-31"

[[schedule.period]]
id = "winter"
from = "12-25"
to = "01-07"                     # from > to は年をまたぐ

[[schedule.block]]
id = "sleep_weekday"
days = ["mon", "tue", "wed", "thu", "fri"]
from = "23:45"
to = "06:30"                     # to < from は日をまたぐ
action = "core.sleep"
place = "kaori_room"

[[schedule.block]]
id = "school"
in = ["default"]                 # 期間に当たらない日だけ
days = ["mon", "tue", "wed", "thu", "fri"]
from = "08:30"
to = "15:40"
action = "attend_class"
place = "classroom_2a"
skip_holiday = true
phone = "closed"

[[schedule.block]]
id = "short_break"
within = "school"                # school の中の休み時間。書かなかった項目は school から引き継ぐ（P-52）
times = [["10:20", "10:30"], ["11:30", "11:40"], ["14:30", "14:40"]]   # 同じ中身の時間帯を並べて書ける
phone = "open"                   # 行動と場所は school のまま、スマホだけ開ける

[[schedule.block]]
id = "lunch_break"
within = "school"
from = "12:20"
to = "13:00"
action = "eat_lunch"
phone = "open"
with = ["shiori"]                # 同行（相手の定義にも書く）
on_partner_absent = "continue"   # continue | cancel（D5）

[[schedule.exception]]
date = "2026-12-24"
skip = ["school"]
[[schedule.exception.block]]
id = "xmas_party"
from = "18:00"
to = "21:00"
action = "party"
place = "home_living"
規則内容
その日の期間日付が当たる期間のうち、いちばん短いもの。どれにも当たらなければ default（ebise と同じ）
ブロックの所属in に、その日の期間があるブロックだけを使う。in を省略したブロックは、すべての期間で使う（睡眠など、期間で変わらないもの）
入れ子ほかのブロックの中に置けるのは、within で親を指したブロックだけ。その間は内側のブロックが優先し、終わったら外側のブロックに戻る。within のないブロックどうしが重なれば、読み込みのエラー（P-52）
within親のブロックを指す。書かなかった項目（曜日、期間、行動、場所、スマホ、祝日に休むか）を親から引き継ぐ。親が休みの日（祝日、例外日の skip）は、子も休む。親の時間からはみ出したら、読み込みのエラー（P-52）
timesfrom と to の代わりに、時間帯を並べて書ける。中身が同じで時間だけ違うブロック（休み時間）を、1つにまとめるため（P-52）
日をまたぐブロック開始した日のブロックとして扱う。月曜 23:45〜火曜 6:30 の睡眠は、月曜の sleep_weekday
スマホphone は、行動定義の既定値を上書きする。長いブロックの途中の機会は phone_every（D5）
例外日skip でその日のブロックを外し、block で足す。足したブロックも、重なりの検査を通す
ブロックの IDプランの中では「定義の ID@開始日」（sleep_weekday@2026-11-02）で指す。プランの継ぎ目をまたいで続いているかの判定に使う（D5 5.5）。times の2つ目以降と、入れ子で分かれた外側の後半は、.2 のように番号を付ける（school.2@2026-11-02）
ブロックの長さ固定予定のブロックでは、行動はブロックの時間いっぱい続く。行動定義の duration は使わない
決定 P-20　固定予定と生活リズムの書き方 上のとおり（VISION 付録「固定予定と生活リズムの書き方」）。ブロックの入れ子と times は、下の P-52。生活リズム（起床・就寝の目安）は、別の項目にせず、睡眠のブロックそのものとする。ebise はセットごとにブロックの配列を持っていたが、TOML では配列を共有できないので、ブロックの側に「どの期間で使うか」（in）を書く形に変える。
決定 P-52　固定予定のブロックの入れ子と、times

授業の中に休み時間や昼休みを置く書き方を許す。外側のブロックを分けて書く必要はない。読み込み時に、入れ子を重ならない区間の列に展開する（授業 8:30〜10:20、休み時間 10:20〜10:30、授業 10:30〜11:30 …）。展開した区間ごとに行動が始まり直すので、Apply と Decider は、いままでどおり重ならないブロックの列だけを見ればよい。

入れ子にするには、within が必須。親を指さずに重ねられると、外側のブロックが祝日や例外日で休みになった日に、内側のブロックだけが残る（クリスマスに、教室で昼休みだけをとる）。それに気づきにくいので、黙って入れ子にせず、エラーにする。within を書けば、親と一緒に休む。

入れ子の深さは制限しない（いちばん内側が優先）。同じ親の子どうしが重なるのは、エラー。

3.6行動と出来事の定義

[[action]]
id = "walk_park"
display = "公園を散歩する"
description = "近所の公園をゆっくり歩く。"
tags = ["outdoor", "exercise"]   # 行動タグ（好みと状態の補正に使う）
duration = ["20m", "60m"]        # 範囲か、固定の "45m"
weight = 1.0                     # 基本の重み
phone = "open"                   # 行動中にスマホを開けるか
requires.place_tags = ["park"]
limits.hours = ["06:00", "21:00"]
effects.rate.energy = -6
effects.on_end.boredom = -25
effects.repeat_decay = 0.6

[[action]]
id = "attend_class"
display = "授業を受ける"
schedule_only = true             # 固定予定と反射からだけ始める（自由時間の候補にしない）
phone = "closed"
requires.place_tags = ["classroom"]
effects.rate.energy = -6
effects.rate.boredom = 4
[[incident]]
id = "road_work"
display = "道路工事"
target = "world"                 # world | persona
chance = 0.03                    # 1日あたりの発生確率
hours = ["08:00", "18:00"]       # 発生する時刻の範囲（現地）
duration = ["2h", "8h"]
cooldown = "7d"                  # 再発までの間隔
effects.slow_place = { place_tag = "road", add = "15m" }

[[incident]]
id = "catch_cold"
display = "風邪をひく"
target = "persona"
chance = 0.01
duration = ["1d", "3d"]
cooldown = "30d"
effects.condition = "cold"

[[condition]]
id = "cold"
display = "風邪"
rate.health = -0.5
weight."tag:outdoor" = 0.3
threshold.health = 25

duration は、その場所でする行動そのものの長さで、移動時間を含まない。移動時間は、場所のグラフから別に足す（D5 5.2 の帰還の式）。固定予定のブロックでは、duration は使わず、ブロックの長さで決まる（3.5）。schedule_only = true の行動は、固定予定のブロックと反射からだけ始まり、Decider と Planner の候補にならない（ペルソナの use のワイルドカードに当たっても外す。D5 5.2）。授業やバイトのように、自由時間に選ばれると困る行動に付ける。duration は省略してよい（固定予定ではブロックの長さを使うため）。効果、requires、制限の語彙は D2。組み込みの反射の行動（core.faint など）は、所要時間を固定で書く（反射は Apply が乱数を引かずに始めるため）。

3.7ドメイン型

状態は、record と System.Collections.Immutable の不変オブジェクトで持つ。Apply は、変わったところだけを作り直した新しい状態を返す。

sealed record SimState(
    Position Position,                                  // 最後に適用した（時刻、段、連番）と適用番号
    ImmutableDictionary<WorldId, WorldState> Worlds,
    ImmutableDictionary<PersonaId, PersonaState> Personas);

sealed record WorldState(
    WorldId Id, string DefId, ulong Seed, WorldStatus Status,
    ImmutableDictionary<PlaceId, RuntimePlace> GeneratedPlaces,   // 生えた場所（候補、採用、廃止）
    ImmutableDictionary<string, TermEntry> Terms,                 // 変換の辞書の実行中の記録
    ImmutableDictionary<long, ActiveIncident> Incidents,          // 発生中の出来事
    long GraphVersion);                                           // 場所のグラフが変わるたびに上げる

sealed record PersonaState(
    PersonaId Id, string DefId, WorldId World, PersonaStatus Status,
    Location Location,                                  // 場所 ID、または移動中（経路と出発時刻）
    Activity? Activity, long ActivityVersion,           // 実行中の行動（D1 1.8）
    Activity? Overlay,                                  // 固定ブロック中にスマホを使っている間だけ（開く、投稿する）
    Vitals Vitals,                                      // 4変数の基準時刻・値・率と、状態変数の版
    ImmutableArray<AttachedCondition> Conditions,
    DayPlan? Plan, long PlanVersion,
    ImmutableDictionary<string, ActionUsage> Usage,    // 行動ごとの前回の開始、今日の回数、連続回数
    ImmutableDictionary<string, ulong> Rng,            // 用途ごとの乱数の位置（D5）
    PostingState Posting,                               // 最後の投稿、空振り、サーバーの制限
    ImmutableList<InboxItem> Inbox,                    // 未処理の通知だけ
    ImmutableList<OutboundOp> Outbound,                // 未送信の操作だけ
    DateTimeOffset? LastWake);                          // 日誌の範囲の起点（VISION 13章）
  • ID は readonly record struct で型を分ける（PersonaId、WorldId、PlaceId）。文字列の取り違えをコンパイラで防ぐ
  • ワールドやペルソナの状態のような、項目の多いものは sealed record（参照型）にする。参照が同じかどうかだけで「変わったか」がわかり（変わった行だけを SQLite に書くため）、辞書から取り出したり写しを渡したりするたびの丸ごとのコピーも起きない。default で中身の空な状態が作られることもない。ID、イベントの並びの位置、状態変数1本ぶん（値、基準時刻、率）のような小さな値は、readonly record struct にする
  • 受信箱は、ペルソナインスタンスの状態に持つ（VISION 2章）。アイテムの形は下の「受信箱のアイテム」
  • 受信箱と未送信の操作は、処理が済んだら状態から外し、SQLite の表にだけ残す。状態は、決める側に渡す写しでもあるので、小さく保つ
  • 居合わせ（誰と同じ場所にいるか）は、状態に持たない。Personas の Location から導く（VISION 2章）
  • 定義も同じく不変の Definitions にし、Apply と決める側に引数で渡す（VISION 4章）。最短経路のような導出データは、Definitions と GraphVersion をキーにしたキャッシュに持ち、保存しない
決定 P-21　状態は不変オブジェクトで持ち、写しは参照を渡す VISION 付録「決める側に渡す状態の写しの作り方」への案。状態が不変なら、写しは参照を渡すだけでよく、コピーもロックも要らない。前提の規模（最大 10 人）なら、Apply のたびに数個の record を作り直すコストは無視できる。
決定 P-22　インスタンス ID は「定義 ID@ワールド ID」 kaori@tokyo。破棄したあとに同じ定義から同じワールドに生成し直したら、kaori@tokyo#2 のように番号を付ける。ログと記憶の表で、人が読んで誰かわかる形にする。

3.7.1受信箱のアイテム

チャンネルは、届いた通知を、コアが読める形に訳して積む（notification.arrived）。コアは、この形だけを見て捌き方を決める（D6 6.5）。外のサービスの形（Misskey の JSON など）は、コアに持ち込まない。

sealed record InboxItem(
    long Seq,                               // 到着のイベントの連番（ID を兼ねる）
    string Channel,                         // "misskey"
    InboxKind Kind,                         // コアが読む大分類：Message / Reaction / Follow / Other
    string ChannelType,                     // チャンネル独自の種類（"mention"、"reply"、"quote"、"chat" など）
    Sender Sender,                          // 送り主
    Audience Audience,                      // public / dm / 記憶にしない（VISION 13章）
    string? ConversationKey,                // 同じ会話を見分ける鍵（スレッドの根元、DM の相手など）
    string? Text,                           // 本文（Message）
    ImmutableArray<Attachment> Attachments, // 添付（画像の URL など。Message）
    ImmutableArray<ThreadMessage> Thread,  // それまでの会話（古い順。Message）
    string? Reaction,                       // リアクションの絵文字（Reaction）
    string? TargetExternalId,               // リアクションされた自分の発言の外部 ID（Reaction）
    DateTimeOffset? OriginalArrivedAt,      // 元の到着時刻（圏外明けに取り直したとき）
    JsonObject Payload);                    // チャンネルだけが読む中身（返信先のノート ID など）

sealed record Sender(string UserId, string DisplayName, string? Handle);
sealed record ThreadMessage(Sender Sender, bool IsSelf, string? Text, DateTimeOffset PostedAt,
                            ImmutableArray<Attachment> Attachments);
sealed record Attachment(string Kind, string Url, string? Description);   // Kind は "image" など
大分類中身コアの捌き方（D6 6.5）
Message言葉で話しかけられたもの（メンション、返信、引用、DM）。本文、添付、それまでの会話を持つLLM が、返信 / リアクション / 何もしない を決める
Reaction自分の発言へのリアクション。絵文字と、どの発言へのものかを持つLLM を使わない
FollowフォローされたLLM を使わず、フォローバックの方針で決める
Other上のどれにも当たらない、チャンネル固有のものプラグインの規則（INotificationRule、D4 4.7）に任せる
  • それまでの会話（Thread）は、チャンネルが到着のときに取って入れる。ノートへの返信なら返信チェーン、DM なら直近のメッセージ（ebise と同じ）。到着のイベントに記録されるので、決める側は外を取り直さずに読める。長い会話でも、直近 20 件までにする
  • 自分の発言かどうか（IsSelf）は、チャンネルが付ける。LLM には、自分の発言と相手の発言を分けて見せる
  • ConversationKey が同じアイテムは、同じ会話として、まとめて捌く（D6 6.5）
  • notification.arrived の適用で入り、inbox.handled の適用で外れる（D2 2.3）。外れたあとは、inbox の表に、結果と一緒に残る（3.8）

  • ペルソナの行は、変わるたびに行ごと書き直す。1行は数 KB で、前提の規模なら十分に軽い
  • キューの順序（時刻、段、連番）は、メモリの上で並べる（D1 1.4）。段は列に持たないので、SQL では並べない
  • イベントは消さない。1人あたり1日 150 件ほどとして、10 人で年 55 万件。SQLite で問題のない量
  • スキーマの版は PRAGMA user_version で持つ。マイグレーションは、アセンブリに埋め込んだ番号つきの SQL で、起動時に足りない分を1つのトランザクションで当てる
  • 接続の設定は journal_mode=WAL、synchronous=NORMAL、busy_timeout=5000、foreign_keys=ON
決定 P-23　表の構成は「よく使う列 + JSON」 完全に正規化すると、ペルソナの状態だけで 10 表近くになり、Apply のたびの書き込みが煩雑になる。状態の表は、絞り込みに使う列（ID、所属、状態）だけを列にし、残りを JSON にする。生えた場所、辞書、受信箱、送信、記憶のように、ビューアや実行レポートで一覧にするものは、別の表にする。
決定 P-24　時刻は UTC の Unix ミリ秒で保存する 比較と並べ替えが整数で済み、インデックスが効く。C# では DateTimeOffset（オフセット 0）で持つ。現地時刻は、ワールドの時差を足して、その場で計算する。時差は固定なので、タイムゾーンのライブラリは使わない。

3.9JSON とバージョン

  • イベントのペイロードは、イベントタイプごとの record にし、System.Text.Json で読み書きする。イベントタイプは列（event_type）で持つので、JSON の中には型の印を入れない
  • ペイロードには "v": 1 のように、イベントタイプごとの版を入れる。項目を足すときは、版を上げずに省略可能な項目として足す。意味を変えるときだけ版を上げ、読み込み時に古い版を新しい形に変換する
  • 知らないイベントタイプのイベント（新しい版で書かれたもの）を読んだら、起動を止める。黙って捨てると、状態がずれるから
  • チャンネルが解釈する中身（返信先のノート ID など）は、コアが中を見ない JSON として持つ（VISION 10章）
