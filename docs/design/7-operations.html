7.1失敗したとき

失敗振る舞い管理者への通知
定義の検証のエラー起動しない。読み直しなら拒否して、古い定義で動き続ける読み直しの結果として返す
LLM の一時的な失敗（タイムアウト、429、5xx）指数バックオフで 3 回まで再試行する。ループの中のハンドラは 2 秒から、記憶の整理は 10 秒から倍にする。尽きたら、ハンドラごとの代わりの出力（D6 6.2）同じ目的が 1 時間に 5 回尽きたら
LLM の恒久的な失敗（認証、不正なリクエスト）再試行しない。代わりの出力にするすぐに
構造化出力が読めない理由を添えて1回だけ作り直させる。だめなら、代わりの出力しない（痕跡に残す）
ハンドラの例外（バグ）LLM の失敗と同じく代わりの出力にする。Decider なら core.go_to_next を選んだことにするすぐに
レーンのジョブの例外（上の扱いから漏れたもの）エンジンを止める。そのレーンを閉じ、実行している呼び出しから、出力を待っている途中でもすぐに例外を出す。コミット済みの状態とログはそのまま残り、停止の手順（D1 1.11）で閉じるすぐに
Apply の例外（バグ）エンジンを止める。イベントを飛ばして進めると、状態の不変条件が崩れるから。メモリの状態は不変なので、コミット前の状態がそのまま残るすぐに
SQLite の書き込みの失敗エンジンを止める（状態とログがずれるのを防ぐ）すぐに
送信の失敗D4 4.3 のとおり。確実に送れていないときだけ再試行する同じチャンネルが 1 時間に 5 回失敗したら
チャンネルの切断チャンネルが再接続し、切れていた間の通知を取り直して、いまの到着として積む（VISION 10章）30 分つながらなければ
記憶の整理の失敗D6 6.7同じ層が 3 回続けて失敗したら
決定 P-49　Apply の例外では、エンジンを止める 止めるのはエンジンだけで、デーモンのプロセスは生かしておく（7.5）。止まっている間も、状態とログは読める。管理者は、原因を直して再起動するか、問題のイベントを却下にして（vivace events reject <seq>）再開する（vivace resume）。自動で飛ばす仕組みは作らない。どのイベントで止まったかは、ログと通知に連番を出す。

7.2定義の検証

検証はコアの関数で、エディタからも呼べる（VISION 2章）。結果は、ファイルと行の位置つきのエラーと警告の一覧。位置は、キーで指せるものはキー、指せないものはテーブルの見出しの位置。入れ子のキーは「親.子」で指す（J-99）。固定予定の重なりは、2028 年から 28 年の全日（うるう年と曜日を一巡する）と、例外日の前後の日について、祝日を考えずに検査する。前日から続くブロックとの重なりも見る（J-104）。同行の相手と時刻、場所、行動の一致も見る（J-117）。出力の並びは序数で固定する。ファイルは相対パスの順、問題は位置、コード、文面の順、場所のつながりは ID の順（J-126）。

エラー（読み込まない）

  • TOML の構文
  • 必須の項目がない（id、lore など）
  • ID の重複、名前空間の違反
  • 参照先がない（区間、居住ワールド、固定予定の行動と場所、home、同行者）
  • 両側に書いた区間の時間の食い違い
  • 固定予定のブロックの重なり
  • 反射の行動の所要時間が範囲になっている
  • ペルソナ定義で core.go_to_next を forbid している（D5 5.2）
  • 値の型と範囲（確率が 0〜1 の外、など）

警告（読み込む）

  • 未知のキー（効果の語彙にないキーも含む）
  • 目的ごとの取り決め（LlmPolicy）に、登録されていない目的がある（D4 P-53）
  • どの行動も要求しない場所のタグ（出来事の slow_place、close_place の place_tag も要求とみなす。J-107）
  • 使う行動のワイルドカード（misskey.* など）に当たる行動がない（警告。プラグインなしでも読める。J-127）
  • requires の携行品を、そのペルソナが持たず、一度も実行できない行動（警告。J-127）
  • 同行の相手と時刻、場所、行動が一致しない（警告。J-117、J-127）
  • requires のタグを、どの場所も持っていない
  • このワールドで一度も実行できない行動（VISION 7章）
  • 片側にしか書いていない同行
  • タイムラインを読めないチャンネルで「投稿する」を使う（VISION 10章）
  • 固定予定の隙間が、場所の間の移動時間より短い

検証の範囲（J-147）：固定予定の隙間が移動時間より短い警告は、この検証で位置つきで出す（ScheduleGap、警告）。重なりの検査と同じ全日の走査（28 年と例外日、(期間, 曜日) の使い回し）。前日からの隙間も見る。

vivace validate の出力（J-162）：問題を読み込みの並びのまま、1行ずつ「位置: 重大度 コード: 文面」で出す。最後に「エラー N 件、警告 M 件」を出す。エラーがあれば終了コード 1、なければ 0。定義のフォルダがなければ、その旨を出して 1 で終わる。

7.3観測

手段中身
ログ（ILogger）カテゴリは部品ごと（Vivace.Engine、Vivace.Llm など）。イベントの適用は Debug、決定と送信は Information、代わりの出力への切り替えは Warning
計測（System.Diagnostics.Metrics）適用の遅れ（実時刻 − イベントの時刻）、キューの長さ、ホライズンで待った時間、ハンドラの所要時間、LLM のトークン数（目的ごと）、却下と破棄の数
痕跡イベントに付けた途中の結果（D2 2.9）。ビューアで決定の理由を読む
実行レポートログの集計。生成された場所の一覧、却下された話題と理由、場所ごとの利用回数（VISION 16章）。加えて、LLM の目的ごとの呼び出し数とトークン数、却下と破棄の内訳、適用の遅れの分布

7.4テストの層

層対象書き方
Apply の単体イベントタイプごとの Apply と guard（状態、イベント、定義）を手で作り、新しい状態、後続のイベント、シグナルを比べる。純粋な関数なので、モックは要らない
決める側の単体Decider、Planner の検査と補正、話題の手順、コンテキストの組み立てスナップショットと now と乱数の位置を与える。LLM は台本で返す
シナリオ数日分の通しの動き仮想時計、メモリの SQLite、台本の LLM、null channel で N 日回し、事実のイベントの列を正規化して、保存しておいた期待値と比べる（スナップショット）
不変条件シナリオの全適用（J-145、J-148）適用のたびに検査する：時刻が戻らない、状態変数が範囲の中、各ペルソナに次の自分のイベントがある（止まっていない。状態ごとに、バージョンまで合わせて見る。行動中は同じバージョンの action.ended、移動中は travel.arrived、決定中は決めるジョブか activity.chosen、自由時間でアイドルなら決定タイミング（decision.requested など））。同じ時刻に適用が 10,000 件を超えたら止める（時刻が進まない状態。J-148）、未適用のイベントの時刻がいまの位置より前にない
再起動落ちても壊れないことシナリオの途中のランダムな位置でエンジンを止め、再起動して最後まで回す。止めなかったときと、事実のイベントの列が一致することを確かめる
評価ケース世界観の逸脱、事実と発話の分離VISION 16章の意地悪なケースを、本物の LLM と LLM 判定で回す。費用がかかるので、CI では回さず、手動で回す
  • 台本の LLM（ScriptedLlm）は、目的（Purpose）と、入力に含まれる文字列で応答を引く。当たらなければテストを失敗させる（黙って空を返さない）
  • 再起動のテストが通るのは、乱数がカウンタ方式で、台本の LLM が決定的だから。本物の LLM では一致しない（再決定で違う結果になる）が、それは仕様どおり
決定 P-50　テストの層 上の6層。最初に作るのは、Apply の単体と、シナリオと、不変条件。再起動のテストは、永続化を作った段階で足す。

7.5デーモンと CLI

作る順番（VISION 1章）の「最小の CLI」。エンジンを動かし続けるデーモンと、それと話す CLI に分ける。実装中に、動いているものを外から見たり触ったりしながらデバッグできるようにするため。コアの外の話で、コアの公開 API（D4 4.6）だけを使う。

コマンドすることデーモン
vivace daemonエンジンを実時間で動かし続け、ローカルの管理用 API を開く。常駐のさせ方は systemd や Docker に任せる（自分でバックグラウンドに回らない）。--watch を付けると、定義のフォルダを監視して読み直す（P-09）本体
vivace statusエンジンの状態（動いている / 止まっている）と、各ペルソナのいまの居場所、行動、状態変数を出す使う
vivace events tail適用されたイベントを、流れてくるそばから出す（動いている様子を見る）使う
vivace events show <seq>イベントの中身と痕跡を出す使う
vivace events reject <seq> / vivace resume止まったエンジンで、問題のイベントを却下にして、再開する（P-49）使う
vivace inject <file.toml>投入 API にイベントを出す（出来事の注入など）使う
vivace reload定義を読み直す（P-09）使う
vivace probe <persona> <語...>話題の注入（VISION 16章）使う
vivace report実行レポートを出す使う
vivace validate <dir>定義を検証して、エラーと警告を出す使わない
vivace dry-run <dir> --days 3自分でエンジンをもう1つ立てて早送りで回し、実行レポートを出す。動いているデーモンには触らない使わない

vivace dry-run の行動表（J-163、J-164）：保存先の記録（適用されたものだけ）から作る。日はワールドの現地の日付で区切り、その中で人を ID の序数順に並べる。行は開始の順で、形は 07:00-07:30 [予定] eat_breakfast @kaori_room（行動）と 08:10-08:25 移動 kaori_room → school（移動）。理由の表記は、予定、自由、反射、遅刻。末尾に、適用、捨てた、却下の件数を出す。定義にエラーがあれば、validate と同じ問題の出力で、回さずに 1 で終わる。既定の開始とシードは Scenario と同じ値を使い、ワールドは全部同じシードで回す（J-163）。祝日は既定で祝日なしで回し、提供元を用意できないワールドは、行動表の前に「ワールド: 祝日のカレンダー 名前 は未対応のため、祝日なしで回した」の1行で知らせる（J-165）。

  • 管理用 API は、ASP.NET Core の Minimal API で書く。.NET に同梱の共有フレームワークなので、パッケージは足さない。ルーター、JSON、イベントの流れ（.NET 10 の Server-Sent Events）が、そのまま使える
  • 待ち受けるのは、Unix ソケットか localhost だけ。管理用で、外には開かない。認証はまだ持たない
  • VISION 1章の API 層（フロントエンドと一緒に作る）は、この API を広げて作る。そのときに、認証と外向けの公開を足す
決定 P-54　CLI は、デーモンとローカルの管理用 API で話す 上のとおり。レビューで決めた。vivace run（1回だけ動かす形）は、vivace daemon に置き換える。
