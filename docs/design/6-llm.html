6.1モデルの段

Main

ペルソナの声で書くもの、判断の質が結果に直結するもの。Planner、返信と投稿の文面、場所の生成、記憶の抽出。

Light

短い分類と変換。受信箱の振り分け、話題の抽出、世界観の判定（VISION 11章「軽量モデルで判定」）、記憶の照合、gist、threads の更新。

決定 P-42　モデルは Main と Light の2段 コアは段だけを指定し、段から実際のモデルへの対応は LLM の実装の設定に持つ（D4 4.4）。段を目的ごとに上書きするときは、コアの目的ごとの取り決め（LlmPolicy、D4 4.4）に書く（post.judge を Main にする、など）。

6.2呼び出しの一覧

「目的」は、LLM の呼び出しに付ける名前（LlmRequest.Purpose、D4 4.4）。LLM には見せない。使うのは、痕跡と計測（目的ごとの回数とトークン数。D7 7.3）、目的ごとの再試行と管理者への通知（D7 7.1）、段の上書き（6.1）、テストの台本の LLM が応答を引くとき（D7 7.4）。目的は登録制で、下の表の目的は、表の段を既定としてコアが最初から登録する。新しい種類の呼び出しを足すときは、目的を登録する（D4 P-53）。

  • 呼び出しごとに、目的、モデル、トークン数、所要時間を、出力のイベントの痕跡に残す

6.3文脈の組み立て

ContextBuilder が、目的に応じて次の部品を並べる。部品の中身は、ハーネスが事実として渡すもので、LLM はそれを書き換えない（VISION 12章）。

ワールドワールドの lore と、存在しないものの一覧すべて
いま現地の日時、曜日、祝日・年中行事、いる場所、している行動すべて

  • ユーザー、記憶のアイテム、threads は、ラベル（U1 / M1 / T1）で見せる（VISION 13章）。ラベルと本当の ID の対応は、呼び出しごとに作り、出力を読むときに戻す
  • 日誌は、ログから、そのペルソナの適用済みの travel.* action.* block.responded incident.* を引き、1行1件で「10:20 早退した（理由：気力の枯渇）」のように整形する。予定にあったのにしなかったことは、プランと突き合わせて「予定：授業 → 実際：…」と並べる
  • 日誌には、居合わせの変化も入れる。自分が着いたときにその場にいた人（「10:15 公園に着いた（詩織も来ていた）」）と、自分がいる場所に人が来たり去ったりしたとき（「10:40 香織が来た」）。どちらも、ログの移動のイベントから導く（保存はしない。居合わせは居場所から導くもの。VISION 14章）
  • 同行と居合わせは、文言で書き分ける。同行は「詩織と一緒に昼食（約束していた）」、居合わせは「詩織も来ていた」。LLM への指示にも、「『一緒に』と書かれていないものは、同じ場所にいただけ」と一行入れる。居合わせを「一緒に遊んだ」のように膨らませても、それは「言ったこと」にとどまり、事実は変わらない（VISION 12章）

6.4記憶の選び方

  1. 読めるアイテムだけに絞る。public と、いまの会話の相手との dm（VISION 13章）。置き換えられた（supersededBy がある）ものは除く。会話の相手以外との会話で、shareable でないものは除く
  2. 関連の度合いを、主題（subjects）とタグの一致で数える。会話の相手が主題に入っていれば大きく足し、話題の語がタグに当たれば足す
  3. 揮発スコア（6.7）× (1 + 関連の度合い) の上位 12 件を入れる。継続中の threads は、読めるものを全部入れる（数が少ないので）
決定 P-43　記憶の検索に、埋め込み（ベクトル）を使わない ebise と同じく、タグと主題の一致で選ぶ。ペルソナあたりの記憶は数百〜数千件にとどまり、タグ（言い換えを含む名詞）を抽出時に付けておけば足りる見込み。足りなくなったら、memory_items に埋め込みの列を足して、関連の度合いの計算だけを差し替える。

6.5受信箱を捌く

  1. 「スマホを開く」の開始の時点の受信箱から、未処理の通知を、元の到着時刻の古い順に最大 20 件取る
  2. 大分類（D3 3.7.1）ごとに捌く。
    • Message：ConversationKey が同じものは1つの会話にまとめる。会話ごとに inbox.triage に渡し、返信 / リアクション / 何もしない を決める。同じ会話に何通も来ていれば、返信は最後の1通にまとめて1回だけ
    • Reaction：LLM を使わない。見たものとして処理済みにする。誰がどの発言に反応したかは、記憶の整理の材料になる
    • Follow：LLM を使わない。フォローバックの方針（P-44）に従って、フォローし返すか決める。フォローできるチャンネル（能力 follow）だけが対象
    • Other：プラグインの規則（INotificationRule、D4 4.7）に当たれば、規則で捌く。当たらなければ、何もせずに処理済みにする。規則が出せるのは発話ではない操作だけ
  3. 返信するものは、会話ごとに inbox.reply で本文を作る。文脈には、本文、添付、それまでの会話（Thread）を入れる（6.3）。相手が持ち込んだ話題が世界観に合わなければ、「知らない」と答える（VISION 11章）。そのための判定は、投稿と同じ辞書と post.judge を使い、却下なら「知らない」と答えるよう指示する。作った本文は、送る前に校閲を通す（6.10）
  4. 出力を、行動の終了の時刻で返す。出力は、同じ時刻の action.ended より先に取り込まれ（D1 1.4）、action.ended は版を上げないので（D2 2.3、J-131）、guard の行動の版が通る。outbound.speech（返信）、outbound.operation（リアクション、フォロー）、inbox.handled（まとめて捌いた通知も、それぞれ処理済みにする）
決定 P-44　フォローバックの方針の持ち方 VISION 付録「フォローバックの方針の持ち方」への案。フォローはコアが捌くので（D3 3.7.1）、方針もコアが読む。ペルソナ定義の [sns] の節に書き、フォローできるチャンネルすべてに効く。 
[sns]
follow_back = "always"           # always | never
既定は always（ebise は、フォローされたら必ずフォローし返していた）。チャンネルごとに変えたくなったら、そのときに上書きの書き方を足す。

6.6投稿する

  • 話題の候補は最大 5 件。辞書に当たったものと、判定で通ったものの中から、乱数（用途 sns）で1つ選ぶ
  • 全部却下なら自分の話題（日誌の今日のこと、好み）に切り替え、それも作れなければ post.skipped
  • 作った本文は、投稿する前に校閲を通す（6.10）。通らなければ post.skipped（理由は校閲）
  • 辞書の食い違いで却下されたら（D1 1.7）、文面の作り直しのハンドラが、辞書の変換を使って文面だけを作り直す。判定と場所の生成はやり直さない（VISION 11章）
決定 P-45　空振りのクールダウン VISION 付録「空振りのクールダウンの細部」への案。空振りのあと 30 分は、「投稿する」を候補にしない。通常の投稿のクールダウン（チャンネルの頻度制限）より短くし、話題がなかったときに、しばらくして TL を見直す形にする。

新しい場所のつなぎ方

  1. post.place に、場所の候補の語、ワールドの lore、既存の場所の一覧（ID、名前、タグ、group）、既存の辺の例（10 本ほど）、タグの語彙（行動の requires に出てくるタグの和集合）を渡す
  2. 出力は、名前、タグ（語彙から選ぶ）、つながる場所（既存の ID、1〜3 本）と移動時間（分）、group
  3. ハーネスが検査する。つながる先が実在し、閉鎖されていないこと。移動時間が 1〜120 分であること。タグが語彙にあること（ないものは捨てる）。名前が既存の場所と重ならないこと。ID はハーネスが gen_ + 連番で振る
  4. 違反があれば、理由を添えて1回だけ作り直させる。だめなら、その話題を却下する
決定 P-46　新しい場所のつなぎ方の細部 上のとおり（VISION 付録）。移動時間の上下限は 1〜120 分。生えた場所の ID は LLM に作らせず、ハーネスが振る。

6.7記憶の整理

ebise の夜間ジョブ（層ごとの抽出 → 照合 → gist → 反映、threads の更新、層ごとのカーソル）を、Vivace のイベントログの上に移す。

範囲と入力

  • 上限は、整理を起こした行動（睡眠、気絶）の開始イベントの適用番号（VISION 13章）。下限は、層ごとのカーソル
  • 入力は、範囲の中のそのペルソナのイベントのうち、事実（行動、移動、出来事、予定の乱れ）、到着した通知の本文、言ったこと（発話）
  • 層への振り分けは audience で行う。事実は public。通知と発話は、チャンネルが付けた audience。記憶にしない audience のもの（相手が2人以上、など）は、どの層にも入れない
  • 事実を public の層に入れられるのは、事実のイベントが dm の中身を運ばないから（VISION 13章）。これが崩れると、dm の中身が public の記憶に漏れる。そのため、dm の会話（受信箱の返信と、その文脈）からは、事実のイベントを生まない。予定への書き込みも、行動の開始もしない。dm の中身が記憶に入る道は、dm の audience の通知と発話だけになる
  • 入力が大きいとき（追いつきのあとなど）は、1回の LLM 呼び出しに入る量（目安 3 万トークン）ごとに区切って、古い順に処理する。区切りごとに反映し、カーソルを進める

アイテムと揮発スコア

アイテムの形は ebise を引き継ぐ（種類 fact / episode、主題、本文、gist、audience、shareable、importance 1〜5、タグ、強化の回数、置き換え先、出所）。出所は、イベントの連番の列で持つ（D3）。

揮発スコア = importance × 0.5 ^ (最後の強化からの経過日数 / 実効半減期)
実効半減期 = 基準半減期(種類) × ペルソナの half_life × min(1 + 0.5 × 強化の回数, 4)
基準半減期 = fact 180 日、episode 14 日（threads は 7 日）

経過日数は、世界の時刻で数える（now を引数に取る。VISION 13章）。置き換え（supersede）は、古いアイテムに supersededBy を付けて新しいアイテムを足す。

shareable は、抽出（memory.extract）で LLM が付ける。基準は ebise と同じで、本人が隠さずに話していて、ほかの人に伝わっても困らないものは true、悩み、健康、人間関係、お金のことなどは false。ハーネスは、狭める方向にしか変えない。置き換えのときは、新しい判定と、置き換えられるアイテムすべての値の論理積にする。dm の中身は、shareable ではなく audience の層で守る（6.4）。shareable が守るのは、public の層の中で、本人がほかの人に話されたくないことだけ。

決定 P-47　記憶力の調整方式 VISION 付録「記憶力の調整方式」への案。ペルソナ定義の memory.half_life（既定 1.0）を、種類ごとの基準半減期に掛ける。ebise の式（強化で最大 4 倍まで延びる）は、そのまま使う。
決定 P-48　層とカーソル 層は audience ごと（public と、dm の相手ごと）。カーソルは memory_cursors に、層ごとの適用番号で持つ。threads のカーソルは別に持つ。新しい dm の相手が現れたら、その層のカーソルは、そのペルソナの生成の時点から始める。

失敗と通知

  • 層の処理が失敗したら、その層のカーソルを進めず、次の整理でまとめて処理する（VISION 13章）
  • 同じ層が 3 回続けて失敗したら、IAdminNotifier で管理者に知らせる（ebise の「記憶化に失敗したときの、管理者への通知」）
  • 整理ジョブは、ペルソナごとに同時に1つだけ動かす。前の整理が終わらないうちに次の睡眠が来たら、前のが終わってから、新しい上限で続ける
  • 整理が終わったら（すべての層の反映と threads の更新のあと）、それを待っている Planner に知らせる（D5 5.5）。失敗した層があっても、終わったことにして知らせる（未処理の分は次に持ち越すだけなので）

6.8記憶の汚染を防ぐ

記憶は、以後の文脈に何度も入るので、指示文が紛れ込むと、ずっと効き続ける。ebise の簡易フィルタを引き継ぐ。

  • 本文が長すぎる（400 字超）、改行を含む、指示文らしい語（[system]、ignore previous instructions など）を含む候補は、反映しない
  • 弾いた候補は、ログに残す（実行レポートで見られるように）
  • 文脈に入れるときは、記憶の本文を、ユーザーの発言と同じ「引用」の扱いにし、システムの指示の位置には置かない

6.9呼び出しの量の目安

契機1日の回数（1人）1回の呼び出し1日の呼び出し
Planner1（睡眠ごと）1〜31〜3
スマホを開く8〜15振り分け 1 + 返信の数 ×（文面 + 校閲。書き直しで最大 3 回）20〜60
投稿する4〜8抽出 1 + 判定 0〜3 + 場所 0〜1 +（文面 + 校閲。書き直しで最大 3 回）15〜50

1人あたり1日 40〜130 回、10 人で 400〜1300 回（校閲は Light なので、費用の増え方は回数ほどではない）。辞書が育つと判定の回数は減る。実際のトークン数と費用は、痕跡の記録から実行レポートで集計する（D7）。

6.10文面の校閲

投稿と返信の本文は、送る前に、作った呼び出しとは別の呼び出しで校閲する。ebise の投稿の校閲（post-review）を引き継ぎ、返信にも使う。作る呼び出しの中で推敲させると、考え事がそのまま本文に漏れるので、役目を分ける。

1. 下書き

post.compose / inbox.reply（Main）。前に却下されていれば、その理由を添える

→
2. 校閲

post.review / inbox.review（Light）。問題を見つけるだけで、書き直さない

→
3. 通す / やり直す

通れば出力にする。却下なら 1 に戻る。下書きは最大 3 回まで

見る観点

観点中身
本文以外の混入考え事、推敲のメモ、制約の確認、複数案の比較、自分への指示が混ざっていないか。段落が分かれている下書きは、LLM に頼らず、ハーネスが先に却下する（ebise と同じ）
矛盾文脈（日誌、今日の予定、記憶、言ったこと）の事実と食い違っていないか。終わった予定をこれからのことのように話す、同じ場所にいただけの人と「一緒に」何かしたことにする（6.3 の書き分け）、など
繰り返し直近の発話と同じ話題を、進展も別の切り口もなく、もう一度述べていないか
世界観ワールドにないもの（存在しないものの一覧、辞書で却下された語）を、本文で新しく持ち込んでいないか（VISION 11章）。話題の判定を通った語や、既存の場所は問題にしない
  • 口調、語尾、口癖、面白さ、上手さは見ない。キャラクターの個性で、好みの問題だから（ebise と同じ）
  • 校閲の入力は、下書きと、下書きを作ったときと同じ文脈（ペルソナの lore は除く）。返信なら、それまでの会話（Thread）も入れる
  • 校閲の応答が読めなかったときは、確かめられないものを通さないよう、却下として扱う
  • 3 回とも通らなければ、送らない。投稿なら空振り（post.skipped、理由は校閲）。返信なら、その会話は「返信を見送った」として処理済みにする（受信箱に残すと、次にスマホを開いたときに、また同じことを繰り返すため）
  • 下書きと校閲の結果は、すべて痕跡に残す。実行レポートで、どんな理由で却下されがちかを見られる
決定 P-57　投稿と返信の文面は、別の呼び出しで校閲してから送る 上のとおり。レビューで決めた。発話は事実にならない（VISION 12章）が、事実や過去の発話と食い違う発話が続くと、ペルソナが嘘つきに見え、同じワールドのほかのペルソナとも話が合わなくなる。校閲は、その食い違いを送る前に減らす。
