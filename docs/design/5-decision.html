5.1Decider の流れ

1. 候補を並べる

使える行動 × 行ける場所。requires と制限で外す

→
2. 所要時間を引く

候補ごとに乱数で決める。決まった値で、帰還できるかを判定する

→
3. 重みで抽選する

状態変数、好み、繰り返し、移動の手間で重みをつけ、1つ引く

Decider は同期の純粋な関数として書く。入力は写しと now と乱数の列、出力は activity.chosen 1件（D2 2.3）。候補とスコアの上位 10 件は、痕跡に残す。

5.2候補の作り方

  1. 行動：ペルソナの use に当たる行動から、forbid に当たる行動を外す。forbid は2か所にある。ペルソナ定義の prefs（その人がしないこと）と、いま付いている状態（風邪のときは外に出ない、など。D2 2.7）
  2. 場所：ワールドの場所（定義の場所 + 採用済みの生えた場所）から、閉鎖中のものを外す。場所を固定するブロックの中なら、その場所だけ
  3. requires：場所のタグ、携行品、チャンネル（つながっていて、圏外でない）を満たす組だけ残す
  4. 制限：クールダウン、1日の回数、時刻の範囲（開始時刻で判定）。投稿は、チャンネルの頻度制限と空振りのクールダウンも重ねる
  5. 所要時間：残った組ごとに、行動 ID と場所 ID の順に並べてから乱数で引く（並びを固定して、結果を再現できるようにする）
  6. 帰還できるか：VISION 5章の式で、次のブロックの開始に間に合うものだけ残す。次のブロックは、プランの中で次に来る固定か計画のブロック。なければ、プランの終わり（翌日の 3:00）
  7. 次の予定の場所へ向かう：core.go_to_next を必ず足す。これで候補は空にならない（VISION 5章）。だから core.go_to_next は forbid の対象にしない。ペルソナ定義で外そうとしたら読み込みのエラー（D7 7.2）にし、付いている状態の forbid に当たっても無視する（状態の forbid は行動タグでも書けて、何に当たるかを前もって全部は確かめられないため）
案 P-29　所要時間の引き方 範囲 [min, max] から、5 分刻みの一様分布で引く。固定の長さなら引かない（乱数を消費しない）。帰還の判定で落ちた候補は、短い値で引き直さない（候補が減るだけで、go_to_next が残るから）。

5.3スコアの式

重みは、要素の積にする。どれか1つが 0 なら選ばれない。

w(a, p) = base(a) × pref(a) × cond(a) × need(a, p) × repeat(a) × travel(p)

need(a, p) = exp( β × Σ_v  u_v × g_v(a, p) )
  u_v   = 切実さ = ( |x_v − 目標_v| / 幅_v )²         いまの値が目標から遠いほど大きい
  g_v   = 良くなる量 = ( |x_v − 目標_v| − |x'_v − 目標_v| ) / 幅_v
  x'_v  = その行動を終えたときの予測値（移動 + 行動の率と、終了時の増減で計算する）

repeat(a)  = 0.7 ^ (直前に同じ行動を続けた回数)
travel(p)  = exp( −移動時間（分） / 30 )
変数目標幅意味
気力100100減っているほど、回復する行動が選ばれやすい
健康度100100下がっているほど、休む行動が選ばれやすい
退屈度0100高いほど、退屈を下げる行動が選ばれやすい
社交欲求0100正なら人と会う行動、負なら一人の行動が選ばれやすい（VISION 6章）。予測値は、行き先にいまいる人の数で、一人の率か同席の率かを選んで計算する
要素決め方
base行動定義の weight（既定 1.0）
prefペルソナの prefs。like = 2.0、dislike = 0.4、forbid = 候補から外す、数値ならその値。数値の 0 は forbid の別名で、同じく候補から外す（重み 0 で残すと、選ばれないのに所要時間の乱数を引いてしまうため）。行動 ID と tag:（行動タグ）の両方に当たれば、積をとる
cond付いている状態の weight の積（D2 2.7）
β状態変数の効き目。既定 3.0。大きいほど、欲求に素直になる

抽選は、重みの合計 W に対して r = NextDouble() × W を引き、候補を ID の順に並べた累積で選ぶ。

need の読み方

  • 切実さ u：いまの値が、目標からどれだけ遠いか。2乗するので、少し離れているだけならほぼ 0 で、大きく離れると急に効く。気力 90 なら 0.01、気力 30 なら 0.49
  • 良くなる量 g：その行動を終えたとき、目標にどれだけ近づくか。遠ざかるなら負になる。移動の分も含めて、状態変数の率と効果から計算する（行動定義に「この行動は疲れが取れる」のような印は書かない）
  • u × g の合計：切実な変数を良くする行動ほど大きく、切実な変数を悪くする行動ほど小さい。切実でない変数は、どう動いても効かない
  • exp(β × …)：合計を、掛け算できる正の倍率に直す。合計が 0 なら 1 倍（欲求は関係なし）、正なら 1 倍より大きく、負なら小さい。β はその効き目の強さ

計算の例

14:00 の自由時間。気力 30、退屈度 70（社交欲求 0、健康度 100 は切実さ 0 なので効かない）。気力と退屈度の切実さは、どちらも (70 / 100)² = 0.49。候補が3つあるとする。

候補終えたときの予測g（気力、退屈度）needほかの要素重み選ばれる確率
家で昼寝（60 分。気力 +20/時）気力 50、退屈度 73+0.20、−0.03exp(3 × 0.083) = 1.28なし1.2826%
公園を散歩（移動 15 分 + 45 分。終了時に退屈度 −25）気力 24.5、退屈度 48−0.055、+0.22exp(3 × 0.081) = 1.27移動 exp(−15/30) = 0.610.7716%
家でゲーム（60 分。終了時に退屈度 −30）気力 26、退屈度 43−0.04、+0.27exp(3 × 0.113) = 1.40好き（like）× 2.02.8058%

気力が 10 まで下がると、気力の切実さが 0.81 になり、昼寝の need は 1.56 に上がる（確率は 31%）。β = 3 では、欲求は「好き」の 2 倍ほどは効かない柔らかい傾向にとどまる。疲れ切ったら休むのを確実にするのは反射の役目（5.7）で、Decider はそこまでの傾きをつけるだけ（VISION 5章）。傾きが弱すぎると感じたら、β を上げる。

案 P-30　Utility AI のスコアの式と、補正の語彙 VISION 付録「Utility AI のスコアの式と、補正の語彙」への案。状態変数ごとの「良くなる量」を行動の効果から自動で予測するので、行動定義に「この行動は退屈に効く」のような印を別に書かなくてよい。補正の語彙は、like / dislike / forbid / 数値の4つと、行動タグ（tag:）による一括指定。

行動定義に tags を足す（D3 3.6）。好み（「運動が嫌い」）と状態（「風邪のときは外に出ない」）を、行動を1つずつ挙げずに書くため。

5.4特別な決めどき

予定の乱れへの対応（遅刻・欠席・待つ）

  • 遅刻：迂回してでもブロックの場所に着けて、着いた時刻がブロックの終わりより前なら候補になる
  • 待つ：満たせない原因（閉鎖など）の解消の時刻がわかっていて、それがブロックの終わりより前なら候補になる
  • 欠席：いつでも候補になる。欠席したブロックの残りは、自由時間として Decider が決める
  • 重みは、ペルソナの disruption（D3 3.4）。既定は 遅刻 1.0、欠席 0.3、待つ 0.5。遅刻の重みには、遅れる時間に応じて exp(−遅れ（分）/ 60) を掛ける（大遅刻なら休みやすい）
案 P-31　遅刻・欠席・待つの重み 上のとおり。VISION の「ペルソナの性質に応じた重み」を、ペルソナ定義の3つの数値で表す。

スマホを開く機会

  • 候補は「スマホを開く」と「何もしない」の2つ（VISION 10章）。開く重みは、スマホを開く行動の base × pref に、1 + 0.5 × min(未読の数, 4) を掛ける（通知のバッジに気づく）。何もしないは 1.0
  • 開いたら、ブロックの行動はそのままにして、副行動（Overlay、D3 3.7）として短く実行する。所要時間は、行動定義の範囲から引く
案 P-32　長いブロックの途中の「スマホを開く機会」 VISION 付録への案。既定では、ブロックの開始時に1回だけ。固定予定のブロックに phone_every = "90m" を書いたときだけ、その間隔で機会を出す（3時間のバイトの休憩など）。間隔は、ペルソナの書き手が決めるもので、コアの既定値は持たない。
案 P-33　ブロックの interruptible は持たない VISION 付録「予定ブロックの interruptible が要るか」への案。行動の中断は、反射と出来事が担う。スマホを開けるかは phone（availability）で足りるので、interruptible は作らない。

5.5Planner

入力と出力

  • 入力（LLM に渡すもの）は D6。日付、曜日、祝日と年中行事、その日の固定ブロック、使える行動と場所の ID つきの一覧、発生済みの出来事、日誌と記憶の要約（public のものだけ。VISION 13章）
  • 出力は、固定ブロックの隙間を埋める計画ブロックの列。各ブロックは「開始、終了、行動 ID、場所 ID」か「開始、終了、自由時間」。ほかに、その日の一言の要約（文脈に使う）
  • 範囲は 3:00 から翌日の 3:00。睡眠の固定ブロックがない日は、睡眠のブロックを1つ置かせる（VISION 5章「睡眠の細部を埋める」）

検査と補正

検査違反したとき
時刻の形式、範囲の内か範囲の外を切り落とす
固定ブロックと重ならないか重なった分を切り落とす（固定予定を優先）
行動と場所の ID があり、そのペルソナが使えるかそのブロックを自由時間に置き換える
requires（場所のタグ、携行品）を満たすか自由時間に置き換える
前のブロックの場所から、移動時間を空けて着けるかブロックの開始を移動時間の分だけ遅らせ、間を移動にあてる（移動ブロックの自動挿入）
切り詰めたあとの長さが、行動の最短の所要時間以上か自由時間に置き換える
全体：置き換えたブロックが半分を超えた、または出力が読めない理由を添えて再生成する（2回まで）。それでも駄目なら、固定予定だけのプラン

汎用の行動への置換（VISION 5章）は、「自由時間にして Decider に任せる」で表す。自由時間なら、Decider が必ず実行できる行動を選ぶから。

3:00 の継ぎ目

プランは「3:00 から翌日の 3:00」の範囲を持つ。新しいプランを適用したとき、3:00 をまたいで続いているブロック（日をまたぐ睡眠など）は、同じブロック ID（sleep_weekday@2026-11-02）なので、積み直さずにそのまま続ける。

案 P-34　前日のプランがないとき VISION 付録「前日のプランがないときの、0:00〜3:00 の過ごし方と Planner のホライズン」への案。召喚した日は Planner を呼ばず、召喚した時刻から翌日の 3:00 までを、固定予定と Decider だけで過ごす（追いつきの過去の日と同じ扱い）。翌日の 0:00 の日の始まりから、通常の Planner が動く。召喚の直後に Planner を急いで回すより、仕組みが1つで済む。

5.6状態変数

VISION 6章のとおり、各変数は「基準時刻での値」と「いまの率」を持ち、値 + 率 × 経過時間で読む。率が変わるのは、行動の開始と終了、居合わせの変化、状態の付け外しのときだけ。

変数範囲初期値既定の率（1時間あたり）しきい値と反射
気力0〜10080起きている間 −4。睡眠中 0。行動が率を書けばそれを使う0 で気絶（core.faint）
健康度0〜100100+0.2（ゆっくり戻る）。状態（風邪など）の率を足す20 で早退して休む（core.go_home_rest）
退屈度0〜10030+3。行動が率を書けばそれを使うなし
社交欲求下限〜上限（既定 −50〜100。どちらもペルソナ定義で変えられる）0一人のとき +2、同席のとき −3なし
  • クランプ：読んだ値は範囲で切る。範囲の端に着いたら、基準を端の値と到達の時刻に置き直す（その先の率は効かない）
  • 到達の予測：率がしきい値に向かうときだけ、t = 基準時刻 + (しきい値 − 値) / 率 を計算し、ミリ秒に切り上げて vital.threshold を積む。すでにしきい値の向こうにいるときは積まない（越えた瞬間にだけ反射する）
  • 決定性：Apply の計算は、四則演算と比較だけで書く。Math.Pow や Math.Exp は、CPU によって結果の末尾がずれうるので、Apply では使わない（repeat_decay の累乗は、掛け算の繰り返しで書く）。Decider の exp は決める側なので使ってよい（結果はイベントに記録される）
  • 居合わせ：travel.started と travel.arrived の Apply で、出た場所と着いた場所にいる全員の社交欲求の率を計算し直す。率が変わった人は、状態変数の版が上がる

寝不足

効果に sleep.debt を持つ行動（睡眠）が終わったとき、実際に眠った長さを、ペルソナの sleep_target（既定 7 時間）と比べる。

足りない時間 h = max(0, sleep_target − 眠った長さ)
h > 0 なら  健康度 −= min(4 × h, 20)
h = 0 なら  健康度 += 5
案 P-35　状態変数の式の形、範囲、数値 上の表と規則（VISION 付録「状態変数の式の形、範囲、数値」）。気力は、16 時間起きていると 64 減る。行動の消費を足すと、夜には 10〜30 まで下がり、睡眠で満タンに戻る、という1日の形を狙った値。
案 P-36　寝不足での健康度の下がり方 上の式（VISION 付録「寝不足での健康度の下がり方」）。睡眠の行動の効果（sleep.debt）に持たせる案を採る。気絶は寝不足の判定をしない（debt = false）。

5.7反射

  • vital.threshold の Apply が、実行中の行動（と副行動）を打ち切り、行動の版を上げ、反射の行動を action.started（理由 reflex）で同じ時刻に積む。Decider は通らない
  • 反射の行動は、所要時間が固定のもの。core.faint は 2 時間、core.go_home_rest は家までの移動と、3 時間の休息
  • 固定ブロックの途中で反射が起きたら、そのブロックの残りは欠席として記録する。反射の行動が終わった時点で、まだ同じブロックの中なら、残りは自由時間として Decider が決める
  • しきい値は、ペルソナの reflexes と、付いている状態の threshold で上書きできる（D2 2.7）

5.8出来事の抽選

  1. 日の始まりに、ワールドレーンで動く。ワールド向けの出来事はワールドの乱数の列、ペルソナ向けの出来事はペルソナごとの列で引く
  2. 出来事の定義ごとに、再発までの間隔（前回の発生から）と、曜日などの条件を確かめ、chance で発生を引く
  3. 発生するものは、時刻（hours の範囲から1分刻みで一様に）、対象（place_tag なら候補から一様に）、持続時間を引く
  4. 結果を incident.occurred のまとまりとして、時刻つきで返す。ホライズンは 0:00 なので、抽選が返るまで、その日の適用は始まらない（LLM を使わないので一瞬）
案 P-37　出来事の頻度の既定値 VISION 付録「出来事の効果の語彙と、頻度の既定値」の頻度の側。chance は定義ごとに必ず書かせ、既定値は持たない。そのうえで、1つのワールドで1日に起きる出来事は、ワールド向けとペルソナ向けを合わせて 2 件まで（超えた分は、抽選の順で後のものを捨てる）。組み込みの出来事は、道路工事（0.03）、店の臨時休業（0.02）、風邪（0.01）の3つから始める。

5.9乱数

シード  s = SHA-256( UTF-8("{ワールドの種}:{持ち主}:{用途}") ) の先頭 8 バイト
i 番目の値 = SplitMix64 の混ぜ関数( s + (i + 1) × 0x9E3779B97F4A7C15 )

NextDouble = (値 >> 11) × 2^−53
NextInt    = 乗算と棄却による偏りのない方法（Lemire）
持ち主用途使うところ
ペルソナ IDdecideDecider、予定の乱れ、スマホを開く機会
ペルソナ IDincidentペルソナ向けの出来事の抽選

  • SplitMix64 は、i 番目の値を i から直接計算できる（カウンタ方式）。だから、保存するのは「引いた回数」だけでよい（VISION 4章「引いた回数のカウンタを、状態として保存する」とそのまま合う）。状態の中では、用途ごとの位置を Rng に持つ（D3 3.7）
  • 決める側は、写しの位置から引き始め、出力に「どの列の、どこからどこまで引いたか」を記録する。Apply は、位置が同じことを guard で確かめてから進める（D1 1.7）
  • string.GetHashCode() と System.Random は使わない（VISION 4章）。SHA-256 と SplitMix64 は、どの環境でも同じ値になる
案 P-38　乱数は SplitMix64 のカウンタ方式 上のとおり。品質はシミュレーションの抽選には十分で、実装は 20 行ほどで済む。xoshiro のような状態を持つ方式だと、位置を復元するのに状態ごと保存するか、回数ぶん空回しする必要がある。

ほかの候補：PCG（状態を持つが、任意の位置へ対数時間で飛べるので、カウンタから復元できる。品質の評判もよい）、Philox（カウンタ方式で、並列向けに作られた。実装が重い）、xoshiro256**（速いが、状態を持つ。変種によっては統計的な検定に落ちるという報告がある）、SHA-256 にシードと回数を通す（いちばん素朴。遅いが、この規模なら足りる）。カウンタをそのまま位置として保存できて、いちばん短く書けるので、SplitMix64 にした。品質が問題になったら、同じ「シードと位置」の形のまま Philox に替えられる（IRandomSource の差し替え）。

5.10最短経路と移動

  • 場所の数は数十〜百程度なので、全点対の最短経路を Floyd–Warshall で求め、経路の復元用の表と一緒に持つ。作り直すのは、グラフの版（GraphVersion）か定義が変わったとき
  • 閉鎖中の場所は、行き先にも経路の途中にもしない。slow_place は、その場所につながる辺の時間を変えた表で計算する
  • 移動の経路は、出発時に辺の列として確定させ、travel.started に記録する。途中で辺が伸びたら、いまどの辺の上にいるかを出発時刻と各辺の時間から計算し、残りの時間を新しい値で積み直す
案 P-39　移動中の居場所 移動中のペルソナは、どの場所にもいないものとして扱う（出発した時点で元の場所から消え、到着した時点で着いた場所に現れる）。途中で通る場所（道など）での居合わせは数えない。居合わせの判定が、出発と到着の2回だけで済む。

5.11同行

  • 同行は、両方の固定予定に、同じ時刻・場所・行動で with を書いたときだけ成立する（VISION 14章）。片方にしか書いていなければ、読み込み時に警告し、同行として扱わない
  • 実行時は、それぞれが自分のブロックとして、自分のレーンで動く。2人分をまとめて決める処理は作らない
  • 片方が欠席・早退・反射で抜けたとき、もう片方の扱いは、ブロックの on_partner_absent で決める。continue（既定）はそのまま続ける。cancel は、相手が抜けたイベントの Apply が、こちらのブロックを終わらせて、自由時間の決めどきを積む
案 P-40　同行で片方が欠席したときの扱い 上のとおり（VISION 付録「同行で片方が欠席したときの扱い」）。予定ごとに continue / cancel を選べる。
案 P-41　2人のレーンをまたぐ決定は作らない VISION 付録「同行・共同行動で、2人のレーンをまたぐ決定の扱い」への案。いまのコアの範囲では、同行は日の始まりの時点で両者の予定に確定しており、実行時の交渉が要らない。相手が抜けたときの影響は、Apply の決定的な後続（上の cancel）で表せる。誘う・応じるの交渉（FUTURE.html）を作るときに、改めて考える。
Vivace 詳細設計 D5。構想の正は VISION.html。「案」は、ユーザーの合意を待っている提案。「決定」は合意したもの。
