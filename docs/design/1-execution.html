1.1前提

項目前提
規模1ホストに 1〜2 ワールド、1ワールドあたり最大 5 人。ホスト全体で最大 10 人程度
プロセス1プロセス。SQLite のファイルは1つ。複数プロセスからの同時実行は扱わない
状態の大きさワールドとペルソナの状態は、全部メモリに載る（数 MB 以下）。イベントログと記憶だけが、時間とともに増える
LLM応答に数秒〜数十秒かかり、ときどき失敗する。同時に投げる数は、少なく絞る

この規模なら、状態を全部メモリに持ち、変わった分だけを SQLite に書く形で足りる。分散やシャーディングは考えない。

1.2全体の構成

  • エンジンは、1本のスレッドで動くアクター。外からのコマンド（投入、到着、送信結果、ハンドラの出力、定義の読み直し）と、時刻が来たイベントの適用を、1つずつ順に処理する。SQLite のイベント表と状態の表に書くのは、エンジンだけ
  • 決める側（Planner、Decider、効果のハンドラ、出来事の抽選）は、レーンの上で並列に動く。受け取るのは状態の写しと、契機のイベントの時刻（now）だけ
  • 配信役と記憶の整理は、エンジンからのシグナルで動く。配信役の結果はコマンドで戻り、記憶の整理はイベントの外の表にだけ書く
案 P-01　エンジンを唯一の書き手にする イベント表と状態の表への書き込みを、すべてエンジンのスレッドに集める。ほかのスレッドは、コマンドを System.Threading.Channels のキューに入れるだけにする。ロックの設計が要らなくなり、「状態はイベントの適用でのみ変わる」（VISION 1章）を、コードの構造で守れる。

代わりの案：イベント表への挿入を各スレッドから直接行い、SQLite のロックに任せる。書き手が増え、連番と適用番号の順序の保証が難しくなるので採らない。

1.3Apply の形

Apply は、状態とイベントと定義を受け取り、新しい状態を返す。それに加えて、そのイベントから決定的に導ける「後続のイベント」と、エンジンへの「シグナル」を返す。

ApplyResult Apply(SimState state, SimEvent ev, Definitions defs);

record ApplyResult(
    SimState State,                         // 新しい状態（不変オブジェクト）
    EventOutcome Outcome,                   // Applied / Skipped / Rejected と理由
    ImmutableArray<NewEvent> FollowUps,      // 後続のイベント（決定的）
    ImmutableArray<Signal> Signals);        // エンジンへの依頼（データ）

後続のイベント

ルールだけで決まる次のイベント。翌日の日の始まり、しきい値到達の予測、行動の終了、到着、決めどきなど。Apply と同じトランザクションでキューに入る。

シグナル

Apply が自分では行わない副作用の依頼。ハンドラの起動、配信、記憶の整理の起動、ハンドラの取り消し。エンジンがコミットのあとに実行する。データなので、Apply は決定的なまま。

案 P-02　Apply は後続のイベントとシグナルを返す VISION では「日の始まりを処理するときに、翌日の分を積む」「率が変わるたびに到達時刻を予測し直して積む」と書かれているが、それを誰が積むかは決まっていない。Apply の戻り値に含めることにする。これで「乱数も LLM も使わずに決まる次のイベント」は、すべて Apply の中に閉じ、単体テストで検査できる。

シグナルは、再起動したときに状態から復元できるものだけにする。メモリの上にしかない依頼は、落ちたら失われるから。

シグナル依頼の中身再起動したときの復元
StartHandler決めどきのハンドラを、レーンで起動する「処理中」の決めどきを探して、起動し直す
CancelHandler割り込みで不要になったハンドラを取り消す不要。古い出力は検査で弾かれる（1.7）
Deliver未送信の外向きの操作を、配信役に渡す未送信のものは、送らずに「送信不明」にする（VISION 10章）
Consolidate記憶の整理を起こす（範囲の上限の適用番号つき）起動時に、カーソルから現在までを1回まとめて整理する（VISION UC-1）
ChannelOnline圏外が明けたことをチャンネルに伝える追いつきの終わりに、毎回出す
案 P-03　割り込まれた行動のハンドラは取り消す 「投稿する」の文面を作っている途中に、反射で行動が打ち切られたら、そのハンドラはもう要らない。Apply が行動の版番号を上げるときに CancelHandler を出し、エンジンはそのハンドラを CancellationToken で止めて、ホライズンの待ちからも外す。止めきれずに出力が返ってきても、版番号の検査（1.7）で弾かれるので、取り消しは最適化にすぎない。

1.4エンジンの1歩

エンジンは、次の手順を繰り返す。

  1. コマンドを捌く。受付のキューにあるコマンドを、すべて処理する（ハンドラの出力の取り込み、到着や投入のイベントの挿入、送信結果の挿入、定義の差し替え）
  2. 次のイベントを見る。キューの先頭（時刻、段、連番の順で最小）を見る。なければ、コマンドが来るまで待つ
  3. ホライズンを確かめる。実行中のハンドラのホライズンのうち最小のものを壁とし、先頭の時刻が壁以上なら、締め切り（1.6）が来るか、出力が届くまで待つ
  4. 時刻を待つ。実時間運転なら、時計が先頭の時刻に達するまで待つ。待っている間にコマンドが来たら、1 に戻る（より早い時刻の到着が入るかもしれないから）
  5. 適用する。Apply を呼び、新しい状態、イベントの状態の更新、適用番号、後続のイベント、付随する表（受信箱、未送信の操作など）を、1つのトランザクションで書く
  6. シグナルを実行する。コミットのあとで、ハンドラの起動、配信、記憶の整理の起動を行い、購読者に適用済みのイベントを流す

キューは、SQLite の未適用のイベントを、メモリの優先度つきキュー（PriorityQueue）に写したもの。起動時に読み込み、以後はエンジンが両方を同時に更新する。読むのはメモリのほうだけ。

1.5ハンドラとレーン

決める側の処理を、ハンドラと呼ぶ。ハンドラは、シグナルで起動し、写しと now を受け取って、出力（新しいイベントの列）を返す。同じレーンのハンドラは順番に、違うレーンのハンドラは並列に動く。

ハンドラ契機レーンホライズンLLM
Decider決めどき（自由時間、行動の終了、中断、決め直し）決定契機の時刻使わない
予定の乱れへの対応（遅刻・欠席・待つ）ブロックの開始時の確認で、満たせないとき決定契機の時刻使わない
スマホを開く機会機会のイベント決定契機の時刻使わない
効果「受信箱を捌く」「スマホを開く」の開始決定行動の終了の時刻使う
効果「投稿する」「投稿する」の開始決定行動の終了の時刻使う
文面の作り直し辞書の食い違いで弾かれたとき（VISION 11章）決定契機の時刻使う
Planner日の始まり計画その日の 3:00使う
出来事の抽選日の始まりワールド契機の時刻（0:00）使わない
  • 決定レーンは、ペルソナの「いまの行動」に関わる決定を順に処理する。同じペルソナで、2つの行動の決定が同時に走ることはない
  • 計画レーンを分けるのは、Planner が LLM を数十秒待つ間も、Decider を止めないため。Planner の出力は 3:00 以降の予定だけなので、Decider の決定とぶつからない
  • 乱数は、用途ごとに別の列を使う（D5「乱数」）。レーンが違えば、引く列も違うので、並列に引いても結果は変わらない
案 P-04　レーンの分け方と LLM の同時実行数 レーンは「ペルソナごとに決定と計画の2本」と「ワールドごとに1本」。LLM の呼び出しは、ホスト全体で同時に 3 本までに絞る（SemaphoreSlim）。前提の規模（最大 10 人）なら、待ちが出るのは日の始まり（全員の Planner が一斉に動く）くらいで、それも 3 時間の余裕に収まる。

1.6ホライズンと締め切り

ホライズンの考え方は VISION 4章のとおり。エンジンは、実行中のハンドラのホライズンの最小値を「壁」として持ち、壁以上の時刻のイベントは適用しない。

  • 壁は、ハンドラが起動したときに足し、出力を取り込んだとき（または取り消したとき）に外す
  • 壁と同じ時刻のイベントも待つ。Decider のようにホライズンが契機の時刻のハンドラでは、同じ時刻の後ろの段のイベント（ほかのペルソナの行動の開始など）も、出力が揃うまで待つことになる。Decider は LLM を使わず、ミリ秒で返るので問題にならない
  • 出力に、すでに処理した段より前の段のイベントが同じ時刻で入っていたら、次にそのまま処理する（巻き戻さない。VISION 4章）

締め切り

LLM が返らないと、壁で世界全体が止まる。そこで、ハンドラごとに締め切りの扱いを決めておく。

ハンドラ締め切り過ぎたとき
Plannerホライズン（3:00）取り消して、固定予定だけのプランを出す（VISION 4章「間に合わなかったとき」）
受信箱を捌くホライズン + 猶予取り消して、処理できなかった通知を受信箱に残す。何も送らない
投稿するホライズン + 猶予取り消して、空振りとして記録する
文面の作り直しホライズン + 猶予取り消して、発話を出さない
LLM を使わないものなし待つ（返らないのはバグなので、ログに出す）
案 P-05　締め切りの猶予と、運転モードによる違い 猶予は既定で 2 分（実時刻）。締め切りは、実時間運転のときだけ効かせる。早送り（ドライラン、追いつき）では、時計が待たずに進むので、ホライズンにはすぐ着いてしまう。そこでは締め切りを使わず、ハンドラが返るまで待つ。追いつきでは LLM を使うハンドラがそもそも動かない（VISION 4章）ので、待ちは起きない。

1.7適用前の検査

決める側の出力は、写しを見て作ったものなので、適用するまでに前提が変わっているかもしれない。そこで、出力のイベントに「適用してよい条件」（guard）を付け、Apply が適用の直前に評価する。

guard確かめること主な使い手
activityVersionペルソナの行動の版番号が、決めたときと同じDecider、効果のハンドラ、予定の乱れへの対応
feasible選んだ行動と場所が、いまの状態でも実行できる（requires、到達性、帰還できること、制限）Decider
rngCursor乱数の列の位置が、決めたときと同じ乱数を引いたすべての出力
planVersionペルソナのプランの版番号が、決めたときと同じPlanner
termUnset変換の辞書に、その語がまだない（または同じ変換）変換の記録
placeUnset同じ名前の場所が、まだない場所の追加
  • 同じハンドラの出力は、1つのまとまり（batch）として扱う。どれか1件の guard が通らなければ、そのイベントを「却下」にし、同じまとまりの残りの未適用のイベントも、すべて「却下」にする
  • まとまりには、却下されたときの動き（onReject）を持たせる。redecide は、同じ時刻（いま）に決めどきを積み直す。recompose は、文面の作り直しを積む（辞書の食い違い）。drop は何もしない（割り込みで不要になった場合）
  • 検査は、状態だけで決まるので決定的。Apply の一部として単体テストできる
案 P-06　検査は、イベントに付けた guard として Apply が評価する 出力を取り込むとき（1.4 の手順1）に一度だけ検査する案もあるが、取り込みから適用までの間に、ほかのペルソナの出力が先に適用されることがある（同じ語の判定など）。適用の直前に、1件ずつ検査するほうが漏れがない。

1.8状態遷移

イベントの状態

  • 適用番号を持つのは、applied と、processing / done の決めどきだけ。skipped と rejected は持たない（何も適用していないから）
  • rejected と skipped には、理由（status_reason）を残す。ビューアと実行レポートで、なぜ起きなかったかを読める
案 P-07　決めどきの適用番号は、処理中に入るときに振る VISION は「適用番号は、適用した瞬間に振る」「決めどきは、未適用 → 処理中 → 処理済みと進む」としている。決めどきにとっての「適用」は、処理中に入る瞬間なので、そこで振る。再起動で処理中のものを決め直すときは、状態を pending に戻さず、processing のままハンドラを起動し直す（効果は「未適用に戻して決め直す」と同じで、適用番号が振り直しで飛ばない）。

ペルソナの行動

  • 行動中のまま、固定ブロックの開始で次の行動に移ることもある（ブロックの開始が、前の行動を終わらせる）
  • 反射と出来事は、どの状態からでも割り込める。移動中に辺が伸びたときだけは中断せず、到着を積み直す（VISION 9章）
  • 行動の中身（どの行動を、どの場所で、いつまで）と、その版番号は、ペルソナインスタンスの状態に持つ（D3）

外向きの操作

VISION 10章のとおり、未送信 → 完了 / 失敗 / 不明 の4つだけ。未送信で残ったまま再起動したら、送らずに不明にする。

1.9トランザクションの境界

処理1つのトランザクションで書くもの書き手
イベントの適用変わった状態の行、イベントの状態と適用番号、後続のイベントの挿入、付随する表（受信箱、未送信の操作、生えた場所、辞書、発生中の出来事）エンジン
ハンドラの出力の取り込み出力のイベントの挿入、決めどきを done にエンジン
到着、投入、送信結果イベントの挿入（pending）。受信箱に入るのは、そのイベントを適用したときエンジン

  • SQLite は WAL モードで開き、エンジン用の書き込みの接続を1本、記憶の整理用の書き込みの接続を1本、読み取り用の接続をいくつか持つ。2つの書き手が書く表は重ならない
  • 実時間運転では、1件の適用ごとにコミットする。早送りでは、数百件ごとにまとめてコミットしてよい（落ちても、まとめた範囲が未適用に戻るだけで、整合は崩れない）

時計を読むのは、エンジンと配信役と到着の受付だけ。決める側には、契機のイベントの時刻を now として渡す（VISION 4章）。到着のイベントの時刻は、受付が時計の「いま」を読んで付ける。

1.11起動・停止・追いつき

起動

  1. スキーマのマイグレーションを当てる（D3）
  2. 定義（TOML）を読み、検証する。エラーがあれば起動しない
  3. 状態の表から SimState を組み立て、未適用と処理中のイベントでキューを作る
  4. 未送信の操作ごとに「送信不明」のイベントを挿入する
  5. 最後に適用したイベントの時刻と、いまの時刻を比べる。差が 1 分を超えていれば、追いつきに入る
  6. 処理中の決めどきのハンドラを起動し直し、エンジンを動かす

追いつき

  • 時計を VirtualClock にし、チャンネルを圏外にして、いまの時刻までを早送りする。いまの時刻に着いたら、時計を SystemClock に替え、ChannelOnline を出して、記憶の整理を1回まとめて起こす（VISION 4章、UC-1）
  • 追いつきの間に積んだイベントには、origin に catchup を付ける
  • 追いつきの最中に届いた到着のコマンドは、受け付けて保留し、追いつきが終わってから、いまの時刻で積む。到着のイベントは、時計の「いま」より前にできないから
案 P-08　追いつきの上限は 14 日 14 日を超える停止は、超えた分を早送りせずに飛ばす。飛ばす区間の先頭で、ペルソナを「空白」の状態にするイベント（persona.gap）を1件積む。状態変数は既定の初期値に戻し、居場所は睡眠ブロックの場所にして、実行中の行動は打ち切る。そこから 14 日分だけ、通常の追いつきで進める。

上限を設ける理由は、早送りの計算ではなく、記憶の整理の入力が膨らむこと。Decider だけの早送りは軽いので、上限は記憶の整理が一晩で捌ける量で決める。ebise の夜間ジョブも、遡る上限を 14 日にしている。

停止

  1. 受付を閉じる（新しいコマンドを受けない）
  2. 実行中のハンドラを取り消す。決めどきは processing のまま残り、次の起動で決め直す
  3. 実行中のトランザクションのコミットを待って、接続を閉じる。配信役が送信中のものは、結果を待たずに閉じてよい（次の起動で不明になる）

1.12定義の読み直し

  • 読み直しは、コマンドとしてエンジンに入る。エンジンは、TOML をすべて読み直して検証し、エラーがあれば拒否して、古い定義のまま動き続ける
  • 通れば、イベントとイベントの間で Definitions を差し替え、definitions.reloaded のイベント（定義のハッシュつき）を記録する。ログを読むときに、どの定義で動いていたかがわかる
  • 場所のグラフが変われば、最短経路のキャッシュ（D5）を作り直す
  • 固定予定の変更は、翌日のプランから効く（VISION 5章）
