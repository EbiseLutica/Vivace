この文書の役割

コアの実装は、この文書の節目を上から順に進める。ここが決めるのは「何をどの順で作り、どこまでできたら次へ進むか」と、各節目で設計のどこまでを作るか。仕組みの完成形は VISION.html と詳細設計（docs/design/）のまま。

  • 参照：各節目は、作るものを設計の章（D1〜D8）で指す。仕組みの説明は繰り返さない
  • 簡易版：設計の一部だけを作るときは、何を省いたかをその節目の「範囲外」に書く。設計書は完成形のまま残し、簡易版に合わせて直さない
  • 更新：終えた項目は、チェックを入れる（checked を足す）。順番や範囲が変わったら、ここを直す

進め方の原則

当初は、ebise 相当の再現を1つの到達点にして、決定的なルールを全部揃えてから LLM と Misskey をつなぐ順にしていた。それだと動きを眺められるまでが長すぎるので、2026-11-15 に、節目ごとに動かして眺められる形に組み直した。

  • 節目ごとに眺められる：どの節目も、終えた時点で vivace run か vivace dry-run で動きを読める状態にする
  • 設計は完成形、作るのは最小：各節目では、設計の中から、その節目に要る部分だけを作る。足りないものは、運転して困ったときに足す
  • いまある保証は守る：決定性、不変条件の検査、イベントの適用でだけ状態が変わることは、すでにあるので崩さない。新しい保証（再起動、追いつきなど）は、要る節目まで足さない
  • LLM は代わりの出力から：LLM を使うハンドラは、台本の LLM（ScriptedLlm）と失敗時の出力を先に作り、テストはそれで回す
  • 稼働データができるまでは作り直す：M5 の運転を始めるまでは、スキーマもペイロードも最初のバージョンを書き換えてよい。マイグレーションを積み上げない

全体の流れ

M1〜M4 はコンソールだけで動き、M5 で Misskey をつなぐ。M4 を終えた時点で、チャンネルを差し替えるだけで ebise の最低限を置き換えられる形になる。

終えた段階

組み直す前の手順で、段階0〜2 と段階3 の 3-1〜3-2c を終えた。中身は git の履歴と PR を正とし、ここには何があるかだけを書く。

  • 段階0 足場：Vivace.slnx、global.json、Directory.Build.props、Directory.Packages.props、xUnit v3 と Verify
  • 段階1 型と定義：ID と SimState、SimEvent とペイロード、TOML の DefinitionLoader と DefinitionValidator、固定予定の解決、IClock と VirtualClock、IRandom と SplitMixRandomSource、RouteTable、テスト用の町
  • 段階2 最初の1日：world.created、persona.created、day.started、plan.committed、plan.due、block.started、decision.requested、activity.chosen、travel.*、action.* の Apply と guard。SimEngine、レーン、UtilityDecider、固定予定だけのプラン（FallbackPlanner）、InMemoryStorage、不変条件の検査、7日のシナリオのスナップショット
  • 3-1〜3-1c：イベントタイプごとのルール（EventRules/）、状態の操作を record のメソッドに寄せる、ワールドとペルソナの ID の整理
  • 3-2a〜3-2c：名前の見直し、公開 API（InjectAsync、Subscribe、View、VivaceEngineBuilder）、vivace validate と vivace dry-run

旧手順の 3-3〜3-8 と段階4〜8 の項目は、下の節目と M6 以降 の候補に振り分けた。

各 PR に共通の決まり

  • 1つの PR に1つの振る舞い：マージした時点で、ビルドとテストが通り、vivace run と vivace dry-run が動く。差分は 1,500 行以内を目安にし、超えそうなら動く所で切る
  • 形を整えるだけの PR は作らない：名前や構造が邪魔になったら、それを触る PR の中で直す（別のコミットに分ける）。振る舞いを変えないリファクタだけの PR は、作業が進まなくなるほど邪魔なときに限る
  • ブランチ：impl/mN-内容（例：impl/m1-system-clock）。main から切る
  • PR の本文：vivace run か vivace dry-run の出力の変化（前後の抜粋）を貼る。レビューは振る舞いの変化から読む
  • コミット：CLAUDE.md の「コミットの粒度」に従う。コードと、そのテスト、関係する文書の修正を同じコミットに入れ、各コミットでビルドとテストが通る順に並べる
  • コードの書き方：CLAUDE.md の「コード」に従う（1ファイルに1つの型、ドキュメントコメント、決定性）
  • テスト：期待値は手で計算できる小さな例で固定し、実装から作らない。わざと壊して、テストが落ちることを確かめる。スナップショットを更新したら、変わった理由を PR に書く。LLM を使う部分は ScriptedLlm で回し、本物の LLM はテストに入れない
  • 設計書：設計の一部だけを作るのは、設計書を直さず、この文書の「範囲外」に書く。設計書の本文と食い違う判断をしたときだけ、正の章の本文を直し、docs/design/index.html の「枠の外の判断」に J-xx の番号と出どころ（エージェント（PR #N））を付けて載せる。合意の印は付けない。PR の本文には、ユーザーに見てほしい判断だけを多くても3件書く。docs/VISION.html の考え方が変わるものは、実装を止めずに無難な形で進め、PR の先頭に書く
  • 数値の調整：気づいた不自然な数値は、値を変えずに、PR の本文と、この文書の見つかった課題に書く
  • 見つかった課題：作業、レビュー、運転で見つけて、その PR で直さない課題は、PR の本文やチャットにだけ残さず、見つかった課題に足す。どの節目で扱うかが決まっているものは、その節目の項目に足す。片付けたら行を消す

M1 実時間で眺める

エンジンを実時間（と倍速）で回し、ペルソナが暮らす様子をコンソールに流す。永続化はしない。起動するたびに、いまの時刻からワールドとペルソナを生成し直す。

参照：D1 1.10、D4 4.6、D7 7.5

  • SystemClock：実時刻を返し、その時刻まで実際に待つ。実時刻は TimeProvider から取り、テストでは差し替える
  • ScaledClock：開始時刻から N 倍の速さで進む時計。眺める時間を縮めるために使う
  • vivace run <dir> [--speed N] [--seed S] [--all]：定義を読み、ワールドとペルソナを dry-run と同じ順に、いまの時刻で生成して、Ctrl+C まで回す。止めたら、適用、捨てた、却下の件数を出す
  • 流れる出力：Subscribe で受けた適用済みのイベントを、ワールドの現地時刻、ペルソナ、内容の1行にする。既定では行動と移動の開始と終了だけを出し、--all ですべてのイベントを出す。書式の組み立ては、テストできるクラスに分ける
  • 表示を日本語の文にする：run の流れる出力と dry-run の行動表で、ID の代わりに定義の名前（行動の display、場所・人・ワールドの name）を使い、読める文にする。名前がなければ ID のまま
  • 次の予定の場所へ向かう行動（core.go_to_next）は、着いたら決め直す。次の予定の場所にいて、ほかにできることがないときだけ待つ（J-112 を改めた）

範囲外：永続化と再起動（M3）、外からの入力とコマンドで待ちを起こすこと（M4）、デーモンと管理用 API、status などの CLI。

完了条件：SystemClock と ScaledClock の待ちのテストがある。出力の書式のテストがある。vivace run Vivace.Testing/Defs --speed 60 で、テスト用の町の1日分が流れ、読んで違和感がない。

M2 独り言を投稿する

ペルソナが、スマホを開く機会に、いまの生活に合った独り言を投稿する。投稿はコンソールのチャンネルに出す。最初に眺めて手応えを確かめる節目。

参照：D8 8.4、D4 4.4、4.3、D5 5.4、D6 6.6、D2 2.3

  • LLM の PoC：1つの実装を選び、投稿文が作れて、失敗と時間切れを扱えることだけを確かめる。結果は D8 8.4 に書く。D8 8.4 の残りの項目は、困ったときに確かめる
  • ILlmClient の最小版と、その実装。Vivace.Testing に ScriptedLlm。API キーは環境変数から読み、TOML には書かない。キーがなければ、失敗時の出力で動く
  • phone.opportunity：ブロックの phone と phone_every から積む。副行動の決定は「投稿する」と「何もしない」だけにする。何もしないは、所要時間 0 の core.idle として記録する
  • sns.post の最小版：コンテキストは、ペルソナの lore、いまの行動と場所、時刻、自分の直近の投稿数件。出力は outbound.speech、失敗したら post.skipped
  • IChannel の最小版（投稿だけ）と、コンソールのチャンネル。outbound.speech を受けて送る。投稿は、イベントの行と見分けられる形で出す

範囲外：スマホを開いて受信箱を見る副行動（M4）、副行動の状態変数の効果と利用の記録、話題の辞書と判定、場所の生成、文面の校閲、記憶、LlmPolicy と段の切り替え、送信の再試行、Misskey（M5）。ILlmClient は本文を返すだけで、構造化出力（GenerateAsync<T>）と ITool は作らない。outbound.speech から未送信の操作と Deliver を作るのは、チャンネルの PR。

完了条件：ScriptedLlm で、スマホを開く機会から投稿までがイベントの列に残るシナリオが通る。LLM が失敗しても、エンジンが止まらずに post.skipped が残る。本物の LLM で vivace run --speed を1日分回し、投稿が生活と矛盾しない。

M3 再起動しても続く

イベントを SQLite に記録し、起動したら記録から状態を戻して続きから動かす。M2 までの「起動するたびに生成し直す」をやめる。

参照：D1 1.9、1.11、D3 3.8、3.9、D7 7.4

  • Vivace.Storage.Sqlite：スキーマ、接続の設定、StorageBatch のコミット、イベントの読み出し
  • ペイロードの JSON（ソース生成、バージョン、知らないイベントタイプでの停止）
  • 起動の手順：記録から状態を戻し、処理中の決定タイミングとハンドラを起動し直す（設計の穴を、ここで決める）
  • 追いつき：止めていた間を早送りで進める。上限は 14 日
  • vivace run --db <path>。指定がなければ、M2 までと同じくメモリで動く
  • 再起動のテスト

範囲外：persona.gap、定義の読み直し（ReloadDefinitionsAsync）、送信不明の扱い。InMemoryStorage はテスト用に残す。

完了条件：シナリオのランダムな位置で止めて再起動しても、事実のイベントの列が止めなかったときと一致する。vivace run --db を止めて起動し直すと、続きから動く。

M4 話しかけると返事をする

vivace run の標準入力から、ペルソナに話しかけられるようにする。ペルソナは、次にスマホを開いたときに受信箱を見て返事をする。チャンネルの抽象が、Misskey の前に一通り通る。

参照：D1 1.10、D2 2.8、D4 4.3、D5 5.4、D6 6.5

  • エンジンの時計の待ち（イベントの時刻までの待ちと、RunUntilAsync の最後の時刻までの待ち）を、コマンドで起きるようにする（J-157）。D1 1.4 の手順2と4に合わせ、先頭を取り出す前に待ち、コマンドで起きたら手順1に戻る
  • コンソールのチャンネルの受け取り：標準入力の行（メンション、DM、フォロー）を、到着のイベントとして投入する。書式はこの PR で決め、vivace run の起動時に出す
  • 副行動に「スマホを開く（受信箱を見る）」を足す
  • InboxHandler の最小版：Message には返信を、Follow にはフォローバックを返す。結果は inbox.handled
  • IChannel に返信とフォローを足す

範囲外：Reaction と INotificationRule、文面の校閲、記憶、圏外の扱い、デーモンと管理用 API。

完了条件：ScriptedLlm で、投入したメンションに次のスマホを開く機会で返信するシナリオが通る。実行中の投入で、待ちが起きることのテストがある。本物の LLM で話しかけると、いまの行動と矛盾しない返事が来る。

M5 Misskey につなぐ

コンソールのチャンネルを Misskey に差し替え、ebise の最低限（投稿、返信、フォローバック）を置き換える。

参照：D4 4.3、4.7、D6 6.5、D7 7.1、D8 8.2、VISION 1章

  • Vivace.Channels.Misskey：HTTP と WebSocket の薄いクライアント、通知、送信、圏外明けの取り直し。インスタンスとトークンは環境変数から読む
  • ebise の audienceOf の規則の移植、同梱の行動 misskey.*
  • 送信の失敗の扱い：再試行と、送信中に落ちたときの「送信不明」
  • Vivace.Calendars.Japan
  • ebise のペルソナと世界を TOML に移す
  • 検証用のアカウントで、数日の実時間運転

範囲外：リバーシ（D4 4.7）、デーモンと管理用 API（M6 の候補）。

完了条件：投稿、返信、フォローバックが、実際の Misskey で数日続く。

見つかった課題

作業、レビュー、運転で見つけて、まだ直していない課題。設計書どうしの食い違いは、上の設計の穴に書く。扱う時期の節目に入るときに見て、片付けたら行を消す。

課題見つけた所起きること扱う時期
実機の Ctrl+C で、件数の行が出るかを確かめていないPR #19件数の行は、テストのキャンセルでしか確かめていない。System.CommandLine は、Ctrl+C のあと既定で2秒しか待たないので、ハンドラが遅いと件数の行を出す前に打ち切られるM2（LLM の待ちが入るので、そのときに確かめる）
DryRun() で時計を省くと、実時間の時計になるPR #18 のレビュードライランは早送りの時計（VirtualClock）のはずだが、いまはドキュメントコメントに書いただけで、検査していない。CLI の dry-run は時計を明示しているので、実害はないM2（チャンネルを作り、DryRun() に中身ができるとき）
同じ行動が続きやすいPR #22 の dry-run詩織が夕方に「テレビを見る」を3回、「喫茶店でひと休み」を2回続けた。香織の「本を読む」が、終わった同じ分にまた始まる。続けた回数による重みの下げ方（RepeatFactor）が弱いと見られるM2 以降（投稿で同じことばかり言うように見えてきたら）
生えた場所の名前が出ないPR #21流れる出力と行動表は、定義にない場所（生えた場所）を ID のまま出す場所の生成を作るとき（M6 以降）
投稿が自由時間の主の行動として選ばれやすいPR #23 の dry-run投稿の行動は効果を書いていないので、欲求で選ばれにくくなる理由がない。60 分の制限で、主の行動としての投稿は1時間に1回までに抑えたが、その分の機会は残る。投稿の場所は、いまの場所だけ（D5 5.2、J-169）M2 の次の PR（sns.post の効果と、投稿の制限を決めるとき）
次の予定の場所へ1分だけ行って戻るPR #23 の dry-run香織が 11-03 の 21:51 に居間から自分の部屋へ移動し、着いた 21:52 にすぐ居間へ戻った。次の予定の場所へ向かう行動（core.go_to_next）が移動だけで終わり、着いて決め直したときに、元の場所の行動が選ばれる（J-143）。予定の開始までまだ2時間あるM2 以降（行き来が目立ってきたら）
投稿の LLM 呼び出しを CancellationToken.None で呼ぶPR #未定 のレビュー取り消しは出力を捨てるだけで、呼び出しは止まらない。同じレーンの次の決定が待つ本物の LLM の PR で
ハンドラの例外を代わりの出力にするとき、例外を記録していないPR #未定 のレビューD7 7.1 の通知（ログ）がなく、落ちた原因が運転中に見えないCore のログを入れるとき
不変条件の Busy() が、ホライズン待ちの効果の出力を数えるPR #未定 のレビュー投稿の行動の間ずっと、そのペルソナの生存の検査が飛ばされるM2 以降
