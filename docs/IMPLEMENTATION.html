この文書の役割

コアの実装は、この文書の段階を上から順に進める。ここが決めるのは「何をどの順で作り、どこまでできたら次へ進むか」だけで、仕組みの正は VISION.html と詳細設計（docs/design/）のまま。

  • 参照：各段階は、作るものを設計の章（D1〜D8）で指す。仕組みの説明は繰り返さない
  • 更新：終えた項目は、チェックを入れる（checked を足す）。設計の落とし穴が見つかったら、設計書を直し、ここは順番や範囲が変わるときだけ直す
  • 範囲：Vivace.Core と、コアが外に求める口の実装。到達点は VISION 1章の「ebise 相当の再現」

進め方の原則

まず1人が1日を過ごす細い道を端から端まで通し、そのあとで太くする。設計の落とし穴は Apply とエンジンの境目に出やすいので、全イベントタイプの Apply を先に書き切らない。

  • 決定的な部分から：LLM を使う前に、時計、乱数、Apply、エンジン、永続化を固める。段階5 までは LLM なしで動く
  • LLM は代わりの出力から：ハンドラは失敗時の出力（D6 6.2）を先に作る。固定予定だけのプランは、段階2 でもう要る
  • テストは段階と一緒に：D7 7.4 の層を、段階ごとに足す。不変条件の検査は段階2 から常に回す
  • 落とし穴はその場で直す：見つけたら設計書を直し、判断を J-xx の一覧に足す。止まって相談するのは、VISION の考え方が変わるものだけ
  • 稼働データができるまでは作り直す：段階8 の運転を始めるまでは、スキーマもペイロードも最初の版を書き換えてよい。マイグレーションを積み上げない

全体の流れ

段階0〜5 は LLM なしで動き、段階6 で LLM、段階8 で Misskey をつなぐ。

案と判断はすべて合意済みで、残る未決は LLM の実装（D8 8.4）だけ。詳細設計の旧 0.7 の順番からは、3点変えた。Apply とエンジンを別の段階にせず、1日分の縦の通しに組み替えた。LLM の PoC は、エンジンの設計を左右しないので、段階6 までの並行作業にした。validate と dry-run は、数値の調整を早く始めるため、段階3 で作る。

段階2 最初の1日

1人が固定予定と Decider だけで暮らす。ここで扱うイベントタイプは、world.created、persona.created、day.started、plan.committed、plan.due、block.started、decision.requested、activity.chosen、travel.*、action.* に絞る。

参照：D1 1.2〜1.5、1.7、1.8、D2 2.3〜2.6、D5 5.1〜5.3、5.5

  • Engine：コマンドのキュー、優先度つきキュー、ホライズンの壁、適用、StartHandler の実行
  • Lanes：ペルソナごとの決定と計画のレーン（ワールドのレーンは、出来事を作る段階3 で足す）
  • UtilityDecider：候補、所要時間、スコア、抽選
  • Planner の代わりの出力：固定予定だけのプランを出す。起動は、記憶の整理を起こす行動の開始と plan.due。整理の待ちは、段階7 まで入れない
  • InMemoryStorage（Vivace.Testing）：IStorage の最小の実装。段階4 で捨てる前提で作る
  • Ingress の最小：ワールドとペルソナの生成

完了条件：仮想時計で7日回し、事実のイベントの列がスナップショットと一致する。全適用で不変条件が通る。

段階3 生活を揃える

LLM を除く決定的なルールを、すべて揃える。人がドライランの結果を読めるようにして、数値の調整もここから始める。段階3 は、下の 3-1〜3-8 の PR に分けて、上から順に進める。

参照：D1 1.13、D2 全体、D4 4.6、D5 5.4、5.6〜5.8、5.10、5.11、D7 7.1、7.5

完了条件（3-8 で満たす）：vivace dry-run --days 7 で2人の1週間が読め、反射、出来事、同行を含むシナリオが通る。全イベントタイプに Apply の単体テストがある。

各 PR に共通の決まり

  • 1つの PR に1つの振る舞い：マージした時点で、ビルドとテストが通り、3-2 以降は vivace dry-run が動く。差分は 1,500 行以内を目安にし、超えそうなら動く所で切って、残りを次の PR に回す（この手順書に PR を足す）
  • ブランチ：impl/phase-3-N-内容（例：impl/phase-3-1-split-rules）。main から切る
  • PR の本文：3-3 以降は、vivace dry-run の出力の変化（前後の抜粋）を貼る。レビューは振る舞いの変化から読む
  • コミット：CLAUDE.md の「コミットの粒度」に従う。コードと、そのテスト、関係する設計書の修正を同じコミットに入れ、各コミットでビルドとテストが通る順に並べる
  • コードの書き方：1ファイルに1つの型。ドキュメントコメントは、その型やメソッドの役割だけを簡潔に書き、設計書の番号（D3 3.8、J-xx など）や、実装が変わるたびに直す事情は書かない。private なメンバーにも付ける
  • 決定性：辞書の列挙順を結果に出さず、序数で並べる。カルチャに依る書式と解析、DateTime.Now、System.Random、GetHashCode を使わない。乱数を引いた出力は RngDraws を持つ
  • テスト：期待値は手で計算できる小さな例で固定し、実装から作らない。わざと壊して、テストが落ちることを確かめる。スナップショットを更新したら、変わった理由を PR に書く
  • 設計書：決めた細部は、正の章の本文に書き、docs/design/index.html の「枠の外の判断」に J-149 から番号を振って載せる。docs/VISION.html の考え方が変わるものは、実装を止めずに無難な形で進め、PR の先頭に書く
  • 数値の調整：気づいた不自然な数値（土曜に次の予定まで15時間45分待つ、など）は、PR の本文に書くだけにして、値は変えない。調整の進め方は別に決める

3-1 Apply をイベントタイプごとに分ける

振る舞いを変えないリファクタ。Rules を、イベントタイプごとのルールに分け、表から引いて呼ぶ形にする。

参照：D1 1.3、1.7、D2 2.3

  • IEventRule（イベントタイプと Apply）と、ペイロードを型つきで受け取る基底 EventRule<TPayload>
  • 段階2 で扱うイベントタイプごとに、ルールのクラスを1つずつ作る。ルールはフィールドを持たず、ルールどうしで呼び合わない
  • Rules.Apply は、guard の評価と、表からルールを引いて呼ぶことだけにする。表は起動時に組む不変の辞書。表にないタイプは、いまと同じく例外にする
  • 複数のルールが使う処理（状態の差し替え、後続のイベントの生成、ブロックの開始、率の計算し直しなど）は、関心ごとのクラスに分ける。1つの共通クラスに寄せない
  • 表が、段階2 で扱うタイプをすべて持つことのテスト

範囲外：振る舞いの変更、新しいイベントタイプ、プラグインがルールを足す仕組み。

完了条件：既存のテストがすべて通り、.verified.txt の差分がない。

3-2 公開 API と CLI

いまの生活（固定予定と Decider）を、外から動かして読めるようにする。以後の PR は、ここで作る dry-run で振る舞いの変化を見せる。

参照：D4 4.6、D2 2.8、D1 1.10、D7 7.2、7.5

  • VivaceEngine とビルダー（D4 4.6 の形）。中で SimEngine を使う
  • InjectAsync：コマンドのキューを通し、実行中にも受け付ける。いまの同期の Inject を置き換える
  • View（いまの写し）、Subscribe（適用済みのイベントを、コミットのあとに流す）、RunUntilAsync、DryRun
  • Ingress の全体：投入のときに、定義と対象を確かめる（D2 2.8）
  • vivace validate：定義のフォルダを読み、位置つきのエラーと警告を出す。エラーがあれば 0 以外で終わる
  • vivace dry-run --days N：定義のフォルダのワールドとペルソナを生成し、仮想時計で N 日回して、実行レポートの最小の形（D7 7.5）を出す。テスト用の定義（Vivace.Testing/Defs）で動くこと

範囲外：デーモン、status などデーモンと話すコマンド、SystemClock と ScaledClock（段階5）。

完了条件：vivace dry-run --days 7 で、テスト用の町の2人の1週間が読める。vivace validate は、テスト用の定義で問題 0 件、壊した定義で位置つきのエラーを出す。実行中の InjectAsync と、Subscribe の順が適用の記録と一致することのテストがある。既存のスナップショットは変わらない。

いま見えている設計の穴

穴場所起きること決める時期
再起動で起動し直せないハンドラがあるD1 1.3、1.11、D2 2.3復元の対象は処理中の決めどきだけ。day.started の抽選も同じで、再実行は J-123 で同じ結果になる（段階4 で扱う）。Planner、出来事の抽選、効果のハンドラは day.started、action.started、plan.due から起動するので、途中で落ちると、出力が届かないまま進む段階4
