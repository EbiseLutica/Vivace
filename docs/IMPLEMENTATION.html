この文書の役割

コアの実装は、この文書の段階を上から順に進める。ここが決めるのは「何をどの順で作り、どこまでできたら次へ進むか」だけで、仕組みの正は VISION.html と詳細設計（docs/design/）のまま。

  • 参照：各段階は、作るものを設計の章（D1〜D8）で指す。仕組みの説明は繰り返さない
  • 更新：終えた項目は、チェックを入れる（checked を足す）。設計の落とし穴が見つかったら、設計書を直し、ここは順番や範囲が変わるときだけ直す
  • 範囲：Vivace.Core と、コアが外に求める口の実装。到達点は VISION 1章の「ebise 相当の再現」

進め方の原則

まず1人が1日を過ごす細い道を端から端まで通し、そのあとで太くする。設計の落とし穴は Apply とエンジンの境目に出やすいので、全イベントタイプの Apply を先に書き切らない。

  • 決定的な部分から：LLM を使う前に、時計、乱数、Apply、エンジン、永続化を固める。段階5 までは LLM なしで動く
  • LLM は代わりの出力から：ハンドラは失敗時の出力（D6 6.2）を先に作る。固定予定だけのプランは、段階2 でもう要る
  • テストは段階と一緒に：D7 7.4 の層を、段階ごとに足す。不変条件の検査は段階2 から常に回す
  • 落とし穴はその場で直す：見つけたら設計書を直し、判断を J-xx の一覧に足す。止まって相談するのは、VISION の考え方が変わるものだけ
  • 稼働データができるまでは作り直す：段階8 の運転を始めるまでは、スキーマもペイロードも最初の版を書き換えてよい。マイグレーションを積み上げない

全体の流れ

段階0〜5 は LLM なしで動き、段階6 で LLM、段階8 で Misskey をつなぐ。

案と判断はすべて合意済みで、残る未決は LLM の実装（D8 8.4）だけ。詳細設計の旧 0.7 の順番からは、3点変えた。Apply とエンジンを別の段階にせず、1日分の縦の通しに組み替えた。LLM の PoC は、エンジンの設計を左右しないので、段階6 までの並行作業にした。validate と dry-run は、数値の調整を早く始めるため、段階3 で作る。

各段階の手順

段階は上から順に進め、完了条件を満たしたら次へ移る。作るものの中身は、参照の章を正とする。

段階0 足場

参照：D4 4.1、D8 8.1、8.2

  • Vivace.Cli と Vivace.Testing、テストのプロジェクトを作り、Vivace.slnx に入れる（いまは Vivace.Core だけが入っていて、Vivace.Cli は空のフォルダ）
  • global.json で SDK を固定し、プロジェクト共通の設定を Directory.Build.props にまとめる
  • D8 8.2 のライブラリを NuGet で確かめて、バージョンを固定する
  • xUnit v3 と Verify のテストを1本通す

完了条件：dotnet test が通る。

段階1 型と定義

参照：D2 2.1、2.2、D3 3.2〜3.7、3.9、D5 5.9、5.10、D7 7.2

  • ID の型、SimState 一式、SimEvent とペイロード、イベントタイプから段を引く表
  • 時間の文字列（"45m"）と現地時刻の計算
  • DefinitionLoader：TOML から Definitions を作る。組み込みの行動 core.* を埋め込む
  • DefinitionValidator：エラーは全項目、警告は段階が進むにつれて足す
  • 固定予定の解決：日付から、期間、例外日、祝日、入れ子（within）、時間帯の並べ書き（times）を踏まえたブロックを出す
  • IClock と VirtualClock、IRandom と SplitMixRandomSource、RouteTable
  • テスト用の小さな世界の定義（1ワールド、数か所の場所、2人、数個の行動）

完了条件：テスト用の定義が読め、壊した定義で位置つきのエラーが出る。乱数は実装を変えても同じ値になることを、既知の値で確かめる。

段階2 最初の1日

1人が固定予定と Decider だけで暮らす。ここで扱うイベントタイプは、world.created、persona.created、day.started、plan.committed、plan.due、block.started、decision.requested、activity.chosen、travel.*、action.* に絞る。

参照：D1 1.2〜1.5、1.7、1.8、D2 2.3〜2.6、D5 5.1〜5.3、5.5

  • Rules：上のイベントタイプの Apply、guard、行動の決定的な効果、状態変数の読み取りと率の切り替え
  • Engine：コマンドのキュー、優先度つきキュー、ホライズンの壁、適用、StartHandler の実行
  • Lanes：ペルソナごとの決定と計画、ワールドごとのレーン
  • UtilityDecider：候補、所要時間、スコア、抽選
  • Planner の代わりの出力：固定予定だけのプランを出す。起動は、記憶の整理を起こす行動の開始と plan.due。整理の待ちは、段階7 まで入れない
  • InMemoryStorage（Vivace.Testing）：IStorage の最小の実装。段階4 で捨てる前提で作る
  • Ingress の最小：ワールドとペルソナの生成
  • 不変条件の検査と、シナリオのスナップショットの仕組み

完了条件：仮想時計で7日回し、事実のイベントの列がスナップショットと一致する。全適用で不変条件が通る。

段階3 生活を揃える

LLM を除く決定的なルールを、すべて揃える。人がドライランの結果を読めるようにして、数値の調整もここから始める。

参照：D1 1.13、D2 全体、D4 4.6、D5 5.4、5.6〜5.8、5.10、5.11、D7 7.1、7.5

  • しきい値の予測と反射、寝不足、居合わせと社交欲求の率
  • 予定の乱れ（block.responded）
  • スマホを開く機会と副行動（候補はスマホを開く、投稿する、何もしない）。効果のハンドラは、何もしないものを入れておく
  • 出来事：IncidentLottery、効果、状態、到着の積み直し
  • 同行（with、on_partner_absent）
  • ペルソナとワールドの破棄
  • 残りのイベントタイプの Apply と guard
  • Ingress の全体、公開 API（VivaceEngine.Create()、InjectAsync、View、Subscribe、RunUntilAsync、DryRun）
  • Vivace.Cli：デーモンを使わない validate と dry-run。実行レポートの最小の形

完了条件：vivace dry-run --days 7 で2人の1週間が読め、反射、出来事、同行を含むシナリオが通る。全イベントタイプに Apply の単体テストがある。

段階4 永続化と再起動

参照：D1 1.9、1.11、1.12、D3 3.8、3.9、D7 7.4

  • Vivace.Storage.Sqlite：スキーマ、接続の設定、StorageBatch のコミット、IEventLog
  • ペイロードの JSON（ソース生成、版、知らないイベントタイプでの停止）
  • 起動と停止の手順、ハンドラの復元
  • 追いつき、persona.gap、14 日の上限
  • 定義の読み直し（ReloadDefinitionsAsync）
  • シナリオをメモリの SQLite に切り替え、InMemoryStorage を消す
  • 再起動のテスト

完了条件：シナリオのランダムな位置で止めて再起動しても、事実のイベントの列が止めなかったときと一致する。20 日止めても追いつける。

段階5 実時間の運転

参照：D1 1.6、1.10、D4 4.3、4.6、4.7、D7 7.1、7.3、7.5

  • SystemClock、ScaledClock、到着の受付、締め切り
  • IChannel、能力の語彙、プラグインの登録。テスト用の偽のチャンネル
  • Dispatcher と送信の再試行
  • 失敗の扱い（D7 7.1）、Status、RejectEventAsync、ResumeAsync、ログ、計測、IAdminNotifier
  • vivace daemon（--watch つき）、ローカルの管理用 API、イベントの流れ（SSE）
  • Vivace.Cli：デーモンと話す status、events、resume、inject、reload、report

完了条件：偽のチャンネルを相手にデーモンが実時間で動き、到着と送信が通る。CLI から状態とイベントの流れが見える。送信中に落とすと、次の起動で「送信不明」になる。

段階6 LLM のハンドラ

前提：LLM の PoC（D8 8.4）が終わっている。

参照：D4 4.4、D5 5.5、D6 6.1〜6.6、6.10、D7 7.1

  • Vivace.Llm.*、ScriptedLlm、エンジンの LLM の口（engine.Llm）、目的の登録、LlmPolicy
  • ContextBuilder と Diary
  • DayPlanner と PlanValidator
  • InboxHandler：Message、Reaction、Follow の処理と、Other を回す INotificationRule
  • PostHandler と TopicPipeline（辞書、判定、場所の生成、文面の作り直し）
  • 文面の校閲（post.review、inbox.review）
  • ProbeTopicsAsync と vivace probe

完了条件：台本の LLM のシナリオが通る。本物の LLM で3日のドライランを回し、実行レポートを読んで破綻がない。トークン数が痕跡に残る。

段階7 記憶

参照：D3 3.8、D6 6.3、6.4、6.7、6.8、D7 7.4

  • IMemoryStore と、整理用の書き込みの接続
  • MemoryConsolidator：層、カーソル、threads、汚染のフィルタ
  • Planner が整理の完了を待つ形にする（D5 5.5）
  • MemoryRetriever と memory.search のツール
  • 追いつきのあとのまとめての整理
  • 評価ケース（VISION 16章）を手で回せる形にする

完了条件：記憶が整理されて翌日の文脈に入る。dm の記憶が別の相手の文脈に入らない。評価ケースが通る。

段階8 Misskey で ebise 相当を再現する

参照：D4 4.3、4.7、D6 6.5、D7 7.5、D8 8.2、VISION 1章

  • Vivace.Channels.Misskey：HTTP と WebSocket の薄いクライアント、通知、タイムライン、送信、圏外明けの取り直し
  • ebise の audienceOf の規則の移植、同梱の行動 misskey.*
  • Vivace.Calendars.Japan
  • ebise のペルソナと世界を TOML に移す
  • 検証用のアカウントで、数日の実時間運転

完了条件：投稿、返信、フォローバック、生活感のある一貫性が、実際の Misskey で数日続く（VISION 1章の最初の到達点）。リバーシ（D4 4.7）は、この到達点に含めない。

いま見えている設計の穴

手順を組む途中で、設計書のどうしが噛み合わない所を2つ見つけた。どれも、表の段階に入るときに決めて、設計書を直す。

穴場所起きること決める時期
効果のハンドラの出力が、必ず却下されるD1 1.7、1.8、D2 2.2、D6 6.5出力は行動の終了の時刻で段7。同じ時刻の action.ended（段2）が先に適用される。D1 1.8 の「どの遷移でも版が上がる」のとおりなら、activityVersion の guard が通らない段階2。action.ended は版を上げず、打ち切りだけが上げる形が有力
再起動で起動し直せないハンドラがあるD1 1.3、1.11、D2 2.3復元の対象は処理中の決めどきだけ。Planner、出来事の抽選、効果のハンドラは day.started、action.started、plan.due から起動するので、途中で落ちると、出力が届かないまま進む段階4
